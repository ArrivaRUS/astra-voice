Транскрибация в Astra Cowork переведена с **whisper.cpp (small)** на **GigaAM RNNT** (Sber, русский-native) — внедрено и проверено вживую, commit dfd2de9 (CI зелёный).

**Как устроено в проде:** GigaAM живёт в ОТДЕЛЬНОМ venv (его torch 2.5.1), демон вызывает `automations/gigaam_worker.py` его интерпретатором как subprocess и читает построчный JSON (прогресс по чанкам + текст); `automations/transcribe.py` находит интерпретатор по `ASTRA_GIGAAM_PYTHON` или дефолтам (`~/.local/share/astra-cowork/gigaam-venv/bin/python`, дев — `~/.cache/gigaam-spike/bin/python`); веса — `ASTRA_GIGAAM_MODEL_DIR` или `data_dir/gigaam` (туда положен `v2_rnnt.ckpt`). Сборка venv — `scripts/setup_gigaam_venv.sh`. Дев-машина: рабочий venv в `~/.cache/gigaam-spike`, веса в `~/.local/share/astra-cowork/gigaam` (и `~/.cache/gigaam-models`).

**Диаризация «кто говорит» (commit 3d18177):** рецепт `audio2dialog` «Транскрибация с дикторами» → .txt «Спикер N: …». Офлайн, без HF-токена: silero-VAD → сегменты, GigaAM транскрибирует каждый (длинные дробятся на ≤28с), SpeechBrain ECAPA-TDNN эмбеддинги (публичная модель, без токена), агломеративная кластеризация по косинусу (порог 0.8, env `--diar-threshold`), короткие <1.5с → к соседу. `transcribe_audio(diarize=True)`; воркер ветка `--diarize`. Качество: разделяет реплики, но фикс-порог приблизителен (тихих участников может слить). Доп. deps в gigaam-venv: silero-vad, speechbrain, scikit-learn.

**Прогресс транскрибации на папке (commit aed42e1):** `FlyOverlayBar` раз в секунду поллит `state.db` и, если открытая в Fly-FM папка-автоматизация имеет running-задачу (файл лежит в ней), показывает её %/ETA прямо на оверлее (не только в ЦУП). Оверлей — `astra-cowork-fly-overlay` (autostart-сервис `app-astra-cowork-fly-overlay@autostart`); чтобы видеть прогресс на папке, он должен быть запущен.

**Почему whisper не годится:** на длинном русском аудио whisper-small (а) медленный (~RTF 2.1 на Intel i5-10210U → ~5ч CPU на 140-мин запись) и (б) **срывается в галлюцинаторную петлю** — на реальной 140-мин встрече 65% вывода (1912 из 2948 строк) оказались одной повторяющейся фразой-фантомом. Авторегрессионный декодер whisper залипает на участках тишины/шума.

**Замер спайка GigaAM `v2_rnnt` на том же i5 (CPU, fp16 off), на куске, где whisper сорвался:** связный корректный русский текст; **петель нет** (макс серия одинаковых слов = 2); **RTF инференса ≈ 0.18** (140-мин файл ≈ 25 мин против 5ч у whisper, ~12×). Прогресс по чанкам + ETA считаются естественно.

**Нюансы интеграции:**
- PyPI-пакет `gigaam==0.1.0` содержит модели до **v2** (`v1/v2_ctc/rnnt/ssl`); **v3 в pip нет** (новее релиза, GitHub/HF). Старт на `v2_rnnt`.
- `transcribe_longform` тянет **pyannote VAD (нужен HF-токен, онлайн, gated)** — для офлайн гос-ОС плохо. Обходим **простым окно-чанкованием (~24с)** через `model.transcribe(chunk)`; чанки = точки прогресса. (Опц. офлайн silero-VAD позже.)
- **Конфликт версий torch:** gigaam пинит `torch<=2.5.1`, в проекте torch 2.12 (для RAG/sentence-transformers). Спайк гонялся в изолированном venv (`~/.cache/gigaam-spike`) на torch 2.5.1. Главный вопрос интеграции — работает ли gigaam на torch 2.12 (тогда без даунгрейда) или выравнивать версии.
- Прогресс-обвязка из issue #1 (колонки `tasks.progress_fraction`/`eta_seconds`, `repo.update_task_progress`, `QProgressBar`, рефреш ЦУП) — **модель-независимая, остаётся целиком**; меняются только внутренности `automations/transcribe.py`.
- Корень `/` на машине почти полон (95%, ~2 ГБ) — ставить в venv на /home, CUDA-колёса не тащить (torch CPU), TMPDIR на /home.

**Отмена транскрибации (2026-07-20):** прервать долгую задачу можно кнопкой ✕ в блоке «Фоновые задачи» правой панели. Механика: `AutomationsManager.cancel_task` ставит флаг → `_RecipeRunner` видит его в **progress-колбэке** (единственная регулярная точка входа во время рецепта) → бросает `TaskCancelled` → `transcribe._run_worker` прибивает воркер. **Убивать надо ГРУППУ процессов**, а не прямого потомка: torch форкает детей, они остаются сиротами и жгут CPU. Поэтому `Popen(start_new_session=True)` + `os.killpg(SIGTERM→SIGKILL)` (`transcribe.kill_worker`). Проверено живьём: 3-мин аудио → 13% → отмена → статус `cancelled` за 11с, процессов не осталось.

**Две гонки отмены (обе найдены ТОЛЬКО живой проверкой, юнит-тесты их не видели):** (1) убийство одного процесса мало — надо группу (`start_new_session=True` + `killpg`), иначе форкнутые torch-потомки остаются сиротами; (2) отмена пишется в БД мгновенно, а воркер узнаёт о ней лишь в progress-колбэке (между чанками до ~30с) — в этом окне дедуп `_enqueue` видел «прошлая задача не активна» и ЗАПУСКАЛ файл заново, т.е. после ✕ поднимались новые воркеры (бесконечный цикл). Лечение: терминальный `cancelled` в дедупе обрабатывается явно (не воскрешаем) + файл помечается «не ретраить» синхронно, до сигнала failed. **Мораль: любую отмену длинной задачи проверять живьём — «статус cancelled» ещё не значит, что работа встала.**

**ВАЖНО про удаление исходника:** транскрибация декодирует mp3 во ВРЕМЕННЫЙ wav (`/tmp/tmpXXXX/audio.wav`) и дальше читает только его — поэтому **удаление оригинала НЕ мешает задаче дойти до конца** (проверено: пользователь удалил mp3 на ~40%, задача успешно записала .txt). Наивная авто-отмена по исчезновению исходника выбросила бы почти готовый результат, поэтому прерываем только если работа ещё не дала результата (`fraction <= 0`).
