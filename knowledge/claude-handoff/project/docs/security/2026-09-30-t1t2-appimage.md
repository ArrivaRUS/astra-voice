## 0. Вердикт

**✅ Слияние в `main`: можно.** Blocker'ов нет. Архитектура R3 и код не противоречат модели угроз: цепочка Debian (ключ → InRelease → Packages → .deb → control) построена fail-closed и проверяется при каждой сборке из кэша на **копии** файла; исходники проверяются по sha256 **до** любого разбора; окружение детей чистится в одной точке; политика — в одной точке (Python); CI — минимальные права, пины по SHA, без `pull_request_target`, секрет подписи изолирован шагом.

- **Blocker — 1 (уточнение T1, релиз/план, не слияние):** BL-1a/У101 — запланированный контроль BL-1 (`check_source` в Python) **не закрывает** угрозу: закреплённый runtime `dd6cebed` переиспользует существующий `$TMPDIR/appimage_extracted_<md5(содержимого)>` (`runtime.c:760`) и пропускает файлы того же размера (`:831-834`), затем `execv(prefix/AppRun)` (`:1637`) — чужой `AppRun` исполняется раньше любой нашей проверки. На многопользовательской машине достаточно быть первым, кто запустил этот же выпуск (§3.1). Контроль — вне бандла: runtime или отказ от extract-and-run на общем `TMPDIR`. Решение нужно до реализации 01.10.

### 1. `debverify.py`: статусы gpgv и clearsign — **ок**
- `packaging/appimage/debverify.py:45-60` белый список; `:151-155` любой статус вне списка → отказ (**fail-closed**); `:156-167` ровно один `GOODSIG`/`VALIDSIG`/`PLAINTEXT`, `VALIDSIG` — последнее поле = отпечаток **первичного** ключа (`tokens[-1]`) сравнивается с `signer` из lock; подпись подключом `4CB5…E131` даёт тот же primary — корректно.
- Проверено экспериментом: на просроченном ключе gpgv выдаёт `KEYEXPIRED`, `EXPKEYSIG` (оба вне списка) **при `VALIDSIG` и rc=0** — код отвергает (тест `test_expired_key_rejected`, `tests/unit/test_appimage_debian.py:1045`). `REVKEYSIG`/`EXPSIG`/`BADSIG`/`ERROR`/`FAILURE`/`NODATA` — вне списка → отказ. `ERRSIG`+`NO_PUBKEY` (подписи ключами 13/trixie и Stable 12, которых в keyring нет намеренно) — допущены и **не** засчитываются как GOODSIG — верно; именно поэтому «rc=0» здесь требовать нельзя (реальный InRelease даёт rc=2 из-за двух отсутствующих ключей при валидной нужной подписи). `TRUST_*`/`VERIFICATION_COMPLIANCE_MODE` gpgv 2.2.40 не печатает (подтверждено выводом эксперимента); новый статус будущей версии уронит сборку в сторону отказа, не пропуска.
- Порядок: `:136` структурная проверка clearsign на сырых байтах → `:142-148` gpgv с `--output` → тело берётся **только из вывода gpgv** (`:170`), не из файла. Clearsign «как apt» (`:92-125`): первая строка BEGIN, только `Hash:` до пустой строки, в теле строки на `-` только dash-escaped `- ` (второй BEGIN спрятать нельзя), ровно один блок подписи, после END — только пустое, CRLF снимается, не-UTF-8 → отказ. Codename/Suite из подписанного текста = lock (`:305-311`).

- `.dsc`: `strip_pgp` (`:402`) снимает **непроверенную** PGP-обёртку, но только **после** `check_file` по sha256 из `Sources` (`:388`), а `Sources` — из подписанного InRelease. Корректно.
- **MN-20 (уточнение после Astra §4 п.1):** `ERRSIG` в белом списке допущен **с любой причиной** и **без связи** с последующим `NO_PUBKEY` (реально Debian даёт пару `ERRSIG … 9`/`NO_PUBKEY` на ключи 13/trixie и Stable 12). ### 5. `git_tree`↔commit через GitHub API — **ок для безопасности, minor для провенанса (MN-16/П21)**
- Что фиксируется: sha256+размер архива (`appimage.lock:129-132`), `git_commit`, `git_tree`, дельта `git-trees/<id>.json` (только export-ignore `.gitignore/.gitattributes`, подмодули 160000, `.tag` export-subst, CRLF — `debverify.py:436-511`, каждое отличие воспроизводится, иное → отказ). `archive_git_tree` пересчитывает blob/tree-хэши — настоящая криптографическая связь **tree → содержимое**; связь **commit → tree** и **тег → commit** взяты из API при пине (обе от одного источника, TOFU 29.09). Тег `v5.15.19-lts-lgpl` не подписан — независимого якоря у Qt нет (download.qt.io недоступен).
- Что защищает: от подмены **после** пина (сеть, регенерация архива GitHub, зеркало) — да (sha256 + дерево). От лжи GitHub **в момент** пина — нет.

- **MN-16 (беклог):** при следующем пине связать commit → tree криптографически: `git fetch` коммита с `fetch.fsckObjects=true` и `git cat-file -p <commit>` → `tree` (git сам проверяет хэш объекта), и/или сверка commit-id тега с code.qt.io. Записать П21.
