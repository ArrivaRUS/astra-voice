# 029 · Squash-слияние стопки веток ломает следующую ветку; `-X ours` при этом молча портит хунки

**Дата:** 2026-09-30. **Где:** стопка `wip/ma-foundation` → `wip/r2-ci` → `wip/appimage-debian3` (PR #31/#32/#33) при слиянии в main.

## Что случилось
1. #31 и #32 слиты squash. У третьей ветки история содержит те же изменения отдельными коммитами, а в main они одним
   новым коммитом → для git это две разные правки одних и тех же строк → `git merge main` дал 18 конфликтов в файлах,
   которые ветка не трогала после r2-ci.
2. `git merge -X ours main` разрешил конфликты «по кускам» и в `scripts/sbom.py` собрал перемешанный хунк из двух
   версий (`)` + `],` + `}` подряд) — синтаксически неверный файл, без сообщения об ошибке. Поймано только сверкой
   `git diff <ветка-до-слияния> HEAD -- код` (должна быть пустой), а не тестами.
3. GitHub сам закрыл PR #33, когда его базовая ветка `wip/r2-ci` была удалена после слияния — новый PR #34.

## Правило
- Стопку веток сливать **только через полное обновление** следующей ветки: после squash-слияния N-й ветки в main —
  `git merge --no-commit main` в (N+1)-ю, **все конфликтные файлы брать из (N+1)-й целиком** (`git checkout <N+1> --
  <файлы>`), потому что main содержит ровно их N-ю версию; затем проверка `git diff <N+1 до слияния> HEAD -- . ':!docs'`
  пуста, lint, полная сюита. Либо не делать squash для стопки (merge-commit), либо сливать стопку одним PR.
- `-X ours`/`-X theirs` на конфликтах кода не использовать: они работают по хункам и могут склеить неверный файл.
- Перед удалением базовой ветки стопки — перенацелить зависимые PR (`gh pr edit --base main`) и дать им CI через
  новый коммит (retarget сам workflow не запускает), иначе GitHub закроет PR.
