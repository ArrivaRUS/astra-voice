# 018 · Codex завис после сна ноутбука, агент-обёртка ждал его 11 часов

**Дата:** 2026-09-24. **Где:** `developer-codex` на карточке модели (`wt-card`), `codex exec` pid 113956.

## Что случилось
Заказчик закрыл крышку ноутбука на ночь. Процесс `codex exec` (сетевая сессия с API) после пробуждения остался в
состоянии `S`, 0 % CPU, без вывода — соединение умерло, но процесс не завершился. Агент-обёртка ждал «пока Codex
работает» циклами `sleep 20/30` и `until grep RC=` и не имел критерия «процесс мёртв». Утром пришлось остановить
Codex по точному pid и возобновить сессию через `codex exec resume <session-id>` — наработки в worktree сохранились.
Второй симптом того же дня: другой агент сторожил Codex по строке в `ps`, совпадавшей с его собственной командой, и
«ждал» сам себя.

## Правило на будущее
1. **Ожидание Codex — с признаком жизни, не бесконечно.** Обёртка проверяет раз в минуту: процесс существует, cwd тот же
   (`readlink /proc/<pid>/cwd`), и **растёт ли размер/мtime лога Codex** (`~/.codex/sessions/.../rollout-*.jsonl`
   или перенаправленного stdout). Нет роста 15 минут подряд → считать зависшим: `kill <pid>` по точному pid, затем
   `codex exec resume <session-id>` с брифом «продолжи с места остановки, диф не переписывай». Два таких повтора →
   отчёт Юрке с состоянием дифа, а не тихое ожидание.
2. **Сторожить по pid из запуска, не по строке в `ps`.** Обёртка запоминает pid дочернего `codex` в момент запуска
   (`$!` / `Popen.pid`) и проверяет только его; поиск по `pgrep -f`/`ps | grep <строка>` запрещён (см. правила машины).
3. **Перед долгим циклом Codex — `session-id` в отчёт-заготовку**, чтобы возобновление было возможно без чтения
   всего `~/.codex/sessions/` (в этот раз пришлось отличать свой rollout от чужого по cwd).
4. Юрке: если заказчик пишет «закрывал крышку» — первым делом проверить процессы Codex по cwd worktree и их CPU/mtime.
