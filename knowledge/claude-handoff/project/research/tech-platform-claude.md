## Итог

1. **Самообновление.** Для машины заказчика (ЗПС выключен) реалистичен ровно тот механизм,
   что уже работает в Handy: скачать `.deb` из GitHub Releases → `pkexec`/polkit-диалог →
   `apt install ./x.deb`. Всё для этого на машине есть (polkit-KDE-агент, PackageKit,
   пользователь в `astra-admin`). Для машин **с включённой ЗПС** ни один вариант не работает
   «сам»: любое обновление приносит новые ELF/.so, которые обязаны быть подписаны, а ключи
   регистрируются в ядре только через `update-initramfs` + **перезагрузку** — то есть это
   всегда действие администратора, а не кнопка в GUI. Планировать надо два трека.
2. **Автозапуск.** `~/.config/autostart/*.desktop` — правильный и единственный нужный механизм:
   на этой машине Plasma 5.27 отдаёт их systemd (`app-Handy@autostart.service` виден живьём),
   так что мы бесплатно получаем и `systemctl --user` для проверки состояния. Свой
   `systemd --user` юнит писать не надо; `OnlyShowIn` не ставить (сессии Fly и KDE
   маркируются по-разному).
3. **GUI-стек.** Top-2: **(1) Python 3.11 + PyQt5 из apt Astra** (ноль вендоринга, лёгкий `.deb`,
   максимальная совместимость с ЗПС, весь системный слой — уже установленные пакеты) и
   **(2) Qt6 C++/QML 6.10 из apt Astra** (современнее вид, один собственный ELF).
   Неожиданная находка: в `repository-extended` Astra 1.8 лежит **Qt 6.10.2**, но
   python-биндингов Qt6 в apt нет вообще.
4. **Хоткей/вставка.** Схема Handy (глобальный хоткей + буфер обмена + `Ctrl+V` + восстановление
   буфера) — проверенно рабочая на этой машине и единственная, где кириллица не ломается.
   `xdotool type` для русского текста — заведомо ненадёжен.

### A.1 ЗПС (замкнутая программная среда) — что реально ограничивает

Источники: [Режим ЗПС в Astra Linux SE x.8](https://wiki.astralinux.ru/pages/viewpage.action?pageId=321820023)
и [Порядок создания подписей файлов для режима ЗПС](https://wiki.astralinux.ru/pages/viewpage.action?pageId=61574460)
— обе страницы вытянуты целиком и цитируются дословно.

- Контроль делает **невыгружаемый модуль ядра `digsig_verif`**; алгоритмы подписи —
  **ГОСТ Р 34.10-2012 (256)** и ГОСТ Р 34.10-2001 (`high`).
- Проверяются **«исполняемые файлы и разделяемые библиотеки»** — то есть **и `.so`**.
  Дословно: *«Для успешного запуска программ при включенной ЗПС подписаны должны быть не только
  исполняемые файлы приложений, но и используемые этими приложениями динамические библиотеки
  (файлы .so)»* (`high`). → **`.so` из pip-колёс (onnxruntime, sherpa-onnx, PyQt6, numpy) под ЗПС не запустятся без подписи.**
- **Интерпретируемые файлы** (bash, Python) в терминах документа — «неисполняемые», под
  `DIGSIG_ELF_MODE` **не попадают** (`high`). То есть чистый Python-код проходит; ловушка — его C-расширения.
  Отдельно существует «блокировка интерпретаторов», её включают вручную поверх ЗПС (`med` — детали на этой странице не раскрыты).
- Режимы: `DIGSIG_ELF_MODE` = 0 (выкл) / 1 (запрет запуска) / 2 (отладочный: пускает + предупреждает).
  `DIGSIG_ELF_VERIFICATION_MODE` = 0 (встраиваемая **и**, в 1.8, отсоединённая — **по умолчанию**) /
  1 (только xattr) / 2 (первая найденная) / 3 (встраиваемая + xattr) (`high`).
- **Ключи (главное для нас):**
  - `/etc/digsig/keys/` — ключи **обязаны быть подписаны изготовителем** (РусБИТех). Только такие
    годятся для **встраиваемой** подписи. Получаются по запросу («Как получить ключи для подписи СПО»).
  - `/etc/digsig/xattr_keys/` — **самоподписанные ключи разрешены**, подпись изготовителя не проверяется;
    годятся для подписи в расширенных атрибутах и (с 1.8) для отсоединённой.
  - `/etc/digsig/certs/` — появился в 1.8, ключи для **отсоединённых** подписей, тоже могут быть
    не подписаны изготовителем; но *«все ключи для проверки отсоединённых подписей должны быть
    загружены **до включения ЗПС**, при включенной ЗПС дополнительные ключи через интерфейс
    загружать нельзя»* (`high`).
  - Регистрация любых ключей в ядре: `sudo update-initramfs -u -k all` + **перезагрузка ОС** (`high`).
- Инструменты подписи: `bsign -s` (встраиваемая), `bsign -s -D` (отсоединённая, кладётся в
  `/etc/digsig/external_sig/@путь@к@файлу.sign`), с 1.8 — `bsign-integrator` (универсальный,
  умеет и поиск подписанных файлов). Управление режимом — `sudo astra-digsig-control enable|disable`
  (пакет `astra-safepolicy`) + GUI `astra-systemsettings astra_kcm_digsig` (`high`).
- Диагностика: `sudo dmesg | grep DIGSIG`, пример отказа —
  `DIGSIG:[ERROR] NOT ELF SIGNED: path=/home/astra/a.out` (`high`).

**Вывод по ЗПС.** Мы можем подписать свои бинарники и `.so` **самоподписанным** ключом ГОСТ
(тип подписи — xattr или отсоединённая), не выпрашивая ключи у РусБИТеха. Но:
① на каждой целевой машине админ должен положить наш публичный ключ и перезагрузиться;
② xattr-подписи теряются при копировании/архивировании без сохранения xattr — то есть при
самообновлении через скачанный файл подпись нужно накладывать заново уже на месте, а инструмент
подписи требует root; ③ отсоединённые подписи живут в `/etc/digsig/external_sig`,
куда пишет только root, и ключи нельзя добавлять при включённой ЗПС.
→ **Самообновление из GUI на машине с ЗПС технически неосуществимо в «одну кнопку»**; максимум —
«скачать пакет и позвать администратора» (`med-high`, вывод мой из совокупности правил выше).

### A.2 Четыре варианта — сравнение

| | 1. GitHub Releases → `.deb` → `pkexec apt install ./x.deb` | 2. Установка в `~/.local` без root (self-replace) | 3. Свой подписанный apt-репозиторий | 4. Flatpak |
|---|---|---|---|---|
| Права | нужен админ (polkit-диалог KDE, пароль) | **не нужны** | нужен админ один раз (добавить репо), дальше `apt` тоже под sudo | flatpak-репо добавляет админ; `--user` установка без root |
| Как выглядит на этой машине | штатное окно ввода пароля polkit-KDE (агент в автозапуске) `high` | без диалогов | штатный `apt` | `flatpak` 1.16.1 есть, remote-ы не проверял (не менял систему) `low` |
| Интеграция с меню Fly/KDE | `.desktop` в `/usr/share/applications` — как сейчас | `.desktop` в `~/.local/share/applications` — Fly/KDE их видят (XDG-стандарт) `med` | как №1 | Flatpak ставит `.desktop` сам |
| Автозапуск | `~/.config/autostart` — одинаково во всех вариантах | ✔ | ✔ | ✔ (но путь запуска — `flatpak run`) |
| Self-replace на лету | не нужен (пакет ставит dpkg) | **нужен**: заменять работающий бинарь/venv «под собой», перезапуск через `exec` | не нужен | не нужен |
| Совместимость с ЗПС | плохая: новые ELF/.so приезжают неподписанными | **худшая**: файлы в `$HOME`, xattr-подпись пользователь наложить не может | лучшая из четырёх (пакеты подписываются на сборке, ключ регистрируется один раз) | плохая: свой рантайм = сотни неподписанных ELF |
| Стоимость для нас | низкая (Handy это уже делает) | средняя (свой updater + аккуратный self-replace) | **высокая**: хостинг, GPG-ключ репозитория, `astra-create-flat-repo`/reprepro, регламент | высокая: рантайм Freedesktop, порталы для хоткеев/вставки на X11 — боль |
| Корп. реалии | сотрудник **без** `astra-admin` обновиться не сможет | работает у всех | обновляет админ централизованно — то, чего корп-ИБ и хочет | обычно запрещён политикой |

Дополнительно: **Tauri-updater уже умеет `.deb`** — changelog `tauri-plugin-updater`:

### A.3 Рекомендация

**(а) Машина заказчика сейчас (ЗПС выкл.)** — вариант **1**:
GitHub Releases API (`/repos/<org>/<repo>/releases/latest`) → скачать `.deb` во временный каталог →
проверить контрольную сумму/подпись (нашу — minisign или GPG; к ЗПС отношения не имеет) →
`pkexec /usr/bin/apt-get install -y ./astra-voice_X.Y.Z_amd64.deb` (именно `apt-get install ./файл`,
а не `dpkg -i`: apt дотянет зависимости) → предложить перезапуск.
Fallback, если polkit-диалог не появился: `pkcon install-local <файл.deb>` (PackageKit есть, действие
`package-install-untrusted` спрашивает пароль администратора).

**(б) Машина с ЗПС** — вариант **3** (свой подписанный репозиторий) как стратегия, а в GUI —
режим «только уведомление»: показать «Доступна версия X», кнопку «Что нового» и текст
«обновление устанавливает администратор». В `.deb` при этом класть все свои ELF/`.so` уже
**подписанными** на сборке (`bsign-integrator`, ГОСТ-ключ организации) и в `postinst` не пытаться
подписывать ничего на месте. Ключ организации — в комплект поставки; регистрация ключа + перезагрузка
= разовая процедура внедрения, описанная в инструкции для админа.

**Практический вывод для архитекторов:** чем меньше в продукте *собственных* ELF и `.so`, тем дешевле
ЗПС-трек. Python поверх системных Qt5/`libasound` даёт минимум неподписанных ELF; Tauri/Rust +
`onnxruntime` из pip/crates — максимум.

### A.4 Механика «строки внизу» (как у Handy)

- **Текущая версия**: для `.deb` честный источник — сам пакет: `dpkg-query -W -f='${Version}' astra-voice`.
  Проще и без подпроцесса — вшивать версию в билд (Python: `__version__`, генерируемый из
  `debian/changelog`; Rust: `env!("CARGO_PKG_VERSION")`). Handy берёт версию из бандла
  (`high`, код `UpdateChecker.tsx` + `tauri.conf.json`).
- **«Последняя проверка»**: `~/.config/astra-voice/state.json` (или `~/.local/state/astra-voice/`
  по XDG Base Dir) — поля `last_check_ts`, `last_seen_version`, `skipped_version`, `update_checks_enabled`.
  Handy держит флаг `update_checks_enabled` в настройках и **не ходит в сеть, пока он выключен** —
  правильное поведение для корпоративного контура, повторить (`high`, `UpdateChecker.tsx`).
- **UI**: у Handy это ровно то, что просит заказчик — строка внизу окна с тремя состояниями
  (`isChecking` → «Проверяю…», `updateAvailable` → «Доступна версия X» + кнопка «Установить»,
  `showUpToDate` → «Установлена последняя версия», гаснет через 3 с) + прогресс-бар по событию
  загрузки (`downloadedBytes/contentLength`). Копировать поведение 1:1 (`high`, читал код).
- **Периодичность**: проверка при старте + ручная кнопка. Автопроверку по таймеру не делать — на
  корп-машинах это лишний сетевой шум.
- **Оффлайн-контур**: обязательна кнопка «Обновить из файла…» (выбрать локальный `.deb`) —
  у части машин ALSE нет доступа в интернет.

## B. Автозапуск при входе в систему (Astra 1.8, Fly/KDE)

### Что проверено на машине (`high`)

- Сессия: `XDG_CURRENT_DESKTOP=KDE`, `DESKTOP_SESSION=plasma`, `Type=x11`.
- `systemctl --user is-system-running` → **`running`**, пользовательский инстанс systemd есть.
- В списке юнитов живьём: **`app-Handy@autostart.service`**, `app-blueman@autostart.service`,
  `app-kscreen@autostart.service`, `app-fly-shutdown-scheduler-service-autostart@autostart.service`.
  → Plasma 5.27 на этой Astra **отдаёт XDG-autostart генератору systemd**
  (`systemd-xdg-autostart-generator`; в Plasma по умолчанию с 5.25 —
  [David Edmundson, «Plasma and the systemd startup»](https://blog.davidedmundson.co.uk/blog/plasma-and-the-systemd-startup/), `med`;
  на нашей машине — факт, `high`).
- В `~/.config/autostart` уже лежат 7 файлов, включая **два** для Handy: `handy.desktop`
  (старый, `Exec=sh -c "sleep 8; exec '…/target/release/handy'"`) и `Handy.desktop`
  (`Exec=/usr/bin/handy`, написан `tauri-plugin-autostart`). Живой пример дубля.
- `/etc/xdg/autostart/klipper.desktop` содержит `OnlyShowIn=KDE;fly;`, а
  `/etc/xdg/autostart/fly-notifications.desktop` — `OnlyShowIn=Fly;`. Значит в системе реально
  существуют **две разные маркировки** окружения, и `OnlyShowIn` — ловушка.

### Рекомендация

1. **Механизм — XDG autostart**: `~/.config/autostart/ru.<org>.astra-voice.desktop`.
   Свой `systemd --user` юнит **не нужен** — генератор сделает
   `app-ru.<org>.astra-voice@autostart.service` сам, и мы бесплатно получаем
   `systemctl --user status/stop` для диагностики.
2. **`OnlyShowIn` не ставить вообще.** Отсутствие ключа = «показывать везде»; с `OnlyShowIn=KDE`
   мы сломаемся в Fly-сессии, с `OnlyShowIn=Fly` — в текущей KDE-сессии.
   `X-GNOME-Autostart-enabled=true` можно оставить как совместимость (так делают
   `astra-cowork.desktop` и `handy.desktop` на этой машине), вреда нет.
3. **Включение/выключение из настроек** — создать/удалить файл (или выставить `Hidden=true`).
   Проверка состояния — существование файла + отсутствие `Hidden=true`. Дополнительно можно
   сверяться с `systemctl --user is-enabled app-<name>@autostart.service`, но это не источник правды.
   Отдельного менеджера `fly-autostart` в системе не обнаружено (`med`, искал по `/usr/bin/astra-*`
   и `/etc/xdg/autostart`).
4. **Гонка со стартом сессии** — реальная проблема именно на этой машине:
   - трей: `org.kde.StatusNotifierWatcher` и `org.kde.StatusNotifierHost-3719` присутствуют на
     сессионной шине (`qdbus`, `high`), но появляются не мгновенно → в `.desktop` ставить
     `X-KDE-autostart-after=panel` (уже используется локально в `handy.desktop` и `astra-cowork.desktop`);
     плюс в коде **ретраить регистрацию трей-иконки**, а не падать.
   - звук: в памяти проекта зафиксирован инцидент «микрофон молчит» — гонка двух WirePlumber
     (linger-сессия пользователя + greeter fly-dm), профиль карты `sof-hda-dsp` слетает на загрузке;
     лечится `systemctl --user restart wireplumber` (`high` — свой опыт, память astra-cowork).
     → **Не открывать аудиоустройство на старте.** Открывать по первому нажатию хоткея, и при
     ошибке — не молча, а показывать в UI «микрофон недоступен, повторить».
   - Костыль `sleep 8` в `Exec=` (как в старом `handy.desktop`) — **не повторять**: лечит симптом
     и ломает «время до готовности».
5. **Двойной запуск** — обязателен single-instance: файловый лок в
   `$XDG_RUNTIME_DIR/astra-voice.lock` или уникальное имя на D-Bus; при повторном старте —
   показать окно уже запущенного экземпляра. У Handy для этого `tauri-plugin-single-instance`.
6. **Ловушка Handy, которую нельзя копировать**: Handy при старте **переписывает свой ярлык
   автозапуска на путь того файла, из которого запущен** — из-за этого на машине живут два
   ярлыка и легко «залипает» старый бинарь (`handy-gigaam/docs/TROUBLESHOOTING.md`, раздел
   «Запускается старая версия Handy», `high`). Наш `.desktop` должен всегда указывать на
   канонический путь из пакета (`/usr/bin/astra-voice`) и **не переписываться при каждом запуске**.

### Смежное: что нужно движку STT (граница с зоной другого ресёрчера)

- `sherpa-onnx` python-колёса — **manylinux2014 (glibc ≥ 2.17)**, у нас 2.36 → ставятся;
  CPU-колесо ~4.1 МБ, `sherpa-onnx-core` 9.5 МБ, `sherpa-onnx-bin` 21.6 МБ
  ([install docs](https://k2-fsa.github.io/sherpa/onnx/python/install.html), [PyPI](https://pypi.org/project/sherpa-onnx/), `med-high`).
- У sherpa-onnx есть **официальные C и Rust API** (`med-high`, там же). Сторонний крейт
  `sherpa-rs` объявлен deprecated в пользу официальных биндингов
  ([sherpa-rs README](https://github.com/thewh1teagle/sherpa-rs), `med`).
- **Риск для ЗПС одинаков для Python и Rust**: `libonnxruntime.so` / `libsherpa-onnx-c-api.so` —
  наши неподписанные ELF. Плюс известная грабля glibc: готовый onnxruntime ссылается на
  `__isoc23_strtoull`, чего нет в glibc 2.36 → нужен шим (`high`, TROUBLESHOOTING.md).
- VAD: `silero-vad` в формате ONNX прогоняется тем же sherpa-onnx (в нём есть готовый
  `VadModelConfig`/`silero_vad`) — отдельной зависимости не требуется (`med`).

### Top-2 (рекомендация ресёрчера, решение — за архитекторами)

**№1 — Python 3.11 + PyQt5 (QtQuick/QML) из apt Astra.**
Почему: (а) ноль вендоринга GUI — `.deb` зависит только от пакетов Astra, что снимает половину
проблем упаковки, от которых уходим; (б) **лучший профиль под ЗПС** — единственные неподписанные
ELF будут `.so` движка STT, и их список короткий и известный; (в) QtQuick 5.15 (QML,
`qml-module-qtquick-controls2` уже в системе) достаточно для «современного минималистичного» —
это не QtWidgets; (г) в команде уже есть Python+Qt-опыт (astra-cowork: оверлеи, детект темы
из `~/.config/kdeglobals`) — прямой переиспользуемый код; (д) быстрее всего до рабочего прототипа.
Минусы, которые надо принять: GPLv3 у PyQt5 и внешний вид QML 5.15 чуть «старее» Qt 6.

**№2 — Qt6 C++/QML 6.10 из `repository-extended`.**
Почему: тот же идеальный профиль ЗПС и упаковки, но современный Qt Quick и один-единственный
собственный ELF. Берём, если (i) QML 5.15 не вытянет макет дизайнера, или (ii) GPLv3 PyQt5
окажется неприемлем (Qt6 из системы — LGPL, динамическая линковка).
**Блокер к проверке до выбора:** реально ли `qt6-*` 6.10.2 доступен на машинах заказчика
(у нас он в `repository-extended`, а установлен 6.4.2).

**Tauri 2 (№3) в top-2 не предлагаю**, хотя соблазн большой (весь код Handy переиспользуется):
это ровно тот стек, от которого заказчик просил уйти, и он же худший под ЗПС. Но **логику**
из Handy (updater-строка, схема вставки, оверлей, single-instance) переносим в любом случае.

## D. Глобальный хоткей и вставка текста на X11/KDE

### Хоткей

| Способ | Push-to-talk (удержание) | Плюсы | Минусы |
|---|---|---|---|
| **`python3-xlib` + `XGrabKey`** | да (ловим KeyPress/KeyRelease) | есть в apt Astra (`python3-xlib` 0.33), без root, работает поверх любого окна | самому обрабатывать XKB-раскладки и маски модификаторов (Num/Caps Lock → `Mod2`/`Lock`); захват «съедает» комбинацию у всех приложений |
| **`pynput`** | да | простой API | **в apt Astra отсутствует** → pip-зависимость (тянет тот же python-xlib), лишний вендоринг |
| **`KGlobalAccel` (D-Bus)** | **нет** — даёт «нажатие», не удержание | родной путь KDE, комбинация видна в «Параметрах системы», конфликты разрулены | ① только toggle, push-to-talk не сделать; ② `org.kde.kglobalaccel` есть на шине (`high`), но в **Fly-сессии** его может не быть → неоднородность |
| **`evdev`** | да, самый надёжный | видит клавиши до X, работает и в Wayland | нужны права на `/dev/input/*`; пользователь `astra` **в группе `input`** (`id`, `high`), но у корпоративных пользователей может не быть; `python3-evdev` в apt есть |
| **`rdev` / `tauri-plugin-global-shortcut`** (Rust) | да | проверено в Handy на этой машине | только для Rust-стека |

**Рекомендация:** `XGrabKey` через `python3-xlib` как основной (push-to-talk и toggle из одного кода),
`evdev` — опциональный «надёжный режим» для тех, у кого есть группа `input`.
KGlobalAccel — только чтобы зарегистрировать красивую строчку в настройках KDE, не как механизм.

### Вставка текста

- **Буфер обмена + `Ctrl+V` + восстановление буфера — проверенный победитель.** Именно так делает
  Handy, и на этой машине это работает: сохранить текущий текст буфера → записать распознанное →
  задержка `paste_delay_ms` → послать `Ctrl+V` (варианты `Ctrl+Shift+V` и `Shift+Insert`) →
  задержка 50 мс → вернуть исходный буфер
  (`handy-gigaam/vendor/Handy/src-tauri/src/clipboard.rs`, `high`).
  Что обязательно повторить: **выбор комбинации вставки настройкой** (терминалы требуют
  `Ctrl+Shift+V`), настраиваемая задержка перед вставкой, восстановление буфера.
- **`xdotool type` — не годится для русского.** Посимвольная эмуляция не работает с Unicode вне
  текущей раскладки и требует временного ремаппинга keymap ([xdotool](https://github.com/jordansissel/xdotool),
  обсуждения по X11/XKB, `med`). Для кириллицы это потери символов и мусор при переключении
  раскладок. Держать только как аварийный fallback и явно помечать в настройках.
- **`XTest` + временная раскладка** — то же самое, что `xdotool type` под капотом: та же проблема
  плюс гонки, если пользователь переключает раскладку в момент вставки.
- **По приложениям** (ожидания, `med`; надёжно проверено только для Handy на этой машине):
  - терминалы (Konsole, xterm): `Ctrl+V` не сработает → `Ctrl+Shift+V` или `Shift+Insert`;
  - браузеры (Chromium/Firefox/Yandex): `Ctrl+V` работает;
  - LibreOffice: `Ctrl+V` работает, но вставляет с форматированием буфера → **писать в буфер только
    `text/plain`**, тогда обычный `Ctrl+V` даст чистый текст без диалога «Специальная вставка».
- **Klipper** (менеджер буфера KDE, в автозапуске — `/etc/xdg/autostart/klipper.desktop`, `high`)
  запомнит наш временный текст в истории буфера: ① утечка распознанного текста в историю,
  ② возможная гонка при восстановлении буфера. Проверить и, если надо, помечать данные как
  скрытые (`x-kde-passwordManagerHint`) либо честно предупредить пользователя.
- **Оверлей записи**: у Handy — отдельное прозрачное окно без декораций, `always_on_top`,
  `skip_taskbar` + принудительное «наверх» (`force_overlay_topmost`). В памяти проекта astra-cowork
  зафиксировано, что в KDE этого мало: нужен `StaysOnTop` + обработка occlusion и grace-период при
  перетаскивании (`high` — свой опыт с оверлеем Fly-FM). Тему (тёмная/светлая) брать **не из палитры Qt**,
  а читать `~/.config/kdeglobals`: в дочернем процессе оверлея палитра Qt врёт (`high`, там же).

## Находки и риски

- **R1 — ЗПС ломает саму идею «обновление кнопкой».** На машине с включённой ЗПС любое новое
  ELF/`.so` требует подписи, а регистрация ключа — `update-initramfs` + **перезагрузка**. Надо
  заранее решить: делаем ли ЗПС-трек вообще, или для таких машин в GUI просто «уведомление +
  инструкция админу». (`high`)
- **R2 — корпоративный пользователь без `astra-admin` не сможет установить обновление** ни через
  `pkexec apt`, ни через `pkcon` — polkit спросит пароль администратора. Наш заказчик сейчас в
  `astra-admin`, но это не типовой случай. (`high`)
- **R3 — `.so` движка STT — единственное «грязное пятно» даже у самого чистого стека.**
  `onnxruntime`/`sherpa-onnx` придётся или подписывать, или (для ЗПС-машин) поставлять отдельным
  подписанным пакетом. Плюс известный шим `__isoc23_strtoull` под glibc 2.36. (`high`)
- **R4 — PyQt5 = GPLv3.** Публичный репозиторий это допускает, но закрывает путь к проприетарной
  поставке. Альтернатива без ограничения — Qt6 C++ (LGPL) или Rust-стек. (`med`)
- **R5 — Qt6 6.10 «кандидат, но не установлен».** Строить на нём — значит завязаться на
  `repository-extended`; надо подтвердить, что он подключён у всех целевых машин. (`med`)
- **R6 — две сессии (Fly и KDE) маркируются по-разному** (`OnlyShowIn=Fly` vs `OnlyShowIn=KDE;fly;`
  живьём в `/etc/xdg/autostart`). Любая привязка к окружению — источник «у меня не запускается». (`high`)
- **R7 — гонка на старте сессии**: WirePlumber (микрофон отваливается) и появление трея.
  Лечится архитектурно (ленивое открытие аудио + ретрай трея), не `sleep`-ом. (`high`)
- **R8 — Klipper пишет наш временный буфер в историю.** Приватность распознанной речи. (`med`)
- **R9 — паттерн Handy «переписывать свой ярлык автозапуска на текущий путь»** приводит к
  залипанию старой версии и дублям в `~/.config/autostart` (наблюдается прямо сейчас:
  `handy.desktop` + `Handy.desktop`). Не копировать. (`high`)
- **R10 — flatpak на X11**: глобальный хоткей и синтез нажатий из песочницы требуют дыр в
  разрешениях (`--socket=x11 --device=all`), что обнуляет смысл песочницы и вряд ли пройдёт
  корп-политику. Вариант 4 отбрасываю. (`med`)

## Противоречия между источниками

1. **Tauri updater и `.deb`.** Официальная документация
   [v2.tauri.app/plugin/updater](https://v2.tauri.app/plugin/updater/) на Linux упоминает только
   AppImage; changelog `tauri-plugin-updater` прямо пишет, что поддерживаются Deb/Rpm/AppImage
   (PR #1991, #2624). Считаю верным changelog, но **проверить на стенде до принятия решения**.
2. **Куда класть самоподписанный ключ для отсоединённой подписи.** Страница «Порядок создания
   подписей» велит класть в `/etc/digsig/xattr_keys`; страница «Режим ЗПС x.8» описывает
   `/etc/digsig/certs` как каталог именно «ключей для проверки отсоединённых подписей»
   (появился в 1.8). Возможно, рабочие оба. Проверять на стенде с включённой ЗПС.
3. **Версии Qt6.** PROJECT.md фиксирует «Qt6 6.4.2» — это *установленная* версия; в
   `repository-extended` **доступен 6.10.2**. Не противоречие источников, а неточность карточки
   проекта — стоит поправить.

## Вопросы к человеку

1. **Целевая аудитория: только машина заказчика или корпоративные ALSE с включённой ЗПС?**
   От этого зависит, тратим ли мы силы на ГОСТ-подпись и свой репозиторий (отдельный крупный
   кусок работ), или делаем один простой трек «GitHub Releases → `.deb` → polkit».
2. **Лицензия.** Публичный GitHub — значит ли это, что GPLv3 (PyQt5) приемлем, или нужна
   возможность закрытой/коммерческой поставки в будущем? Это решает выбор между Top-1 и Top-2.
3. **Подключён ли `repository-extended` на целевых машинах** (нужен для Qt6 6.10)?
4. **Приватность распознанного текста**: допустимо ли, что распознанная фраза попадает в историю
   Klipper, или нужна защита?

## Предлагаемый следующий шаг

Готово к передаче архитекторам (`dual-architect`) вместе с отчётом по моделям.
Перед фиксацией стека предлагаю три коротких проверки на стенде (не на машине заказчика):

1. **Спайк GUI, ~1 день**: минимальное окно PyQt5+QML на этой Astra — тёмная тема из `kdeglobals`,
   трей через `QSystemTrayIcon`, прозрачный оверлей поверх окон. Ответит на «хватает ли QML 5.15
   для макета» — главный вопрос выбора Top-1 vs Top-2.
2. **Спайк обновления, ~0.5 дня**: `pkexec apt-get install ./test.deb` из GUI-процесса — убедиться,
   что polkit-KDE рисует окно пароля и не блокирует основной поток.
3. **Спайк ЗПС, ~1 день** (только если ответ на вопрос 1 — «корпоративные машины»): ВМ с
   `astra-digsig-control enable`, самоподписанный ГОСТ-ключ, `bsign-integrator`, попытка запустить
   Python + `sherpa-onnx`. Это единственный способ снять R1/R3 с уровня «предположение».
