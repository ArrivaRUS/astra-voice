# Межпроектный контракт Astra Voice ↔ Astra Cowork

Дата: 2026-09-24. Релиз: **v0.2**, согласно новому решению заказчика. Статус: предложение независимого архитектора для согласования контракта до планирования v0.2.

План подготовлен чтением обоих репозиториев. Код и файлы не изменялись; GUI, службы, тесты и обращения к рабочему D-Bus не запускались. Второй архитектурный план не использован.

## 1. Резюме контракта — 10 строк

1. Транспорт — пользовательский D-Bus через локальное Unix-соединение; Voice использует уже имеющийся PyQt5.QtDBus.
2. Cowork публикует сервис `org.astra.Cowork`, объект `/org/astra/Cowork/Command1`, интерфейс `org.astra.Cowork.Command1`.
3. Наличие исполняемого файла, ярлыка или пользовательского юнита означает «установлен», но не «готов».
4. Живая готовность проверяется при начале командной диктовки и повторно перед доставкой; фонового опроса нет.
5. Voice передаёт одну законченную строку, источник `astra-voice`, версию контракта и уникальный идентификатор запроса.
6. Cowork сразу регистрирует обычную задачу помощнику; предварительное заполнение формы и дополнительное подтверждение не требуются.
7. `ACCEPTED` означает регистрацию задачи с идентификатором, а не успешное выполнение поручения.
8. Проверка и доставка ограничены общим бюджетом 300 мс после распознавания; при отказе текст остаётся в буфере без вставки.
9. Автоматической повторной отправки нет; дедупликация переживает перезапуск Cowork, потерянный ответ считается неопределённым исходом.
10. Текст исключается из технических журналов и статистики обеих сторон; исполнение, история задач и разрешения принадлежат Cowork.

## 2. Выбор транспорта

| Вариант | Преимущества | Недостатки и ограничения | Решение |
|---|---|---|---|
| **D-Bus session bus, Unix-транспорт** | Владелец имени и уведомления о его смене; типизированные сообщения; учётные данные отправителя; QtDBus уже используется обоими приложениями | Нужно ограничивать время всей операции, исключить автоматическую активацию и учесть зависания QtDBus | **Основной транспорт v1** |
| Unix-сокет демона | Не требует TCP; доступны права файлов и `SO_PEERCRED`; у Voice уже есть QtNetwork | Собственный протокол, framing, лимиты, обнаружение, очистка сокета, контроль владельца и восстановление соединения | Резервная архитектура при доказанной непригодности QtDBus; не второй автоматический путь |
| CLI `astra-cowork --…` | Удобен для ручной диагностики | Сейчас CLI — вход в демон, команды доставки нет; запуск процесса, риск текста в argv, неоднозначное подтверждение и риск второго экземпляра | Не использовать для доставки; будущий CLI может быть клиентом того же D-Bus API |
| REST Hermes `127.0.0.1:8765` | Существующий транспорт Cowork ↔ Hermes | TCP даже на loopback; токен становится доступен Voice; обходятся диспетчеризация и UX Cowork; `POST /v1/messages` ждёт результат до 1800 с | **Не использовать из Voice** |

Выбор опирается на существующий код:

- Voice уже импортирует QtDBus в `ui/tray.py` и `ui/notify.py`; дополнительный Python-пакет для IPC не нужен.
- В `ui/tray.py` Voice подключение и обслуживание D-Bus вынесены из GUI-потока из-за возможных зависаний. Этот опыт нужно применить и здесь.
- Cowork использует `qtpy.QtDBus` в `daemon/tray.py`. Наличие `dbus-next` в зависимостях не требует вводить ещё один цикл событий для этой интеграции.
- Текущий REST описан в [docs/hermes_adapter.md](</home/astra/Документы/Astra Cowork/astra-cowork/docs/hermes_adapter.md>) и остаётся внутренним транспортом Cowork.

**Ограничение соединения:** оба участника используют только адрес пользовательской шины с транспортом `unix:`. Адреса D-Bus через TCP и запуск шины через `autolaunch` не допускаются. При неподходящей среде — недоступность и запасной путь.

## 3. Точная спецификация вызова

### 3.1. Адрес и версия

| Поле | Значение |
|---|---|
| Well-known name | `org.astra.Cowork` |
| Object path | `/org/astra/Cowork/Command1` |
| Interface | `org.astra.Cowork.Command1` |
| Версия первого контракта | `1.0` |
| Источник | Строго `astra-voice` |
| Владелец имени | Единственный экземпляр пользовательского демона Cowork |
| Автоматическая активация | Запрещена для вызовов Voice |

Имя захватывается без очереди ожидания и без вытеснения действующего владельца. Конфликт регистрации выключает внешний приём у нового экземпляра; он не выдаёт себя за готовый.

Ниже обозначения D-Bus: `u` — uint32, `t` — uint64, `s` — строка. Выходные аргументы перечислены отдельно, не упакованы в дополнительную структуру.

### 3.2. Методы

```text
GetStatus()
  -> u major,
     u minor,
     s instance_id,
     s state,
     s reason,
     u max_text_bytes

SubmitCommand(
     u major,
     u minor,
     s request_id,
     s source,
     s expected_instance_id,
     s text,
     t deadline_boottime_us)
  -> u code,
     s reason,
     s task_id,
     s instance_id

GetRequest(
     u major,
     u minor,
     s request_id,
     s source)
  -> u state,
     s task_id,
     s task_state,
     s instance_id
```

`instance_id` — UUID нового экземпляра приёмника. Меняется после перезапуска демона или переподключения к шине.

`GetStatus.state`:

| Значение | Смысл |
|---|---|
| `ready` | Приёмник может зарегистрировать новую внешнюю задачу |
| `busy` | Приём временно ограничен |
| `not_ready` | Инициализация, остановка, ошибка необходимого компонента |
| `disabled` | Внешний приём запрещён настройкой или политикой Cowork |

`reason` — закрытый машинный код, без произвольного текста исключения. Для статуса: `none`, `starting`, `stopping`, `queue_full`, `rate_limited`, `session_locked`, `auth_unavailable`, `backend_unavailable`, `storage_unavailable`, `policy_disabled`.

`GetRequest.state`:

- `0 UNKNOWN` — сохранённой квитанции нет; это **не разрешение повторить** запрос.
- `1 ACCEPTED` — запрос был принят, возвращается прежний `task_id`.
- `2 UNAVAILABLE` — состояние установить нельзя.

`task_state`: `queued`, `running`, `attention`, `completed`, `failed`, `interrupted`, `deleted`, `unknown`. Это справочная информация; Voice не становится интерфейсом наблюдения за задачами.

### 3.3. Поля запроса и валидация

| Поле | Правило |
|---|---|
| `major`, `minor` | Для первой версии — `1`, `0` |
| `request_id` | Канонический UUIDv4; создаётся один раз для одной законченной диктовки |
| `source` | Только `astra-voice`; метка происхождения, не доказательство личности |
| `expected_instance_id` | Значение из последнего успешного `GetStatus` |
| `text` | Непустая строка, максимум **16 384 байта UTF-8**, без вложений |
| `deadline_boottime_us` | Абсолютный срок допуска по Linux `CLOCK_BOOTTIME`, в микросекундах |

Voice склеивает сегменты по порядку, применяет существующую нормализацию `platform/paste.py`, удаляет крайние пробелы. Дополнительно переводит Unicode-разделители строк U+2028/U+2029 в пробелы. Cowork независимо проверяет отсутствие переводов строк, C0/C1 и превышения лимита.

Cowork не исправляет и не обрезает запрос молча. Несоответствие формату — отказ. Слишком длинную команду Voice целиком сохраняет для ручной передачи, не разбивает на несколько поручений.

Срок выставляется на оставшуюся часть бюджета доставки. Приёмник отклоняет новый запрос с истёкшим сроком или сроком более чем на 300 мс в будущем. Проверка выполняется и при получении, и перед началом транзакции регистрации. Она исключает исполнение сообщения, пролежавшего в очереди, но не устраняет гонку между фиксацией транзакции и потерей ответа.

### 3.4. Ответ на доставку

| Код | Имя | Семантика |
|---:|---|---|
| `0` | `ACCEPTED` | Задача и квитанция сохранены; `task_id` непустой |
| `1` | `BUSY` | Запрос не принят; очередь или лимит допуска заняты |
| `2` | `REFUSED` | Запрос не принят: политика, блокировка сеанса или полномочия |
| `3` | `NOT_READY` | Запрос не принят: обязательный компонент недоступен |
| `4` | `INVALID_ARGUMENT` | Запрос не принят: формат, длина, источник или идентификатор |
| `5` | `UNSUPPORTED_VERSION` | Запрос не принят: версия не поддерживается |
| `6` | `ID_CONFLICT` | Такой идентификатор уже связан с другим содержимым |
| `7` | `STALE_INSTANCE` | Новый запрос адресован уже сменившемуся экземпляру |
| `8` | `EXPIRED` | Новый запрос поступил слишком поздно |
| `9` | `INTERNAL_ERROR` | Подтверждён откат регистрации; задача не создана |

Для `ACCEPTED` допустимы причины `accepted` и `already_accepted`. Для остальных ответов `task_id` пустой.

Если приёмник не способен доказать откат транзакции, он не возвращает определённое «не принято»: клиент получает транспортную ошибку или тайм-аут и рассматривает исход как неизвестный.

Ошибки D-Bus, включая отсутствие владельца, неизвестный метод, потерю соединения и `NoReply`, обрабатываются отдельно от кодов приложения. Неизвестный код или повреждённый ответ не считаются успехом.

### 3.5. Тайм-ауты

**При начале командной диктовки:**

- асинхронный `GetStatus`, предел 300 мс;
- запись и появление индикатора не ждут ответа;
- неготовность не отбрасывает речь: после распознавания пользователь получит текст через запасной путь.

**После получения результата распознавания:**

- единый абсолютный бюджет **300 мс** на повторную проверку, доставку и переход интерфейса в конечное состояние;
- целевой внутренний бюджет IPC — до 250 мс, оставшиеся 50 мс — публикация буфера и обновление UI;
- поиск владельца, проверка его UID, `GetStatus` и `SubmitCommand` расходуют один бюджет, а не получают по 300 мс каждый;
- ни один вызов не блокирует GUI-поток;
- ожидания Hermes, загрузки модели и выполнения задачи в этом бюджете нет.

Voice получает уникальное имя владельца сервиса и адресует проверку и доставку этому владельцу. При его смене старое подтверждение готовности аннулируется. Методы вызываются без синхронного `Introspect` и без автоматического запуска Cowork.

Это проверяемая граница поведения приложения, а не обещание жёсткого реального времени при остановленном планировщиком GUI.

### 3.6. Что делает Cowork

**Основной сценарий — немедленная отправка задачи.** Это соответствует F17.5 и S18-A1: фраза должна уйти сразу, а предварительный просмотр в Voice уже отнесён к P2.

Предлагаемый внутренний путь:

```text
D-Bus-приёмник
  → проверка допуска и дедупликации
  → регистрация задачи и квитанции
  → штатная диспетчеризация Cowork
  → локальное умение либо Hermes
  → штатные подтверждения, результат и ошибки Cowork
```

Параметры задачи:

- `source = "astra-voice"`;
- текст — полученная строка;
- вложения и список файлов пустые;
- отсутствует неявное заимствование выделения, буфера, снимка экрана или черновика формы;
- адресация диалога — как у новой задачи виджета; существующие правила операционных команд и отмены сохраняются.

Не следует реализовывать это последовательностью `open_form(prefill=...)` → искусственный Enter. Сейчас `open_form` объединяет текст с черновиком, а `on_task_submitted` очищает черновик и вложения. Такой путь способен отправить или удалить чужой незаконченный материал.

Нужен общий прикладной метод отправки для формы и внешнего входа с явными аргументами. Представление внешней задачи не должно изменять черновик формы.

В Cowork:

- задача видна в «Чатах и задачах» с источником «Astra Voice»;
- штатная индикация приёма и ссылка «Открыть» доступны без раскрытия текста в системном уведомлении;
- основное окно автоматически не раскрывается — это соответствует текущему поведению `prompt_widget`;
- занятость отдельного диалога или выполнение других задач сами по себе не означают глобальный `BUSY`;
- запрещён обход обычных разрешений Cowork.

**Существенная правка оркестратора:** текущий `TaskPool.submit()` может отменить другую задачу ещё до `create_task()`. Для внешнего контракта вычисление маршрута должно быть отделено от действий: отмена, запуск локального умения и обращение к Hermes допускаются только после фиксации приёма. Иначе ответ «не принято» уже мог бы иметь побочный эффект.

### 3.7. Идемпотентность и перезапуск

Ключ дедупликации: `(UID, source, request_id)`.

Cowork сохраняет квитанцию и задачу **в одной транзакции**. Уникальное ограничение в БД защищает от двух одновременно пришедших одинаковых запросов.

Правила:

1. Повтор с тем же идентификатором и содержимым возвращает прежний `task_id`, не создавая задачу и не повторяя действия.
2. Тот же идентификатор с другим текстом — `ID_CONFLICT`.
3. Сравнение выполняется с защищённым содержимым задачи; текст и его хеш не попадают в технический журнал.
4. Квитанции хранятся минимум 24 часа, в том числе после удаления задачи; при невозможности проверить совпадение повтор отвергается, а не исполняется заново.
5. Гарантия повтора ограничена этим сроком. После него повторная доставка старого запроса контрактом не разрешена.
6. Уже существующая квитанция может быть возвращена после рестарта независимо от старого `expected_instance_id`; новый запрос со старым экземпляром отвергается.
7. **Voice автоматически не повторяет `SubmitCommand`**, в том числе после рестарта или `BUSY`.

После краха Cowork сохранённые, заведомо ещё не переданные на исполнение задачи могут быть восстановлены. Для задач, выполнение которых уже могло начаться, состояние — «прервано / исход неизвестен», без автоматического повторения действий. Контракт гарантирует дедупликацию приёма, но не «ровно одно» внешнее действие при любом крахе.

### 3.8. Версионирование и публикация

- `GetStatus` возвращает максимальную поддерживаемую minor-версию интерфейса 1.
- Voice выбирает максимальную общую minor-версию. Cowork с `1.n` обязан принимать все предыдущие `1.x`.
- Ломающие изменения получают новый интерфейс и путь `Command2`; сервис может одновременно поддерживать обе версии.
- Нет общей версии — отказ, буфер, пояснение «Версии программ не подходят друг другу. Обновите программы».
- Переход на REST, CLI или вставку в окно при несовместимости запрещён.

Публикуемые артефакты в обоих репозиториях:

```text
docs/contracts/astra-voice.md
docs/contracts/astra-voice-v1.xml
docs/contracts/astra-voice-v1-vectors.json
```

Markdown задаёт семантику, XML — точные D-Bus-сигнатуры, JSON — общие положительные и отрицательные тестовые векторы. JSON Schema не является необходимой зависимостью исполнения: транспорт не JSON.

Предлагаемый владелец канонической копии — сопровождающий Cowork как поставщик API; изменения согласуются с сопровождающим Voice. Копии имеют одинаковую ревизию и контрольные суммы. CI каждого проекта проверяет реализацию против своей зафиксированной копии и общих векторов.

Сам этот план ещё не означает двустороннюю фиксацию контракта. Условие до планирования v0.2 закрывается принятием одинаковой ревизии обеими сторонами.

## 4. Признак доступности

### 4.1. Статическое обнаружение

Проверять при старте, входе на экран 3 мастера, открытии «Общих» и по кнопке «Проверить снова».

`installed = true`, если обнаружен хотя бы один артефакт:

| Артефакт | Проверка |
|---|---|
| `astra-cowork` в PATH | Поиск исполняемого файла без его запуска |
| `astra-cowork.desktop` | XDG-каталоги приложений, пользовательский и системный autostart; учитывать `Hidden=true` |
| `astra-cowork-daemon.service` | Наличие файла в пользовательских каталогах юнитов systemd и системных каталогах user units |

Не запускать `astra-cowork --version`, не опрашивать systemd и не читать журнал ради детекта. Артефакт — эвристика установки, не удостоверение подлинности и не доказательство работоспособности.

Упаковка Cowork должна гарантировать хотя бы один такой артефакт. Установленную, но отключённую службу всё равно считать установленной.

Без артефактов:

- командную клавишу не захватывать;
- вторую строку в мастере скрыть;
- в «Общих» показать «Astra Cowork не установлен»;
- Win остаётся системной клавишей.

### 4.2. Живая доступность

Разделять состояния:

| Уровень | Доказательство |
|---|---|
| Установлен | Статический артефакт |
| Запущен приёмник | Есть владелец D-Bus-имени |
| Совместим | Ответ `GetStatus` поддерживаемой версии |
| Готов принять | `state=ready`, действующий экземпляр и допустимый контекст сеанса |

`ready` требует:

- завершённой инициализации внешнего входа и оркестратора;
- доступного хранилища задач;
- работающего пути отображения результата пользователю;
- разрешённого внешнего приёма;
- незаблокированного сеанса;
- свободного допуска по очереди;
- корректно инициализированной авторизации Cowork и известного рабочего состояния необходимого backend.

Сведения о backend берутся из уже имеющегося состояния Cowork. `GetStatus` не выполняет HTTP-проверку по запросу Voice и не ждёт модели. Готовность означает возможность принять ответственность за задачу, не гарантию успешного ответа помощника.

Подписка на `NameOwnerChanged` используется для сброса кеша, без фонового polling. При открытии настроек допустим один живой запрос. После неудачного запроса показывать «Доступность не подтверждена», а не утверждать, что помощник точно остановлен.

Кратковременная недоступность Cowork не освобождает Win: регистрация режима определяется установкой и политикой. Иначе клавиша непредсказуемо меняла бы назначение при каждом рестарте.

## 5. Безопасность

### 5.1. Граница доверия

В текущей модели угроз другой процесс того же UID явно считается недоверенным — [docs/threat-model.md, §2](</home/astra/Документы/astra-voice/docs/threat-model.md:39>). Раздел 4 этого документа посвящён главным образом обновлятору и не является уже выданным одобрением новой IPC-поверхности.

Предложение для T2:

- разрешать вызовы только от того же UID через пользовательскую локальную шину;
- получать UID отправителя от D-Bus, а не из аргументов;
- проверять UID владельца Cowork на стороне Voice;
- PID допустим для диагностики и проверки жизненного цикла, но не является надёжной авторизацией приложения;
- проверка имени процесса, argv или пути Python не доказывает, что отправитель — Voice.

**Остаточный риск:** любой процесс того же UID может вызвать API или занять имя при отсутствии Cowork. Session bus не изолирует приложения одного пользователя. Предлагается принять эту границу для v0.2 при сохранении всех разрешений Cowork; окончательный вердикт — отдельный T2.

Если требуется отличать доверенный Voice от произвольного процесса того же UID, нужен отдельный механизм изоляции/аттестации. Общий секрет в доступном этому UID файле такую задачу не решает.

### 5.2. Токен

Voice не читает, не создаёт и не передаёт `auth.toml`. Новый D-Bus-вход не использует Bearer-токен Hermes.

Текущий Cowork создаёт токен при инициализации. Если файл отсутствует, работает его штатная процедура создания. Если авторизация не может быть инициализирована либо Hermes отвергает токен:

- до приёма — `NOT_READY/auth_unavailable`;
- после приёма — ошибка задачи в Cowork;
- никаких анонимных запросов или ослабления авторизации.

### 5.3. Текст и журналы

Запрет охватывает INFO, DEBUG, исключения, HTTP-ошибки, журналы плагина, диагностику и статистику:

- не писать строку, префикс, тело D-Bus-сообщения или HTTP-запроса;
- не журналировать `str(exc)`/`repr(exc)`, если исключение могло включить содержимое;
- разрешены код результата, версия, длина, время, `request_id` и `task_id`;
- не передавать команду через argv, переменные окружения или временный файл;
- не рассылать текст D-Bus-сигналом.

**Найденные обязательные исправления Cowork:**

| Место | Текущее поведение |
|---|---|
| `daemon/service.py::_on_widget_submit` | INFO с `preview=text[:80]` |
| `hermes/client.py::send_message` | DEBUG с `preview=text[:80]` |
| Обработка ошибок HTTP и оркестратора | Встречаются тело ответа и строковое представление исключения; необходима проверка распространения текста |

Одного безопасного D-Bus-приёмника недостаточно. Перед включением интеграции нужно проверить весь путь до плагина и настройки диагностики движка. Запрет логирования должен действовать и при включённом DEBUG.

История задач — отдельная категория: `Task.text`, текст чата и производный заголовок уже сохраняются Cowork. План сохраняет это поведение для выполнения требования «команда видна в чате/задачах». Это **не** обещание отсутствия текста на диске Cowork. Voice хранит последний текст только по своим существующим правилам.

### 5.4. Исполнение, ограничения и политика

- IPC-приёмник не интерпретирует строку как shell, argv, имя метода, путь к скрипту или программный код.
- Строка поступает как обычный пользовательский запрос в Cowork; дальнейшие действия проходят его штатные проверки.
- Максимум 16 КиБ текста; ограниченная очередь приёма — 8 запросов на UID; ограничение частоты — 10 новых запросов в минуту с кратким всплеском до 3.
- Превышение лимита — `BUSY`, без скрытой очереди повторов.
- Заблокированный сеанс — отказ.
- Внешний вход должен иметь собственную возможность отключения в Cowork.

`command_hotkey=` или `off` запрещает режим в Voice: нет захвата, записи командного режима и отправки. Проверка выполняется в рантайме, включая момент перед доставкой, а не только в UI.

Этот ключ не запрещает другим программам обращаться к Cowork. Для запрета всех внешних команд нужна политика самого Cowork.

### 5.5. Сеть и буфер

Voice не открывает IP-соединений для обнаружения, готовности или доставки; REST Hermes ему недоступен по архитектуре.

Дальнейшая сеть Cowork определяется его собственными настройками. В «Приватности» Voice:

> «Команды передаются Astra Cowork на этом компьютере. Дальше действуют его настройки обработки и хранения данных».

При успешной доставке буфер не меняется. При отказе используется существующая публикация `text/plain` с подсказками менеджерам буфера KDE/Fly, без восстановления прежнего содержимого и без синтетических клавиш.

## 6. Отказы и запасной путь

| Ситуация | Voice | Cowork |
|---|---|---|
| Не установлен | Режим не регистрируется | Ничего |
| Установлен, приёмник не запущен | После распознавания — буфер и «Помощник недоступен — текст в буфере» | Ничего |
| `BUSY` | Та же пилюля; подробность «Помощник сейчас занят»; без повтора | Новую задачу не создаёт, текущая работа продолжается |
| `REFUSED` | Буфер; понятная причина запрета | Никаких действий по запросу |
| Несовместимая версия | Буфер; предложение обновить программы | Никаких действий |
| Невалидный или слишком длинный запрос | Буфер с полным текстом; понятная причина | Никаких действий |
| Нет ответа за бюджет | Буфер; исход помечается как неизвестный | Задача могла быть принята |
| `ACCEPTED`, позже ошибка выполнения | Voice уже завершил доставку | Ошибка в задаче и штатной индикации Cowork |
| Ошибка публикации буфера | «Не удалось скопировать текст»; последний текст доступен в Voice | По фактическому исходу доставки |

Для недоставленного текста пилюля показывается 3 с. Уведомление: «Открыть Astra Cowork» и «Что случилось». Первая кнопка запускает проверенный установленный launcher только по явному действию пользователя, без текста команды в аргументах и без повторной отправки.

**Потеря подтверждения — особый случай.** Тайм-аут не доказывает, что задача не создана. В подробностях:

> «Не удалось узнать, принята ли команда. Перед повторной отправкой проверьте задачи в Astra Cowork».

Поздний достоверный `ACCEPTED` для того же запроса может уточнить индикацию. Он не вызывает новую отправку и не очищает буфер автоматически. `GetRequest` используется для проверки по действию пользователя либо если ответ успевает в оставшийся бюджет; постоянного опроса нет.

**Перезапуск во время диктовки:**

1. Потеря владельца инвалидирует старые сведения о готовности.
2. Voice продолжает запись и распознавание.
3. Перед доставкой проверяется новый экземпляр.
4. Если новый экземпляр готов в пределах бюджета — команда отправляется ему один раз.
5. Если запрос уже был отправлен прежнему экземпляру, передача новому автоматически не повторяется.

**Отмена:**

- `Esc`/«×» до отправки исключает вызов Cowork;
- пустое распознавание не отправляется и не заменяет буфер;
- отменённый или устаревший результат воркера не доставляется;
- после отправки запроса Voice не обещает отменить уже принятую задачу: остановка выполняется средствами Cowork.

Во всех исходах режима «Команда» отсутствуют вставка в активное окно и зависимость адресата от `focus_client()`. Существующая защита фокуса остаётся важной для режима «Текст», включая обычную диктовку в форму Cowork.

### Детали реализации Voice

- Добавить явный `DictationMode.TEXT | COMMAND`, закреплённый за `utterance_id`; смена настроек или другое нажатие не меняет адресата уже записанной фразы.
- Распознавание остаётся в текущем воркере. Новый процесс распознавания и новый аудиопротокол не нужны.
- Выделить `DELIVERING_COMMAND`, не переиспользовать ветку вставки с её автоматическим повтором.
- Ошибка одного хоткея не блокирует другой; перезахват раз в 30 с отдельно для каждого, без кнопки ручного повтора захвата.
- Отсутствующий ключ политики — пользовательское значение либо Win по умолчанию; **присутствующий пустой ключ** и `off` — запрет.
- Неразбираемое значение или совпадение с «Текст» — отключить командный режим, не подставлять Win.
- Нечитаемая/испорченная обнаруженная политика не должна включать командный режим по умолчанию. Текущий общий подход `invalid → absent` для этого пути непригоден.
- В мосты добавить `commandHotkey`, доступность Cowork, целевой режим захвата и статус политики. Сохранение и откат при ошибке проходят через существующий механизм SettingsBridge.
- Обновить [docs/ui-bridge.md](</home/astra/Документы/astra-voice/docs/ui-bridge.md>) вместе с QML; сейчас экран 3 описывает одну комбинацию.

### Ключевые автоматические проверки

- Qt5-клиент ↔ Qt6-сервер: точные типы, Unicode, границы размера, неизвестная версия.
- Приём один раз при двух одинаковых одновременных вызовах, потере ответа и рестарте.
- Крах до фиксации, после фиксации и после начала действия; отсутствие повторного действия.
- Зависший приёмник, смена владельца, занятое хранилище: Voice завершает ожидание и остаётся отзывчивым.
- Непустой черновик с вложением не меняется после внешней команды.
- Режим Command никогда не вызывает XTest, восстановление фокуса или AUTO-вставку.
- Политика пусто/off/ошибка/совпадение, независимый перезахват.
- Контрольная строка отсутствует в технических логах обеих сторон при DEBUG, ошибках и отказах.
- Cowork-тесты — `QT_QPA_PLATFORM=offscreen`; D-Bus — отдельная тестовая шина, без рабочего сеанса.

## 8. Риски и проверки вживую

| Риск | Следствие | Проверка / мера |
|---|---|---|
| QtDBus может задержать подключение или обслуживание | Превышение 300 мс, зависание UI | Выделенный Qt-поток, абсолютный deadline, тест зависшей шины |
| Текущий `submit()` делает действия до регистрации | Побочный эффект при ответе «не принято» | Разделение планирования и исполнения, тесты порядка событий |
| Потерянный ответ после сохранения | Пользователь может повторить уже принятую команду | Квитанция, `GetRequest`, отсутствие автоматического повтора, честное пояснение |
| Процесс того же UID подделывает отправителя/сервис | Ложные поручения или получение текста | Явное принятие границы T2; UID не выдавать за идентификацию приложения |
| Preview и исключения содержат текст | Нарушение приватности | Сквозной аудит и контрольная строка на всех уровнях |
| Работа с формой удаляет черновик | Потеря материала пользователя | Отдельное представление внешней задачи, без имитации Enter |
| Формальное обнаружение по старому ярлыку | «Установлен», но недоступен | Не смешивать статический детект с живой готовностью |
| Win и evdev взаимодействуют иначе, чем XGrabKey | Системные действия или соседние хоткеи срабатывают во время записи | S7 и совместный живой прогон |
| Демон работает из старого prod-worktree | Checkout исправлен, рабочая интеграция отсутствует | Проверять реально развёрнутую ревизию обеих сторон |
| Пользовательская шина общая для нескольких GUI-сеансов | Команда попадает не на тот рабочий стол | В v1 поддерживать один активный графический сеанс данного UID; многосеансовость требует отдельной адресации |

**Только после отдельного «ок» заказчика на живую проверку `:0` и пользовательского D-Bus:**

1. KDE и Fly: короткий тап Win, удержание, системные сочетания до/во время записи, освобождение после штатного выхода и краха.
2. Совместное поведение с evdev-хоткеями Cowork, Ctrl×2, Ctrl+Space и проверкой занятости другой программой.
3. Команда при курсоре в Kate, терминале, форме Cowork и при открытом черновике: отсутствие вставки, успешная передача без изменения буфера.
4. Потеря активации формы: обычная диктовка не закрывает её; командная доставка не зависит от оконного фокуса.
5. Остановка, перегрузка и перезапуск Cowork во время записи и доставки; измерение всей задержки после распознавания.
6. Отсутствующий/нечитаемый токен и отказ backend — на отдельной тестовой конфигурации, без порчи рабочего токена.
7. **20 команд:** `tcpdump` на внешних интерфейсах и loopback плюс наблюдение сокетов процесса. Сам `tcpdump` не устанавливает PID, поэтому нужна корреляция с процессом Voice; ожидаются только локальные Unix-соединения, без IP-соединений Voice.
8. Контрольная фраза отсутствует в журналах Voice, Cowork и технических журналах плагина; её наличие в пользовательской истории Cowork оценивается отдельно.
9. Развёртывание Cowork через согласованный снимок prod-worktree, сверка хеша работающей версии. Перезапуск — только в разрешённое окно без важных активных задач.

Необходимость этих разрешений следует из брифа: в текущем задании разрешено только чтение. Никакие живые проверки этим планом не объявляются выполненными.

## 9. Открытые вопросы заказчику

1. **Принимаем ли для v0.2 границу «любой процесс того же UID может вызвать внешний вход», при сохранении всех обычных разрешений Cowork?** Рекомендация — принять после T2; более строгая идентификация приложения требует расширения архитектуры.
2. **Подтверждаем ли сохранение команды и её заголовка в обычной истории Cowork при полном запрете текста в технических журналах и статистике?** Рекомендация — да, как следует из требования показывать команду в чате/задачах.
3. **Кто закрепляется владельцем канонического контракта со стороны Cowork и когда доступно окно живой приёмки KDE/Fly?** До этого можно завершить реализацию и изолированные тесты; рабочий сеанс и службы не затрагиваются.
