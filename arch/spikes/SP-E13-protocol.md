## 1. Общие правила прогона

### 1.1 Правовые границы (из `legal-meetings.md` M1–M12, решения 24–26.09)

1. **Записываются только тестовые звонки владельца** — с самим собой (телефон в другой комнате), с коллегой, который знает о записи
   и согласен, или **синтетический звук** (корпус §5.3). Настоящие рабочие встречи в спайках не записываются.
2. **Записи CustDev из Astra Cowork не используются** (чужие ПДн): ни для SP4, ни для калибровки порога.
3. Звук спайков живёт только в `<ROOT>/spikes/e13/out/` на ноутбуке и **не уходит на VPS** (remote-hands переносит только `report.md`
   ≤ 4 МиБ); после анализа звук удаляется (`run.sh clean`), остаются JSON-метрики и `pw-dump`-снимки (без звука).
4. Никакой автоматической записи: каждый захват стартует явной командой/подсказкой на экране владельца, с отметкой в `markers.jsonl`.
5. `pw-dump`, `pactl list` — чтение метаданных графа (имена процессов, свойства потоков), **без звука**; тем не менее по HEARTBEAT 12.10
   они требуют отдельного «ок» владельца — в протоколе каждый шаг помечен: 📄 (только метаданные) или 🎙 (открывает звук).
6. **(T1 §4, MJ-7) Сырые свойства потоков — не в репозиторий.** `media.name` (у Firefox — заголовок вкладки), названия окон, имена файлов и прочие
   строки из `pw-dump`/`pactl` остаются в локальном файле на ноутбуке (`out/raw/`, 0600) и в отчёт/фикстуры попадают только **классами и схемами
   полей** (`pwgraph.py --redact` по умолчанию: значения `media.name`, `node.name` потоков, `window.*`, пути заменяются на `<redacted:поле>`;
   остаются `application.process.binary`, `application.name`, `media.class`, `pipewire.sec.*`, состояния). Что увидено сырым — смотрит Юрка руками (T1 §9.2).
7. **Разрешение владельца 12.10** (`decisions/log.md`): заходы 1–2 разрешены — чтение графа, виртуальный захват без присмотра, тестовые звонки
   DION и Телемост, BT-гарнитура, колонки, установка SaluteJazz его руками. Разрешение **не отменяет** §1.4: без `module-echo-cancel`, без смены
   умолчаний звука, 0.1.2 не трогать. Часовой звонок снят; вместо него калибровочный блок ≈ 5 мин (заход 2, блок F).

## 3. SP2 — эхо

### 3.1 Вопрос и решения

**Вопрос.** Без гарнитуры голоса собеседников звучат из колонок и попадают в микрофонную дорожку (R-A1, Р18-3). Сколько именно —
и достаточно ли **пост-обработки на наших двух дорожках** (гейт по нормированной кросс-корреляции микрофона с дорожкой собеседников
в окне ±400 мс), чтобы реплики собеседников не попадали в расшифровку как «Я» и не дублировались; или нужны системное
`module-echo-cancel` (меняет граф звука — запрещено в спайке без отдельного разрешения) либо требование «только гарнитура».
**Решения:** D7 (стратегия), D8 (BT HFP — заметка в документе администратора). Побочно: подсказка в карточке старта (F18.4 (л)) — оставить или усилить. **Граница T1 (§4.2 п. 2, BL-1):** ни один вариант не открывает микрофон до нажатия «Начать запись» — «замер уровня для калибровки эха» тоже захват; поэтому гейт работает только по двум уже записанным дорожкам, без предварительной калибровки, и это проверяется конструкцией `sp2_analyze.py` (чисто офлайн по файлам).

### 3.2 Процедура (блок B захода 2, после SP3c)

Собеседник в SP2 — **не DION**, а `pw-play corpus/sp2_far.wav` (узел `Stream/Output/Audio`, тот же механизм захвата, что в SP1-E2):
акустический путь «sink → колонки → микрофон» одинаков, а текст собеседника **известен** (синтетический корпус §5.3), поэтому дубли
считаются точно, без ручной разметки.

| Шаг | Скрипт | Владелец | Время |
|---|---|---|---|
| B0 📄 | снимок умолчаний; проверка, что вывод — встроенные колонки (не гарнитура), громкость в журнале (без изменения) | снимает гарнитуру, ставит привычную громкость (≈ 50 %), садится как на обычном звонке | 0,5 мин |

Анализ (`sp2_analyze.py`, Codex-job или VPS по JSON; звук остаётся на ноутбуке — значит **анализ со звуком идёт на ноутбуке** в Codex-job
без `--write` → только чтение `out/SP2`, результат печатается в `report.md`; либо `run.sh analyze SP2` владельцем):
1. VAD микрофонной дорожки — `astra_voice.worker.vad` (Silero из репо, `data/vad/silero_vad.onnx`).
2. На каждом речевом отрезке микрофона: NCC с дорожкой собеседников, лаги 0…400 мс (FFT), окно 1 с; `max_ncc` → отрезок помечен «эхо»,

4. Контроль B3 — то же без колонок.

### 4.4 Правило детектора в спайке (`detector_rule.py`, то же, что пойдёт в продукт)

```
вход: события/снимки {t, узлы: [{serial, dir: in|out, binary, pid, app_name, media_name, state, monitor_capture: bool, target}]}
apps.json: [{id:"dion", title:"DION", binary:["dion"]},
            {id:"browser", title:"браузер", binary:["chromium","chromium-browser","yandex_browser","firefox","firefox-bin","firefox-esr"], class:"browser"}]
exclude: app_name ∈ {"astra-voice","astra-voice-spike*"} ∪ pid ∈ {свои}; binary ∈ {"pw-cat","pw-record","pw-play","parec","parecord","pacat","handy","speech-dispatcher"};
         узлы с monitor_capture=true (захват монитора — не микрофон)
для каждого app: in_active = ∃ узел dir=in того же binary (не монитор); out_active = ∃ узел dir=out того же binary
   оба истинны непрерывно ≥ T_on (5 с) → call_started(app, t0)      (t0 — начало окна, не момент срабатывания)
   после старта: in_active ∧ out_active ложно непрерывно ≥ T_off (10 с) → call_ended
   mute: узел in остаётся (state idle/suspended) → звонок продолжается; узел in исчез → отсчёт T_off
выход: events.jsonl {t, event, app, title, evidence:[serial…]}
```
**Ревизия 2.1 — схема идентификации клиента (находка code-reviewer B1, доказательство на стенде VPS `spikes/e13/out/tmp/captures/05_monitor_capture_live.json`: клиент 61 `pactl`, `client.api=pipewire-pulse`, `pipewire.sec.pid` = pid процесса `pipewire` (pulse-сервер), декларированный `application.process.id` — настоящий pid `pactl`).** Серверные `pipewire.sec.*` на объекте клиента принадлежат **тому, кто открыл сокет `pipewire-0`**: для native-клиентов это сам процесс, для pulse-клиентов — `pipewire-pulse`, который держит отдельное core-соединение на каждого pulse-клиента. В `libpipewire-module-protocol-pulse.so` 1.6.2 нет ключа с кредами pulse-peer (есть только `pulse.server.address/peer/type` и предупреждение «no peercred»): pipewire-pulse читает `SO_PEERCRED`, но наружу не отдаёт (вариант (б) — проверить ещё раз на стенде `pactl list clients`/`pw-dump` и в `src/modules/module-protocol-pulse/server.c`; ожидание — **нет**). Все значимые программы — pulse-клиенты (Chromium/Electron через libpulse, Firefox через cubeb-pulse, Telegram через OpenAL→pulse, наш `PulseStreamSource`), поэтому правило «ключ = `sec.pid` → exe» давало бы `pipewire` для всех и 100 % пропусков. **Решение — вариант (г):**

| Класс клиента | Как узнаём | Ключ группировки | `key_source` | Остаток |
|---|---|---|---|---|
| native PipeWire (`client.api` отсутствует или ≠ `pipewire-pulse`: `pw-cat`/`pw-record`, WirePlumber, наши подпроцессы) | `pipewire.sec.pid` с объекта клиента (сервер, по `SO_PEERCRED`) | `readlink /proc/<sec.pid>/exe` | `sec` | нет (не спуфится тем же uid) |
| pulse-клиент на PipeWire (`client.api=pipewire-pulse`) — **все ВКС и браузеры** | декларированный `application.process.id` (из proplist libpulse) **с проверкой**: (1) процесс жив и `/proc/<pid>/status` Uid = наш uid; (2) `readlink /proc/<pid>/exe` читается; (3) `basename(exe)` = декларированному `application.process.binary` (libpulse ставит его из `/proc/self/exe`); (4) **`ss -xp`**: у pid есть unix-stream-соединение, peer которого — accepted-сокет процесса pulse-сервера (`pipewire-pulse`/`pulseaudio`, владелец сокета `pulse/native`); (5) **счётчик**: число pulse-клиентов, заявивших pid P, ≤ числа соединений P к `pulse/native` — иначе `identity_mismatch` | `basename(exe)` по декларированному pid | `declared-verified` ((1)–(4)), `declared` (нет `ss`/`/proc` недоступен — MAC), `mismatch` (5) | спуф тем же uid с pid живого DION проходит (1)–(4); ловится только (5) и только как флаг — **П30 распространяется на PipeWire** |
| pulse-клиент на PulseAudio 16.1 (нет `pw-dump`, `pactl list clients`) | то же, что строкой выше — `ss -xp` работает и против `pulseaudio` | то же | `declared-verified` / `declared` | П30 |
| свои потоки | **индекс собственного клиента** `pa_context_get_index()` (= id объекта клиента у pipewire-pulse и у PulseAudio) для контекстов GUI/воркера; дочерний `pw-record` — native, по `sec.pid` = pid ребёнка; резерв — декларированный pid ∈ свои pid | — | `own` | не спуфится (индекс выдаёт сервер) |

Цена (4)–(5): один вызов `ss -xp` (iproute2, фиксированный argv, `LC_ALL=C`, таймаут 2 с, ≈ 20–60 мс; читает `/proc/<pid>/fd` только своих процессов — без прав) **на решение детектора** (появился кандидат на звонок / выбор цели захвата), не на каждое событие; на ALSE с мандатным контролем процессы другого уровня невидимы → `declared`, без отказа. `ss` отсутствует → `declared`. Группировка — по бинарю (`basename(exe)`): у Chromium/Electron звук держит utility-процесс с pid ≠ pid окна, но exe тот же. `application.process.binary` без проверки — только на уровне «подсказки» в журнале; `media.name` не читается и не пишется (MJ-7). Для продукта это значит: канал D9 (libpulse-подписка + `get_client_info`/`get_sink_input_info`) даёт декларированные поля на обоих серверах, `pw-dump` нужен только для `client.api` и `sec.pid` native-клиентов (и его можно не использовать вовсе, считая всех клиентов pulse-клиентами, кроме наших подпроцессов).

**Старый текст (ревизия 2, неверная предпосылка):** группировка по серверному `sec.pid` для всех клиентов —
PID ≠ PID окна; это проверяется в A3 (S3.1 фиксирует `application.process.id` узлов DION против PID главного процесса `dion`).

`sp3_analyze.py` прогоняет правило по журналу обоих каналов и сверяет с `markers.jsonl`: задержки, ложные/пропущенные, таблица свойств
каждого бинаря (для `apps.json` и фикстур), расхождения каналов.

### 5.4 Что считаем (`der.py`)

DER = (пропуск + ложная речь + путаница) / общая речь, разметка кадрами 10 мс, сопоставление дикторов гипотезы и эталона —
венгерский алгоритм (scipy, если есть, иначе перебор при ≤ 8 дикторов), коллар 250 мс; плюс ошибка числа дикторов `|found − true|`
и «чистота» (доля кадров доминирующего эталонного диктора в каждом кластере). Для сравнения двух гипотез (B1 vs A1) — тот же DER, где эталон = A1.

## 8. Вопрос по US-13.12 — замки «Задано администратором» для `meeting_*` в v1.1 или v1.2

> **Решение владельца 12.10 (через Юрку): ждать v1.2 (вариант B).** В v1.1 строки «Встреч», заданные политикой, показываются **серыми (неактивными)** с
> **пояснением вверху раздела** («часть настроек задана администратором…»), без пер-строчной подписи «Задано администратором» и без компонента замка; значения
> применяются fail-closed, как в таблице F18.11. Следствие для PM: критерии US-13.1/13.6/13.11/13.12 и S26-A4…A6 переписать под «строка неактивна +
> общее пояснение» (ревизия 19 PRD вместе с правками T1 §9.1). Анализ ниже сохранён как обоснование вариантов.

**Факты.**
- Механизм уже есть в `core/policy.py`: `Policy.locked_keys` = все ключи из `policy.conf` + явный `locked=`; `Policy.is_locked(key)`;
  `effective()` накладывает значения; ключи вне `Settings` уходят в `extra` строками (валидация — при использовании, по ключу, fail-closed —
  как требует таблица F18.11). Значит **принуждение** (`meeting_record=off` → функции нет) работает без всяких замков: это уже «политика».
- Замок — это **UI-честность** (US-9.4: «сотрудник видел, что это политика, а не баг»): заблокированная строка + подпись. Общая история US-9.4
  (все разделы) решением 28.09 ушла в v1.2 (PRD р18: «замки строк политики — v1.2»).
- Но acceptance самих историй E13 уже требует подписи у строк «Встреч»: US-13.1 «кнопка включения заблокирована с „Запись встреч отключена
  администратором“», US-13.6 «строка заблокирована», US-13.11 «строка заблокирована на 30», US-13.12 «годные значения блокируют строки
  с „Задано администратором“», S26-A4…A6. Без какого-то замка эти истории не принимаются по собственным критериям.

**Варианты для решения владельца.**

| | A. Минимальные замки в v1.1 — только раздел «Встречи» (рекомендация) | B. Ждать v1.2 (US-9.4 целиком) |
|---|---|---|
| Что делается | один QML-компонент `PolicyLockedRow` (disabled + подпись «Задано администратором» / текст ошибки политики) + свойство моста `policyLocked(key)` на базе `Policy.is_locked`; применяется к 5 строкам «Встреч» (включение/детектор ← `meeting_record`, разделение ← `meeting_diarization`, адрес ИИ ← `meeting_ai_endpoint`, хранение звука ← `meeting_audio_retention_days`, текст уведомления ← `meeting_notice_text`); `meeting_ai_allow_external` без строки | значения политики применяются (fail-closed), строки «Встреч» показывают значение, но **не заблокированы**; критерии US-13.1/13.6/13.11/13.12 и S26-A4…A6 переписываются PM («строка показывает значение политики, редактирование не сохраняется») |
| Цена | **≈ 0,5 дн.** (компонент + 5 привязок + тесты моста/QML; раздел «Встречи» всё равно пишется с нуля в v1.1 — строки сразу делаются lock-aware, ретрофит в v1.2 не нужен) | 0 дн. в v1.1; +0,25 дн. PM на правку критериев; в v1.2 US-9.4 делает всё разом, включая «Встречи» |
| Риск | две реализации замков (v1.1 «Встречи», v1.2 остальное) — снимается тем, что US-9.4 в v1.2 **переиспользует** `PolicyLockedRow`, а не пишет свой | UX-ловушка в корпоративном контуре: тумблер «Предлагать запись» при `meeting_record=manual` выглядит рабочим, но «не включается» — ровно то, что US-9.4 называет «похоже на баг»; документ администратора (US-13.13) вынужден описывать это как известное ограничение |
| Право (M9) | политика есть, принуждение есть — замок к правовому условию не относится ни в A, ни в B | то же |
| Рекомендация | **A**: 0,5 дн. против переписывания критериев четырёх историй и заведомо странного UI в единственном разделе, который корпоративный админ будет настраивать первым | — |

Открытое для архитекторов (не для владельца): где живёт `policyLocked(key)` — в `SettingsBridge` (как `offline`) или общий `PolicyModel`; это решается в двойном архитекторе E13.
