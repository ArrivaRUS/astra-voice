## 1. Суть контракта (простым языком)

Astra Voice распознаёт фразу, произнесённую по клавише «Команда помощнику», и передаёт её Astra Cowork
**одной строкой, один раз, только на этом компьютере**. Cowork отвечает сразу — принял или нет и почему.
Voice ждёт ответ не дольше 300 мс. Если помощник не принял команду или ответа нет — текст остаётся у пользователя
(в буфере обмена и в памяти Voice), а помощник команду не выполняет. Voice текст не толкует и не исполняет;
дальнейшая судьба команды (задача, ответ, история) — зона Cowork.

Что гарантируется:
- **Локально и без сети.** Передача — по шине сообщений сеанса пользователя; сетевых соединений нет.
- **Только свой пользователь.** Cowork принимает команду только от процесса того же пользователя.
- **Один раз.** Voice отправляет команду ровно один раз, без автоповторов; Cowork не создаёт вторую задачу по повтору.
- **Текст не попадает в журналы** ни у Voice, ни у Cowork — только длина, тайминги, коды исходов.
- **Ответ до работы.** Cowork сначала отвечает, потом делает: решение о приёме — за миллисекунды, выполнение — отдельно.
- **Честные исходы.** Voice различает «не отправлено / отказано» и «отправлено, но ответа нет»: во втором случае
  команда могла быть принята, и Voice так и говорит.

Что не гарантируется (ограничения v1.0): квитанций о выполнении нет; приём в память ≠ сохранение (сбой Cowork сразу
после «принято» может потерять команду — об этом сообщает сам Cowork); один графический сеанс на пользователя;
не более трёх незавершённых голосовых команд и не чаще одной новой за полсекунды.

отправил запрос, но достоверного ответа нет.

## 3. Транспорт и адрес

### 3.1 Проверка адреса шины (обе стороны)
- Переменная `DBUS_SESSION_BUS_ADDRESS` задана → допустим только адрес с транспортом `unix:` (`unix:path=…`,
  `unix:abstract=…`); `tcp:`, `autolaunch:`, `unixexec:` и прочие — отказ (клиент: исход `no_bus`; сервер: имя не
  регистрируется, в журнал код `bus_address_unsupported`).
- Переменная не задана → если `$XDG_RUNTIME_DIR/bus` существует и это сокет — использовать `unix:path=$XDG_RUNTIME_DIR/bus`;
  иначе состояние **`address_not_passed`** (клиент: исход `no_bus`). Оно отличается от «шины нет»: чинится окружением
  запуска (передачей адреса юниту/сеансу), а не транспортом — эксперимент 2 приёмки K5.
- Клиент подключается **своим** соединением: `QDBusConnection.connectToBus(<проверенный адрес>, "astra-voice-cowork")`
  в рабочем потоке (образец — `ui/tray.py` Voice); `QDBusInterface` с интроспекцией не используется.
- Сервер регистрируется на сеансовой шине демона (`QDBusConnection.sessionBus()`); `scripts/doctor.py` Cowork сверяет,
  что адрес у юнита демона и у графического сеанса — один и тот же (только чтение `DBUS_SESSION_BUS_ADDRESS`).

### 3.2 Регистрация на сервере
1. Зарегистрировать **объект** `/ru/astralinux/Cowork` с адаптором интерфейса (§5.1) — раньше имени, чтобы первый
   вызов не получил `UnknownObject`.
2. Зарегистрировать **имя** `ru.astralinux.Cowork` после завершения инициализации демона (`CoworkDaemon.__init__`).
   Отказ (имя занято другим экземпляром) — код `dbus_name_taken` в журнал, демон работает дальше без приёма голосовых
   команд; `doctor.py` показывает это.
3. Снять имя в `_quit` **до** остановки оркестратора; между `begin_shutdown` и снятием имени `Submit` отвечает
   `busy/shutting_down`.

Что видит клиент по уровням доступности (§8.1): L0 «установлен» — статически по файлам; L1 «запущен» — у имени есть
владелец; L2 «готов» — сам ответ `Submit`.

## 4. Интроспекция

Канон — файл `ru.astralinux.Cowork.Command1.xml` (рядом с этим документом). Содержательная часть:

```xml
<node name="/ru/astralinux/Cowork">
  <interface name="ru.astralinux.Cowork.Command1">
    <method name="Status">
      <arg name="info" type="a{sv}" direction="out"/>
    </method>
    <method name="Submit">
      <arg name="text" type="s" direction="in"/>
      <arg name="options" type="a{sv}" direction="in"/>
      <arg name="reply" type="a{sv}" direction="out"/>
    </method>
  </interface>
</node>
```

Правила сравнения в контрактных тестах (вектора I-01…I-05):
- сравнивается только интерфейс `ru.astralinux.Cowork.Command1`, нормализованно: имя метода → упорядоченный список
  `(direction, type)`; имена аргументов — справочные (Qt не экспортирует имя выходного аргумента, а имена входных
  берёт из сигнатуры Python-функции);
- стандартные интерфейсы (`org.freedesktop.DBus.Introspectable`, `Peer`, `Properties`) в XML не перечислены — их
  добавляет Qt;
- служебный аргумент `QDBusMessage` (§5.1) в интроспекции не виден: у `Submit` ровно два входных аргумента;
- сигналов и свойств у интерфейса нет и быть не должно (`ExportAdaptors` без `ExportAllSignals/Slots/Contents`).

## 5. Маршаллинг (PyQt6 на сервере, PyQt5 на клиенте)

### 5.1 Сервер (PyQt6 6.7.1)
- `class Command1Adaptor(QDBusAbstractAdaptor)` с `pyqtClassInfo("D-Bus Interface", "ru.astralinux.Cowork.Command1")`;
  родитель — `QObject` сервиса; регистрация `bus.registerObject("/ru/astralinux/Cowork", obj, QDBusConnection.RegisterOption.ExportAdaptors)`.
- Слоты: `@pyqtSlot(result="QVariantMap") def Status(self)` и
  `@pyqtSlot(str, "QVariantMap", QDBusMessage, result="QVariantMap") def Submit(self, text, options, message)`.
  Словарь — `QVariantMap` (`a{sv}`), **не** `QDBusVariant` целиком; значения словаря приходят в Python как обычные
  значения (`int`, `str`, `bool`, `float`), тип на проводе виден только через `QDBusArgument` при необходимости.
- В PyQt6 6.7.1 нет `QDBusContext` и `QDBusVirtualObject` (проверено 24.09): отправитель берётся из **служебного
  последнего аргумента `QDBusMessage`** — `message.service()` (уникальное имя соединения `:1.NNN`).
- **Отложенный ответ** (нужен для асинхронной проверки UID, §7 шаг 2): в слоте `message.setDelayedReply(True)`,
  возврат слота игнорируется; ответ позже — `connection.send(message.createReply([reply_dict]))`. Ответ сразу (шаг 1
  и `Status`) — обычный `return dict`. Вложенный event loop (`QEventLoop.exec`) в слоте **запрещён**.
- Целые: сервер принимает целочисленные ключи в любой из сигнатур **`i`, `u`, `x`, `t`** (диапазон — по сигнатуре);
  `b` (bool), `d` (double), `s` (строка) на месте целого — `refused/invalid_options`. Python-`int` с клиента PyQt5
  маршалится как `i`, `u` или `x` в зависимости от величины — поэтому сервер обязан быть терпим к сигнатуре.
- Ответ всегда `a{sv}`; сервер **никогда** не отвечает D-Bus-ошибкой сам. D-Bus-ошибки клиенту приходят только от
  шины или Qt (нет владельца, неизвестный метод/интерфейс/объект, неверная сигнатура).

### 5.2 Клиент (PyQt5 5.15.9)
- `msg = QDBusMessage.createMethodCall("ru.astralinux.Cowork", "/ru/astralinux/Cowork", "ru.astralinux.Cowork.Command1", "Submit")`;
  `msg.setAutoStartService(False)`; `msg.setArguments([text, options])` — `dict` маршалится как `a{sv}`.
- Вызов **только асинхронный**: `connection.callWithCallback(msg, receiver, ok_slot, err_slot, timeout_ms)` с
  `ok_slot(QDBusMessage)` и `err_slot(QDBusError, QDBusMessage)` (образец `_BusRequest` в `ui/tray.py`, но **без**
  превращения любой ошибки в `None`: сохраняются `QDBusError.name()`, `.type()` и признак «отправлено»).
- `timeout_ms` = остаток бюджета (§8.3). Синхронные `call(..., QDBus.Block)` — только в измерительных пробниках.
- Разбор ответа: `message.type() == ReplyMessage`, `message.arguments()[0]` — `dict`; если значение пришло как
  `QDBusVariant` — взять `.variant()`. Всё прочее — `unknown/bad_reply` (§8.4).
- Соединение, подписки (`NameOwnerChanged`, login1) и получатели сигналов живут в рабочем потоке, как в `ui/tray.py`;
  результат в GUI — очередью сигналов.

## 6. `Submit(text, options) → reply` и `Status() → info`

### 6.1 `text` (s)
Распознанная фраза целиком, одной строкой. Voice **нормализует** перед отправкой: `paste.normalize` (CR/LF → пробел,
C0/C1 удалены) + U+2028/U+2029/U+0085 → пробел + серии пробелов → один + `strip`. Cowork **проверяет и не исправляет**
(отказ `refused/invalid_text`, текст в задачу уходит как получен):
- длина **1…4000 кодовых точек Unicode** (`len(str)`; не байты и не единицы UTF-16 — вектор T-17);
- запрещены U+0000–U+001F, U+007F–U+009F (в т. ч. U+0085), U+2028, U+2029;
- строка, пустая после `strip`, — недопустима (T-03, T-20).
U+0000 в строках D-Bus невозможен: сообщение не уйдёт с клиента.

### 6.2 `options` (a{sv})

| Ключ | Тип на проводе | Обяз. | Правило |
|---|---|---|---|
| `source` | `s` | да | ровно `"astra-voice"` (закрытый список версии 1); иная строка → `refused/bad_source`; не строка → `invalid_options` |
| `contract` | целое `i/u/x/t` | да | `1`; `> 1` → `refused/unsupported_contract` (в ответе `contract` = максимум сервера); `< 1` или не целое → `invalid_options` |
| `request_id` | `s` | да | `uuid4().hex`: ровно 32 символа `[0-9a-f]`; иначе `invalid_options`; ключ идемпотентности (§7 шаг 3) |
| `sent_mono_ms` | целое `i/u/x/t` | да | `time.monotonic_ns() // 1_000_000` на клиенте в момент начала доставки; `≥ 0` |
| `deadline_mono_ms` | целое `i/u/x/t` | да | `sent_mono_ms + 300`; сервер требует `deadline ≥ sent` и `deadline − sent ≤ 5000`, иначе `invalid_options` |
| `mode` | `s` | нет | по умолчанию `"submit"` (задача сразу). `"draft"` — зарезервировано (форма ввода с предзаполненным текстом), сервер отвечает `refused/bad_mode`, пока не объявит `draft` в `Status.modes`; любая другая строка → `bad_mode`; не строка → `invalid_options` |
| `client_version` | `s` | нет | версия Voice, только для журнала; в журнал попадает лишь при соответствии `^[0-9A-Za-z.+~_:-]{1,64}$`, иначе игнорируется без отказа |

Незнакомые ключи сервер игнорирует (O-03) — добавление ключей не меняет версию. Часы: обе стороны — системный
`CLOCK_MONOTONIC` (Python `time.monotonic_ns()`), сравним между процессами одной машины; **не идёт во время сна** —
поэтому сон закрывается отдельно (§9).

### 6.3 `reply` (a{sv})

| Ключ | Тип | Когда | Значение |
|---|---|---|---|
| `status` | `s` | всегда | `accepted` · `busy` · `refused` · `expired` — закрытый список; клиент **не принимает** незнакомых статусов (→ `unknown/bad_reply`) |
| `reason` | `s` | при `status ≠ accepted` | закрытый список по статусу (ниже); при `accepted` — отсутствует или `""` (клиент трактует одинаково); незнакомую причину клиент принимает как «неизвестная причина этого статуса» |
| `request_id` | `s` | если из `options` удалось прочитать строку | эхо; при `accepted` клиент сверяет с отправленным (несовпадение → `unknown/bad_reply`) |
| `contract` | целое | всегда | максимальная версия контракта, которую понимает сервер (= `1`) |
| `duplicate` | `b` | только при идемпотентном повторе | `true` — тот же `request_id` уже принят, новой задачи нет (§7 шаг 3); иначе ключа нет |

Закрытые списки `reason`:
- `busy`: `shutting_down` · `rate_limited` · `locked` · `suspending` · `queue_full`;
- `refused`: `invalid_options` · `invalid_text` · `unsupported_contract` · `bad_source` · `bad_mode` ·
  `unverified_sender` · `request_conflict` · `policy_disabled` · `not_ready`;
- `expired`: `deadline` · `suspended`.
Никаких текстов исключений, сообщений об ошибках и тем более фрагментов команды в ответе нет.

### 6.4 `Status() → info`

| Ключ | Тип | Значение |
|---|---|---|
| `contract` | целое | `1` |
| `version` | `s` | версия Cowork (строка пакета) |
| `state` | `s` | `ready` · `not_ready` · `disabled` · `locked` · `suspending` · `shutting_down`; старшинство: `shutting_down` > `suspending` > `locked` (в т. ч. «неизвестно») > `not_ready` > `disabled` > `ready` |
| `modes` | `as` | поддерживаемые режимы, в v1.0 `["submit"]` |

`Status` — без побочных эффектов (не трогает окно частоты и дедуп), без проверки UID, ответ немедленно (≤ 50 мс при
свободном цикле). У клиента используется **только** кнопкой «Проверить снова» и строкой состояния в «Общих»; в цикле
доставки не вызывается — один обмен на команду.

## 7. Порядок допуска `Submit` на сервере (обязателен; синтез §1а)

Один запрос проходит шаги строго по порядку; первый сработавший даёт ответ.

1. **Формат** (синхронно, ≤ 5 мс, без обращений к шине), внутри — в таком порядке:
   типы и диапазоны `options` (§6.2) → `refused/invalid_options`; правила текста (§6.1) → `refused/invalid_text`;
   `contract > 1` → `refused/unsupported_contract`; `source` → `refused/bad_source`; `mode` → `refused/bad_mode`.
   Ответ — сразу (вектора O-42…O-45 — старшинство).
2. **Отправитель.** `org.freedesktop.DBus.GetConnectionUnixUser(message.service())` асинхронно (`callWithCallback`),
   срок `clamp(deadline − now − 20, 20, 100)` мс. `uid ≠ os.getuid()`, ошибка или таймаут → `refused/unverified_sender`.
   Ответ на `Submit` — отложенный (§5.1). Проверка выполняется до дедупа и допуска (A-25).
3. **Поиск принятого `request_id`.** Запись дедупа хранит `request_id`, отпечаток `sha256(text_utf8)` и `mode`.
   Тот же ID, тот же отпечаток и `mode` → `accepted` повторно с `duplicate=true` — идемпотентно: без новой задачи,
   без расхода окна частоты, **раньше** проверки deadline (A-04, A-05). Тот же ID, иной отпечаток или `mode` →
   `refused/request_conflict` (A-06, A-07). Запись живёт до терминального исхода задачи + 60 с, ёмкость 64 (LRU) —
   вспомогательная защита; гарантию «ровно один раз» даёт клиент отсутствием повторов.
4. **Допуск нового ID**, по порядку (первый сработавший):
   `now > deadline_mono_ms` → `expired/deadline`;
   `sent_mono_ms ≤ sleep_start_mono` (отправлен до последнего сна) → `expired/suspended`;
   демон в `begin_shutdown` → `busy/shutting_down`;
   между `PrepareForSleep(true)` и `(false)` → `busy/suspending`;
   сеанс заблокирован **или состояние неизвестно** → `busy/locked`;
   предыдущий принятый новый ID < 500 мс назад → `busy/rate_limited`;
   незавершённых голосовых допусков ≥ 3 → `busy/queue_full`;
   оркестратора нет → `refused/not_ready`;
   приём выключен настройкой/политикой Cowork → `refused/policy_disabled`.
5. **Резервирование и ответ.** Атомарно: запись дедупа + место среди незавершённых + отметка окна частоты → ответ
   `accepted` → работа `QTimer.singleShot(0, …)` с родителем-сервисом. `accepted` = **приём в память**; долговечность
   до записи задачи не обещается. В работе:
   - `submit` → `TaskOrchestrator.submit(text, context={"source": "astra_voice", "hotkey": "astra_voice"})`;
     `request_id` в контекст **не** кладётся — живёт только в памяти сервиса (карта `request_id → task_id`, отдельно от
     `attention_request_id`);
   - `draft` (когда объявлен в `modes`) → `form_router.open_form(FormRequest(source=FormSource.ASTRA_VOICE, prefill=text))`;
   - сервис закрыт к моменту callback → место освобождено, задачи нет (A-31);
   - исключение → место освобождено, уведомление Cowork «Не удалось принять голосовую команду», в журнале тип исключения
     без текста (A-26); ошибка хранения **после** начала побочных эффектов — сбой после приёма (сообщает Cowork), не
     «доказанный отказ без эффекта»;
   - терминальный исход задачи (`task_id` из карты) освобождает место; запись дедупа живёт ещё 60 с;
   - команда, принятая до блокировки/сна, исполняется; новых допусков в этих состояниях нет (A-27).

Что делает Cowork с принятой командой (продукт, не транспорт): задача создаётся как введённая в окно помощника,
`FASTPATH_SOURCES` включает `astra_voice` (локальные умения ОС — «Открой папку загрузки» — не уходят в облако), окно
**не** открывается (`_AUTOOPEN_SOURCES` без изменений), ответ — штатным уведомлением Cowork. **Новая задача ≠ новый
диалог:** локальная команда по вердикту роутера — в общей ветке «Операционные команды», просьба об откате — в диалоге
предыдущего действия, облачная — в новом диалоге (как у виджета); В-2 может уточнить (§15). В `TaskOrchestrator.submit`
порядок: проверка входа/допуска → побочные эффекты; для невалидной команды — ни отмены чужой задачи, ни диалога, ни записи.

## 8. Правила клиента Astra Voice

### 8.1 Доступность (три уровня)
- **L0 «установлен»** — статически, без запуска служб: хотя бы один артефакт Cowork (исполняемый файл в `PATH`,
  ярлык приложения, файл пользовательского юнита, файл активации на шине — когда появится). Нет → второй режим не
  регистрируется, клавиша не захватывается (C-30). Установлен, но нет каталога настроек Cowork → «найден · не запущен».
- **L1 «запущен»** — `NameHasOwner("ru.astralinux.Cowork")` один раз при старте и подписка на `NameOwnerChanged`
  (без опроса); кеш состояния. Обновление владельца **до** отправки разрешает доставку новому владельцу (C-27).
- **L2 «готов»** — сам `Submit`. `Status()` — только для «Проверить снова» и строки в «Общих».

### 8.2 Гейты перед отправкой (порядок)
1. Адрес шины проверен (§3.1), соединение есть; иначе `undelivered/no_bus`, вызова нет.
2. У имени есть владелец (L1); иначе `undelivered/not_running`, вызова нет, предлагается «Запустить Astra Cowork».
3. Сеанс **не заблокирован и состояние известно** (§9); иначе `undelivered/locked` — вызова нет, **буфер не
   трогается, уведомления нет**, фраза только в памяти (C-22).
4. Сон не начался (§9); иначе `undelivered/suspended`.
5. Остаток бюджета > 0; иначе `undelivered/timeout`, вызова нет (C-25).

### 8.3 Один вызов и бюджет
- `sent_mono_ms` ставится в момент начала фазы доставки (сразу после распознавания и прохождения гейтов),
  `deadline_mono_ms = sent_mono_ms + 300`; таймаут `callWithCallback` = `deadline − now` в момент вызова (остаток после
  передачи в рабочий поток), не меньше 1 мс.
- **Ровно один вызов на команду.** Повторов нет ни при каком исходе (at-most-once обеспечивает клиент). Отмена в фазе
  доставки не действует: ушедший запрос доставляется.
- Ровно один терминальный callback: поздний ответ после таймаута, ответ после сна, ответ прежнего владельца
  отбрасываются по счётчику поколения (C-24, C-28).

### 8.4 Два класса исходов
`DeliveryOutcome{kind ∈ delivered | undelivered | unknown, reason, error_name}`; `reason` — закрытый список
`none | not_installed | no_bus | not_running | no_contract | busy | refused | expired | timeout | disconnected | bad_reply | locked | suspended | clipboard_failed`.

| Событие | kind | reason | Примечание |
|---|---|---|---|
| ответ `accepted` с нашим `request_id` | `delivered` | `none` | буфер не трогается |
| ответ `busy` / `refused` / `expired` (любая причина) | `undelivered` | `busy` / `refused` / `expired` | доказано: не принято |
| ответ с незнакомым `status`, без `status`, не `a{sv}`, чужой `request_id` | `unknown` | `bad_reply` | отправлено, ответ недостоверен |
| `org.freedesktop.DBus.Error.NoReply`, `.Timeout`, `.TimedOut` | `unknown` | `timeout` | в т. ч. смена владельца во время вызова (C-26) |
| `org.freedesktop.DBus.Error.Disconnected` после отправки | `unknown` | `disconnected` | до отправки → `undelivered/no_bus` |
| `.ServiceUnknown`, `.NameHasNoOwner` | `undelivered` | `not_running` | предлагать «Запустить Astra Cowork» |
| `.UnknownInterface`, `.UnknownMethod`, `.UnknownObject` | `undelivered` | `no_contract` | старый Cowork без контракта |
| `.InvalidArgs`, `.InvalidSignature`, любая другая ошибка-ответ | `undelivered` | `refused` | имя ошибки — в журнал (без текста) |
| гейты §8.2 | `undelivered` | `no_bus` / `not_running` / `locked` / `suspended` / `timeout` | вызова не было |

Правило: **ошибка-ответ, которую сформировала шина или Qt до исполнения слота, доказывает «не принято»; отсутствие
ответа, обрыв и повреждённый ответ — не доказывают** → `unknown`, без повтора.

### 8.5 Запасной путь и память
- `undelivered` или `unknown` → `publish_clipboard(text)` (как «только буфер»; прежнее содержимое не восстанавливается;
  подсказка менеджеру буфера «не хранить в истории» — история Klipper не пополняется, так задумано) → пилюля по
  результату публикации (§11). Последняя фраза остаётся в памяти Voice для повторного копирования из пилюли/трея
  независимо от службы уведомлений; сохранность в буфере ограничена временем жизни Voice и владением выделением.
- `locked` (гейт 3) — ничего не публикуется и не показывается; фраза в памяти до «Скопировать последнее».
- `PrepareForSleep(true)` — командная диктовка/доставка отменяется, поздние ответы отсекаются.

### 8.6 Статистика Voice (без текста)
Событие `dictation`: `result` += `delivered | undelivered | unknown`; поля `mode ∈ {text, command}`, `deliver_ms`,
`deliver_reason` (список §8.4; если публикация в буфер не удалась — `clipboard_failed` вместо причины доставки, как
самый тяжёлый для пользователя исход; C-29). `error_name` — только в журнал. Обновляются `_FIELDS`/`_CHOICES`/`summary()`;
произвольных строк в статистике нет.

### 8.7 Политика и клавиша (для полноты, вне провода)
`command_hotkey` в `policy.conf`: `off` → режим выключен; неразбираемо, совпадает с «Текст», неверный JSON-тип
настройки, файл политики невалиден (`PolicyStatus.INVALID`) → режим выключен (fail-closed), Win не подставляется.
Сравнение сочетаний двух ролей — по разобранным keycode + modifiers с алиасами (`ctrl`/`control`, `win`/`super`).
Захват клавиатуры на время записи — отдельный сторож на `RECORD_LIMIT_S + 5` со снятием на всех исходах.

## 9. Блокировка сеанса и сон (обе стороны)

Общий источник — `org.freedesktop.login1` на **системной** шине, только чтение, асинхронно (`callWithCallback`,
подписки на сигналы), без `loginctl` и без опроса:
- блокировка: свойство `LockedHint` объекта своего сеанса (`Manager.GetSession($XDG_SESSION_ID)` либо объект
  `session/auto` — выбор за реализацией, проверяется в KDE и Fly на K5) + `PropertiesChanged`, сигналы `Lock`/`Unlock`;
  кеш `{locked, known}`; `known=false` (login1 недоступен, свойства нет, ошибка/таймаут) — **неизвестно = нет допуска**:
  Voice не отправляет (и не публикует), Cowork отвечает `busy/locked`;
- сон: сигнал `Manager.PrepareForSleep(b)`. Сервер: при `true` — `sleep_start_mono = monotonic_ms`, состояние
  `suspending` до `false`; запросы с `sent_mono_ms ≤ sleep_start_mono` → `expired/suspended` (часы MONOTONIC во сне
  стоят, deadline сам по себе сон не закрывает). Клиент: при `true` отмена командной диктовки/доставки; ответы после
  resume — `unknown/suspended`.
- Cowork: `core/session_state.py` заменяет опрос `loginctl` в `prompt_widget/monitor.py`; Voice: `platform/session_state.py`.
  Если во Fly login1 не ведёт сеансы — режим выключен по правилу «неизвестно = нет допуска»; запасной источник
  `org.freedesktop.ScreenSaver` на шине сеанса — решение по факту K5.
- Принятая до блокировки/сна команда исполняется; новых допусков нет.

## 10. Безопасность (вход для T1/T2 security-analyst)

- **Локально.** Шина сеанса — unix-сокет с аутентификацией EXTERNAL; сетевых соединений нет по построению
  (`tools/validate privacy` Voice расширяется кейсом «команда»; `tcpdump` 20 команд на K5: 0 SYN от Voice).
- **Тот же UID.** Сервер принимает `Submit` только от отправителя с UID демона (§7 шаг 2; недоказанный UID = отказ).
  Любой процесс того же пользователя вызвать приём **может** — как и сегодня может напечатать в виджет или обратиться к
  локальному шлюзу с токеном того же пользователя; новых прав метод не даёт (В-4). PID-проверка (`/proc/pid/exe`) не
  делается: не даёт защиты (тот же интерпретатор) и гоночна.
- **Лимиты.** Текст 1…4000 кодовых точек; ≤ 1 принятого нового `request_id` за 500 мс; ≤ 3 незавершённых голосовых
  допусков поверх пула задач; дедуп 64 записи / терминальный исход + 60 с; `deadline − sent ≤ 5000` мс; закрытые списки
  статусов/причин; ответ никогда не содержит текст.
- **Текст не попадает** в журналы (INFO **и** DEBUG), диагностику и `doctor`, статистику Voice, `argv`/окружение,
  публичные D-Bus-сигналы и ответы методов — на обеих сторонах. Допустимо в журнале: `request_id`, длина, тайминги,
  `status`/`reason`, имя D-Bus-ошибки, `client_version` по шаблону. Внутренние Qt-сигналы Cowork
  (`task_completed(task_id, reply_text)`), его БД истории и уведомления — продукт (В-4). Адаптор экспортирует только
  контракт (`ExportAdaptors`).
- **Предпосылка C0 (blocker, Cowork, v0.2):** до реализации C1 из журналов Cowork убираются все утечки текста запросов и
  ошибок — три `preview` (`daemon/service.py`, `hermes/client.py`, `ui/fullscreen/main_window.py`), заголовки диалогов,
  исключения на границах HTTP/SSE/decision, pydantic `ValidationError`, SQLAlchemy, `task_pool.py`, `service.py`
  (`error=str(e)`, `exc_info=True`); в `core/logging.py` — процессор structlog с чёрным списком приватных полей; проверка
  INFO и DEBUG контрольной фразой (фейковый Hermes возвращает фразу в заголовке/ответе/ошибках). Стоки вне пути `Submit`
  (`form_routing.py`, `cover_finder.py`, `prompt_widget_preview.py`) — отдельная гигиена после v0.2.
- **Никакого shell/exec по строке.** Текст идёт только в оркестратор тем же путём, что напечатанный; умения ОС исполняют
  фиксированные команды с параметрами.
- **Токен** локального шлюза Voice не читает и не хранит; активация сервера по шине не используется
  (`setAutoStartService(False)`); запуск Cowork — только явным действием пользователя.
- **Ослышанная команда** исполняется как напечатанная (подтверждения у заказчика выключены) — В-1; `source` в задаче
  позволяет Cowork применить к голосу свою политику без изменения контракта.
- Перехват системной клавиши Win, сторож захвата клавиатуры, evdev-хоткеи Cowork (Ctrl+C+C, правые Ctrl×2/Alt×2) —
  T2 по Voice, транспорта не касаются.

## 11. Отказы и тексты интерфейса (простым языком)

Состояния пилюли Voice в режиме команды: «Слушаю команду…» → «Распознаю…» → «Отправляю помощнику…» →
**«Передано помощнику»** (800 мс). Подсказка трея во время записи — «Слушаю команду». Вставки в активное окно нет ни при
каком исходе.

| Исход у Voice | Пилюля (3 с, клик — подробности) | Подробности («Что случилось») | Действия |
|---|---|---|---|
| не доставлено, текст скопирован | «Помощник недоступен — текст в буфере» | по причине, см. ниже | «Что случилось»; «Запустить Astra Cowork» — только если помощник не запущен; «Скопировать ещё раз» |
| не доставлено, скопировать не удалось | «Помощник недоступен — не удалось скопировать текст» | то же + «Текст сохранён в программе — нажмите «Скопировать ещё раз»» | «Скопировать ещё раз», «Что случилось» |
| неизвестно, принята ли команда | «Не удалось узнать, принята ли команда — текст в буфере» (или «…— не удалось скопировать текст») | «Помощник не ответил вовремя. Возможно, команда всё же принята — проверьте в Astra Cowork, прежде чем повторять» | «Скопировать ещё раз», «Что случилось» |
| экран заблокирован в момент доставки | не показывается | — | после разблокировки в трее доступно «Скопировать последнее» |
| компьютер уходит в сон | «Отменено» (при пробуждении ничего не всплывает) | — | «Скопировать последнее» в трее |

Тексты подробностей по причине:
- помощник не запущен → «Astra Cowork не запущен»;
- помощник без поддержки команд → «Помощник не поддерживает голосовые команды — обновите Astra Cowork»;
- занят (частота, очередь) → «Помощник сейчас занят. Попробуйте ещё раз через несколько секунд»;
- завершает работу → «Помощник завершает работу. Попробуйте ещё раз через несколько секунд»;
- экран заблокирован → «Экран заблокирован — команда не отправлена»;
- сон → «Компьютер уходил в сон — команда не отправлена»;
- приём выключен на стороне помощника → «Приём голосовых команд выключен в настройках Astra Cowork»;
- помощник не успел → «Помощник не успел принять команду. Попробуйте ещё раз»;
- прочие отказы → «Помощник отклонил команду» (код причины — в журнал, не на экран);
- нет связи с помощником (нет шины/адреса) → «Не удалось связаться с помощником на этом компьютере».

Строка «Команда помощнику» в «Общих» и на экране 3 мастера: «Astra Cowork найден · доступен» / «найден · не запущен» /
«Astra Cowork не установлен» / «Приём голосовых команд выключен в Astra Cowork» / «Помощник не поддерживает голосовые
команды — обновите Astra Cowork»; кнопка «Проверить снова». Текст про клавишу Win и «Выбрать другую» — по PRD F17.10.

Действие «Запустить Astra Cowork» предлагается **только** когда помощник не запущен; при прочих отказах — только
«Что случилось». Уведомление с действиями показывается через штатную службу уведомлений, но «Скопировать ещё раз» и
«Что случилось» доступны из самой пилюли и трея, даже если уведомления не работают.

Сторона Cowork: успешный приём виден как обычная задача (ответ — штатное уведомление помощника); сбой после приёма —
уведомление «Не удалось принять голосовую команду». Отдельный знак приёма (анимация) — В-3.

## 12. Версионирование

- Версия контракта = `1`: поле `contract` (в `options`, `reply`, `Status`) **и** суффикс имени интерфейса `Command1`.
- **Совместимые изменения** (без смены версии): новые ключи `a{sv}` в `options`/`reply`/`info`, новые значения
  `reason`, новые значения `modes`, новые значения `source`. Клиент игнорирует незнакомые ключи и незнакомые `reason`,
  но **не** незнакомые `status`; сервер игнорирует незнакомые ключи `options`.
- **Несовместимые** (новые/переименованные методы, иные сигнатуры, иная семантика `accepted`) → `Command2` на том же
  объекте; `Command1` живёт ещё один релиз Cowork.
- Матрица: Voice новый / Cowork без интерфейса → `UnknownInterface` → «обновите Astra Cowork»; `contract` клиента >
  сервера → `refused/unsupported_contract` (в ответе `contract` сервера — в журнал); Cowork новый / Voice старый →
  режима нет.
- Публикация: канон в Cowork `docs/contracts/` (три файла), зеркало в Voice; sha256 XML и JSON — в шапке этого документа;
  контрактные тесты: Cowork — интроспекция адаптора = XML (§4), Voice — сигнатуры клиента = XML; в обоих — sha256 зеркала
  (дрейф ловится на CI, не у заказчика). Журнал изменений — §17.

## 16. Уточнения, внесённые при фиксации K0 (сверх синтеза v2 — на подтверждение Юрке)

1. `deadline_mono_ms − sent_mono_ms ≤ 5000` → иначе `invalid_options` (защита от ошибочного клиента; Voice шлёт 300).
2. Срок проверки UID — `clamp(deadline − now − 20, 20, 100)` мс: нижняя граница 20 мс, чтобы повтор принятого ID после
   deadline всё же дошёл до дедупа и получил `accepted`, а не срезался до шага 3.
3. Ключ ответа `duplicate=true` при идемпотентном повторе (совместимое добавление; упрощает тесты S9-3 и приёмку).
4. Отпечаток дедупа включает `mode` наравне с текстом; расхождение любого → `request_conflict`.
5. `client_version` пишется в журнал только по шаблону `^[0-9A-Za-z.+~_:-]{1,64}$`, иначе игнорируется без отказа.
6. `Status.state` — закрытый список из шести значений со старшинством (§6.4); `busy` из плана #1 как состояние `Status`
   не используется (окно частоты 500 мс для строки настроек бессмысленно).
7. Клиент сверяет `request_id` в `accepted`-ответе с отправленным; несовпадение → `unknown/bad_reply`.
8. Порядок проверок внутри шага 1 зафиксирован явно: options → текст → версия → source → mode (вектора O-42…O-45).
9. Ошибки-ответы `InvalidArgs`/`InvalidSignature`/прочие → `undelivered/refused` (не `no_contract`): это не «старый
   Cowork», а несовпадение форм — имя ошибки в журнал.
10. `deliver_reason=clipboard_failed` замещает причину доставки при неудачной публикации в буфер (список синтеза сохранён,
    задано старшинство).
