# Безопасность Astra Voice

Документ описывает **ключи подписи, ротацию, отзыв и канал сообщений об уязвимостях**.
Он же закрывает требование ФСТЭК № 239 п. 29.3.3 «процедуры устранения уязвимостей».
Модель угроз — `docs/threat-model.md` (§4.2 — обоснование схемы ключей).

**Статус:** мастер M1 сгенерирован 26.09.2026 на рабочей машине заказчика, не офлайн
(отклонение от инструкции §4; закрытые части затем перенесены на носитель). Риск для
пилота v0.1 принят заказчиком письменно: [журнал решений](../decisions/log.md)
(запись от 26.09 «K-1 … риск принят») и [отчёт T2](security/T2-2026-09-26-master-key.md)
(K-1). До v1.0 (31.10.2026) преемник M2 будет сгенерирован офлайн, добавлен в
`data/keys/release.gpg` и `PINNED_FINGERPRINTS` рядом с M1; после v1.0 пин M1 снимается.
Отпечаток M1:
`5F1F 7718 559F 8F57 FFE1  1780 55BB 1162 F17A 5CB0`;
`S1` в Environment `release`, закрытая часть `S2` на носителе у заказчика.

## 1. Что и чем подписывается

| Объект | Чем подписан | Кто проверяет |
|---|---|---|
| `SHA256SUMS` релиза (в нём — имя и sha256 `.deb`) | подключ `S1` (в CI) | `Verifier(purpose="release")` в GUI и в root-помощнике |
| `catalog.json` (каталог моделей) | тот же `S1` для публичного каталога | `Verifier(purpose="catalog")` |
| корпоративный каталог | ключ организации (`policy.conf: catalog_pubkey`) | `Verifier(purpose="catalog")` с админской связкой из `/etc/astra-voice/` |
| `trust.json` (эпоха доверия, отзыв) — M8 | офлайн-подключ `T` с точным пином (K-2/У93); мастер cert-only и подписывать данные не умеет | план M8: `Verifier("trust", keyring, pinned={T})`; сейчас у `Verifier` цели только `release` и `catalog` |

Разделение целей (`purpose`) обязательно: каталог, подписанный релизным ключом,
и релиз, подписанный каталожным, отвергаются (гейт T-31).

Проверка идёт через `gpgv --status-fd 1 --keyring <абс. путь> --homedir <пустой>`
и принимает результат **только** по строке `VALIDSIG`. Для релиза и каталога отпечаток
должен быть в `PINNED_FINGERPRINTS` и отсутствовать в `REVOKED_FINGERPRINTS`
(`src/astra_voice/security/verify.py`). Код возврата и `GOODSIG` сами по себе не признак:
`man gpgv` (2.2.40) прямо говорит, что просроченные и **отозванные** ключи не проверяются, —
отзыв ведём мы, списком в коде.

## 2. Владение ключами

| Ключ | Тип | Где хранится | Кто владеет |
|---|---|---|---|
| **Мастер M1** | Ed25519, только сертификация (`cert`) | создан на рабочей машине заказчика; закрытая часть затем перенесена на носитель | заказчик (ArrivaRUS) |
| **`S1`** | Ed25519, подпись, до 26.09.2027 | секрет GitHub Environment `release` (required reviewer, доступен только job по тегу `v*`) | заказчик; CI получает только его |
| **`S2`** | Ed25519, подпись, до 26.09.2027 | закрытая часть — на носителе у заказчика, рядом с мастером; публичная — в `release.gpg` заранее | заказчик |

Разработчики закрытых частей не получают. Мастер в CI не попадает **никогда**.

## 3. Ротация

Плановая, раз в 12 месяцев или при истечении срока `S1`:

1. релиз N поставляется со связкой `мастер + S1 + S2`, подписан `S1`;
2. релиз N+1 подписывается `S2`, связка = `мастер + S2 + S3` (новый резерв сгенерирован офлайн);
3. клиенты релиза N принимают N+1 без внешнего канала — `S2` у них уже есть;
4. `PINNED_FINGERPRINTS` править не нужно, пока закреплён отпечаток **мастера**:
   `VALIDSIG` отдаёт первичный отпечаток последним полем, `verify.py` пинит и его.

Перед выпуском релиза без `S1` переподписать ключом `S2` встроенный и публичный
каталог (`data/catalog.json.sig`); иначе клиенты получат `NO_PUBKEY`.
Клиент, пропустивший релиз с новым подключом в связке, не примет следующий:
нужен промежуточный релиз или установка по треку администратора.

Сейчас `S1` и `S2` истекают в один день, 26.09.2027. При церемонии M2 продлить
`S2` мастером: `gpg --quick-set-expire 5F1F7718559F8F57FFE1178055BB1162F17A5CB0 2y 9053EE0C0085683CE6C7042EDC2E593225D80428`
и заново экспортировать связку (K-4). Отпечатки при продлении не меняются.

Экземпляр отпечатков и дат публикуется в `README.md` и в теле GitHub Release.

## 4. Церемония преемника M2 (офлайн) — инструкция заказчику

M1 и его `S1`/`S2` созданы 26.09.2026 по прежней версии этой инструкции на
рабочей машине заказчика (см. «Статус» выше). Для M2 выключить Wi-Fi и кабель:
отсутствие сети заодно останавливает ИИ-агентов на машине. Лучше загрузиться
с live-USB Astra. Флешка к началу церемонии уже должна быть зашифрована.
Ниже команды выполняются без сети; пустой `GNUPGHOME` для M2 создаётся сразу
на флешке.

```sh
export GNUPGHOME=/media/<флешка>/astra-voice-gnupg
mkdir -p "$GNUPGHOME"
chmod 700 "$GNUPGHOME"
cd "$GNUPGHOME/.."  # публичный экспорт и секрет S1 остаются на зашифрованной флешке

# Мастер только для сертификации, без срока; на запрос gpg задать пароль.
gpg --quick-gen-key "Astra Voice Release <alekovalev@astralinux.ru>" ed25519 cert never
MASTER=$(gpg --list-keys --with-colons | awk -F: '/^fpr:/{print $10; exit}')

gpg --quick-add-key "$MASTER" ed25519 sign 1y  # S1: рабочий
gpg --quick-add-key "$MASTER" ed25519 sign 2y  # S2: резерв
gpg --quick-add-key "$MASTER" ed25519 sign 5y  # T: только trust.json, офлайн, не в CI (K-2)

gpg --export "$MASTER" > release-m2.gpg
gpg --list-keys --with-subkey-fingerprints "$MASTER"  # записать отпечатки M2, S1, S2 и T

# Подставить отпечаток именно S1; не использовать буфер обмена.
gpg --export-secret-subkeys --armor '<S1-fpr>!' > s1-secret.asc
export TMPDIR=/dev/shm  # проверочный дом с импортированным секретом — тоже в tmpfs
TMPH=$(mktemp -d)
gpg --homedir "$TMPH" --import s1-secret.asc && gpg --homedir "$TMPH" --list-secret-keys
# Убедиться: одна ssb — S1; sec# — заглушка; S2 и T отсутствуют.
rm -rf "$TMPH"
gpgconf --kill gpg-agent
```

Секрет `S1` можно сохранять в файл на той же зашифрованной флешке или в tmpfs
`/dev/shm`, но не передавать через буфер обмена. Сертификат отзыва `.rev` из
`$GNUPGHOME/openpgp-revocs.d/` перенести отдельно от мастера (бумага в сейфе
или третий носитель) и удалить его с флешки с мастером. Сделать вторую копию
зашифрованной флешки и проверить, что она открывается. После проверки флешку
отмонтировать **до подключения сети**. На онлайн-машине открыть зашифрованную
флешку (или использовать файл в tmpfs) и из каталога с `s1-secret.asc` выполнить:

```sh
gh secret set GPG_SIGNING_KEY --env release --repo ArrivaRUS/astra-voice < s1-secret.asc
shred -u s1-secret.asc
```

`shred -u` на SSD/флешке не гарантирует стирания, поэтому файл допускается
только на зашифрованном носителе или в tmpfs.

Для M2 отпечаток **добавляется** в `PINNED_FINGERPRINTS` рядом с M1; связка
`data/keys/release.gpg` содержит M1 + M2 со всеми их подключами. Встроенный
`data/catalog.json.sig` переподписывается `S1` нового мастера. После v1.0 пин
M1 снимается. Отпечаток M2 публикуется в `README.md` и `docs/INSTALL-ADMIN.md`
(раздел 2).

## 5. Компрометация подписывающего ключа

Порядок при подозрении на утечку `S1`:

1. **Отозвать доступ CI**: удалить секрет из Environment `release`, отключить job `release`.
2. **Опубликовать `trust.json`** (с M8) с новым `trust_epoch` и `revoked = [S1]`, подписанный
   офлайн-подключом `T` с точным пином. Он принимается «из файла» администратором — отзыв доезжает без установки пакета.
3. **Выпустить релиз**, подписанный `S2`, со связкой **без** `S1` и с
   `REVOKED_FINGERPRINTS += <S1-fpr>` в коде. Сертификат отзыва в связку класть бессмысленно:
   `gpgv` его игнорирует.
4. **До выпуска релиза переподписать встроенный и публичный каталог** моделей
   (`data/catalog.json.sig`) ключом `S2`, иначе клиенты получат `NO_PUBKEY`.
5. **Объявить**: GitHub Release + `README.md` + канал заказчика — отпечатки старого и нового ключей,
   дата, номер версии, с которой действует отзыв.

Остаточный риск принят и назван честно: пока пользователь не поставил релиз с отзывом,
украденный ключ подписывает и «версию с огромным номером». Онлайн-якоря доверия у офлайн-продукта
нет; смягчение — трек B (администратор ставит пакет вручную, сверив отпечаток по `INSTALL-ADMIN.md`).

Компрометация **мастера** = смена якоря доверия: новый мастер, объявление по всем каналам,
переустановка пакета администратором с ручной сверкой отпечатка. Автоматического пути нет.

Сертификат отзыва `.rev` хранится отдельно от мастера: бумага в сейфе или третий
носитель. Заранее его не публикуют (K-8).

## 7. Сообщения об уязвимостях

- **Основной канал:** GitHub Security Advisories репозитория `ArrivaRUS/astra-voice`
  (Security → Report a vulnerability) — приватное обсуждение до выпуска исправления.
- **Резервный канал:** `alekovalev@astralinux.ru`.
- **Срок реакции:** подтверждение получения — 5 рабочих дней; оценка и план — 15 рабочих дней;
  исправление критичного дефекта — очередным релизом, внеочередным при активной эксплуатации.
- Просьба не публиковать детали до выхода исправления; в сообщении полезны версия пакета
  (`dpkg-query -W astra-voice`), сессия (KDE/Fly) и шаги воспроизведения. Аудио и распознанный
  текст присылать **не нужно** и не следует.
