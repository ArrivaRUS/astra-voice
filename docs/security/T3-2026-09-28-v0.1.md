## 2. Релизный конвейер: от тега до ассетов (п. 1 брифа)

Как устроено: `scripts/release.sh vX.Y.Z --push` (человек) выполняет предпроверки и ставит аннотированный тег, `git push`
идёт через `gh` тем же PAT. Дальше `ci.yml`: все job → `release`. Там ждём одобрения → checkout `fetch-depth: 0` →
тег = changelog (`:295-302`) → тег — предок `origin/main` (`:312-316`) → `check_keyring.py` (`:317-318`) → колёса и сборка
(`:319-323`) → `SHA256SUMS` + импорт S1 + `check_signing_secret.py secret` + подпись `-u "<S1>!"` + `gpgv` +
`check_signing_secret.py signature` (`:324-341`) → `gh release create` (`:342-353`).

Что проверено и в порядке:
- **Environment `release`:** required reviewer ArrivaRUS, `prevent_self_review: false` (при одном reviewer так и
  должно быть, иначе некому одобрить); политика деплоя — одно правило `v*` типа tag. Тег `v0.1.0` под неё подходит.
- **Rulesets:** `release-tags` (создание/изменение/удаление `refs/tags/v*`) и `main-guard` (удаление, force-push);
  обход у обоих — роль Repository admin, `always`. Actions: только GitHub-owned, SHA pinning. `ci_lint.py`: ok.
- **Сможет ли заказчик создать тег:** да, он admin. Для текущего PAT API возвращает `current_user_can_bypass: "always"`,
  то есть `release.sh --push` с этой машины пройдёт ruleset. Проверено по API; живой push тега я не делал — по брифу нельзя.
  **Сможет ли CI:** создавать тег CI не нужно — `gh release create` вешает релиз на уже существующий тег.
  `GITHUB_TOKEN` (приложение github-actions) обход не имеет, так что если тега почему-то нет, публикация упадёт,
  а не создаст его. Поведение правильное.
- **Обход для PAT владельца — главное следствие:** ruleset `release-tags` **не отделяет агентов от человека**. Он
  защищает от ролей без admin: `GITHUB_TOKEN`, будущие коллабораторы, deploy keys. Реальный барьер между агентом и
  секретом — только одобрение deployment в браузере (§3.2 P2-1, §6).
- **Секрет:** сейчас в CI настоящим секретом не пользовались ни разу — тегов и релизов нет (`gh api …/tags` → `[]`).
  Проверка состава секрета (`check_signing_secret.py secret`) до подписи и проверка подписанта после неё — на месте.
  Если секрет выгружен с паролем или не тем набором, job упадёт **до** публикации с понятным `::error::` (§3.4 О-3).
- **Связка и каталог:** sha256 `data/keys/release.gpg` = `6847a5b4…b7f7` — тот же, что в T2; `check_keyring.py` → OK
  (предупреждение K-4: у S1 и S2 один срок, 2027-09-26); связка в пакете байт в байт совпадает с репо;
  `gpgv` каталога → `VALIDSIG 7602…4D79 … 5F1F…5CB0`.
- **`tools/validate release`:** читает файлы через `lstat`+`O_NOFOLLOW`+`fstat` с лимитом, один снимок; связка по
  умолчанию из репо сравнивается с `release.gpg` из ассетов побайтно; `Verifier` с пинами из кода; покрытие
  `SHA256SUMS`, запрет путей и повторов; `dpkg-deb -f` по копии; строгий `latest.json` (`tools/validate:80-300`).
  Посторонний `pub` в скачанной связке отсюда не пройдёт — в отличие от ручной инструкции (P1-2).
