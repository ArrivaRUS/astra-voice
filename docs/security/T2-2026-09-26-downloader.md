## 3. Находки

### P1-1 · Усечённый ответ с `Content-Length` считается повреждением: `.part` удалён, следующий источник не пробуется, UI сносит весь staging

**Где:** `src/astra_voice/models/downloader.py:494-498` (`written != file.size` → `DownloadError("bad-checksum", "Файл загружен не полностью…")`), `:332-335` (`bad-checksum` → `part.unlink`), `:32` и `:401` (`bad-checksum` ∉ `_MIRROR_CODES` → `raise`), `src/astra_voice/ui/model_downloads.py:751` (`fail_reason("bad-checksum") == "bad-sha"`) и `:2129-2130` (`failed:bad-sha` → `discard_staging` **всего** staging, включая уже проверенные файлы модели).

**Вектор:** сервер (или что угодно на пути: прокси с лимитом размера/времени, CDN-узел, MITM с корпоративным CA — по модели он легитимен, B4) отдаёт заголовок `Content-Length: <size>`, часть тела и закрывает соединение **штатно** (FIN). `urllib3 1.26` (`enforce_content_length=False`, Debian 12 / Astra 1.8) и `http.client.read(amt)` молча возвращают `b""`; для загрузчика это неотличимо от «файл кончился» → `bad-checksum`. Итог: сохранённая половина уничтожена, `github`/`corp` не опрошены, пользователь видит «Файл не прошёл проверку — загруженное удалено», а для многофайловой модели теряются и уже скачанные соседние файлы. Chunked-обрыв при этом даёт `ProtocolError` → `host-unreachable` → зеркало с `Range` работает — то есть исход зависит от кодирования ответа, а не от факта обрыва. Строка была и на main (`downloader.py:357` main), но диф добавил снос staging (`:2129`) и объявил перебор/докачку целью — противоречие с N-17 («обрыв на 60 % → «Повторить» продолжает с `Range`») и T-80.

**Воспроизведение (сделано, §Приложение A/B):** два loopback-сервера, первый — `Content-Length=10240`, отдаёт 5120 и закрывает; второй — честный с `Range`. Результат: `code='bad-checksum' → fail_reason='bad-sha'`, `.part сохранён: False`, `запросы к зеркалу: []`. Контроль: первый chunked без завершающего чанка → `host-unreachable` → зеркало получило `Range: bytes=5120-`, файл собран, sha ok.

**Что делать (developer):** в `_download_file` различать «не хватило байт при штатном EOF» и «сумма не сошлась при полном размере»: первое → новый код (например `short-read`), **входит в `_MIRROR_CODES`**, `.part` **не удаляется** (следующий источник докачает `Range` с проверенного префикса, sha256 всё равно сверяется в конце); `bad-checksum` оставить только для `written == size && digest ≠ sha256`. В `fail_reason` `short-read` → `server` (или `no-network`). `discard_staging` при `bad-sha` — удалять только испорченный `.part` (это уже делает загрузчик), не весь staging: проверенные файлы перечитает установщик (О2.1), повторная закачка их — лишний трафик и лишняя окно для DoS. В `tests/unit/test_models_downloader.py` fault-серверу добавить режим `truncate` (Content-Length полный, тело короче, чистый FIN) и тест: зеркало опрошено с `Range: bytes=<n>-`, `.part` сохранён, итог — успех; плюс тот же режим на последнем источнике → отказ без удаления `.part`.

**Серьёзность:** P1 — не blocker (целостность не страдает), но это отказ в обслуживании с нулевой стоимостью для любого посредника и потеря прогресса вопреки объявленной гарантии и плану (`plans.md:401`: «сеть → следующий»); чинится локально. Astra: major, подтверждено независимо (`Content-Length: 16`, тело 4 байта, EOF).

### P1-2 · Allowlist обходится через расхождение IDNA: проверка видит corp-хост, `requests` подключается к чужому домену

**Где:** `src/astra_voice/net/http.py:82` (`_validate_url`: `parts.hostname.encode("idna")` — IDNA2003/nameprep, `ß → ss`, `ς → σ`, ZWJ/ZWNJ удаляются) и `:64` (`_extra_host_allowed` — тот же кодек); транспорт `requests` кодирует хост через `idna.encode(host, uts46=True)` (IDNA2008: `ß` остаётся `ß` → `xn--…`). Вызов на каждом хопе (`:483`, `:550`) не помогает — расходятся не хопы, а два кодека на одной строке.

**Вектор:** `corp_base=https://fass.example` (любая метка регистрируемого домена с `ss`, `σ`-вариантами и т. п.: `assets`, `access`, `express`, `rosstat`…). Ответ первого источника (HF/GitHub — по модели B4 «3xx на любой хост» это ожидаемая враждебная возможность, allowlist и есть контроль против неё; либо сам corp-сервер/его прокси) — `302 Location: https://faß.example/probe`. `_validate_url` → `fass.example` == corp → **разрешено**; `requests` → `https://xn--fa-hia.example/probe` — домен, который атакующий регистрирует сам и получает на него обычный DV-сертификат, корпоративный CA не нужен. Дальше: GET с нашим UA на чужой хост (egress-контроль побеждён, IP/модель утекают), любые байты в ответ (sha256 отбросит, целостность держится), DoS по P1-1/P2-3. Воспроизведено на `requests.PreparedRequest.prepare_url` без сети (§Приложение Q1c′): `fass.example ↔ xn--fa-hia.example`, `rosstat.ru ↔ xn--rotat-mqa.ru`; fullwidth-латиницу `requests` отвергает сам (`InvalidURL` → `not-allowed`) — там расхождения нет. Для публичных хостов эксплуатации нет: расхождение остаётся внутри зоны `huggingface.co`/`hf.co`, чужой поддомен там не зарегистрировать.

**Что делать (developer, до мержа):** в `_validate_url` **отвергать не-ASCII хост** до любой нормализации (`if not (parts.hostname or "").isascii(): raise NetworkError("not-allowed", …)`) — allowlist ASCII, `corp_base` администратор задаёт в punycode (документировать в P2-2); то же в `corp_origin`/`_extra_host_allowed`. Альтернатива — нормализовать тем же `idna.encode(uts46=True)`, что и `requests`, но запрет проще и не зависит от версии библиотек. Тест T-119.

**Серьёзность:** P1/major — обход единственного контроля против враждебного 3xx; предусловие (ответ с allowlist-хоста под контролем атакующего + `corp_base` с отображаемой меткой) сужает круг, но фикс — одна строка. Изначально я оценивал как minor (смотрел только поддомены HF) — Astra права.

### P2-1 · При заданном `corp_base` клиент сначала идёт в публичный интернет

**Где:** `downloader.py:363-380` — `sources = [hf, github…] + [corp]`; corp всегда последний.
**Вектор/риск:** администратор задал корпоративное зеркало, но каждая машина парка при каждой загрузке первым делом обращается к `huggingface.co` (и `github.com`): наружу уходят IP, факт использования утилиты, выбор модели (У22); при доступном HF корпоративное зеркало не используется вовсе; при закрытом файрволе — по 3 с connect-timeout на два публичных хоста на каждый файл. `PRIVACY.md:27-29` говорит «либо … либо корпоративное зеркало» — читатель ожидает альтернативу, а не запасной вариант; дух У38 («в корпоративном профиле публичного fallback нет») — тот же.
**Что делать:** решение Юрки/заказчика: (а) `corp_base` задан ⇒ corp **первый**, публичные — запасные; (б) дополнительно ключ `corp_only=true` (или `profile=corp`) — публичных источников нет вовсе. Документировать в `INSTALL-ADMIN.md` и `PRIVACY.md`. Тест T-117.

### P2-2 · `corp_base`/`ca_bundle` теперь действуют, а `INSTALL-ADMIN.md` говорит обратное; семантика не описана

**Где:** `docs/INSTALL-ADMIN.md:249` («Сетевого зеркала (ключи `catalog_url`, `corp_base`) в v0.1 нет») и `:335` (таблица «ключи, которые в v0.1 не действуют» включает `corp_base`); `:315` про `ca_bundle` не говорит, что он **заменяет** системный набор для всех хостов, включая HF/GitHub.
**Риск:** администратор корпоративного контура настроит `ca_bundle` только с корпоративным CA — публичные источники перестанут работать (или наоборот, решит, что `corp_base` ничего не делает и оставит тестовый адрес). Неверная документация ключа, который расширяет egress-allowlist, — это ИБ-дефект конфигурации, не косметика.
**Что делать (tech-writer, до релиза с ключом):** описать `corp_base`: только `https`, без userinfo/`?`/`#`, хост точный (без поддоменов), порт закреплён (`host:8443` разрешает только 8443), URL `{corp_base}/{id}/{revision}/{path}`, порядок источников (по решению P2-1), что редиректы с corp на публичные хосты и обратно допустимы (P2-5), что `ca_bundle` действует на все хосты и должен содержать и публичные CA, если публичные источники не отключены. Убрать `corp_base` из таблицы «не действуют».

### P2-3 · `bad-checksum` при полном размере не переводит на следующий источник

**Где:** `downloader.py:32` (`_MIRROR_CODES`), `:401`, комментарий `:30-31` — сознательный выбор.
**Риск:** первый источник (HF или посредник с доверенным CA) отдаёт файл нужного размера с другим содержимым → на каждой попытке пользователя отказ до того, как дойдёт до `github`/`corp`. Атакующий, способный на это, может и вернуть 500 (тогда перебор сработает), поэтому **дополнительной** возможности у него немного, но «отказ навсегда вместо запасного источника» — худший из вариантов для парка с corp-зеркалом. Склейки нет: `.part` уже удалён до любого перехода.
**Уточнение Astra (подтверждаю по коду `downloader.py:427-439`, `:473`): отравленный префикс ломает честное зеркало.** Первый источник отдаёт 2 «чужих» байта и обрывает соединение сетевой ошибкой → `.part` = `XX` **сохраняется** (сетевой код), digest пересчитывается с диска; честный GitHub отвечает на `Range: bytes=2-` правильным хвостом → `XXcdef…` → `bad-checksum` → `.part` удалён, corp не вызывается, виноватым выглядит GitHub. Склейка чужих байт **происходит**, но установка блокируется sha256 — целостность держится, страдает доступность. Механизм существовал до дифа. Astra: major доступности; я оставляю P2 (нужен враждебный первый источник, доброкачественный прокси байты не портит), но фикс должен идти вместе с P1-1.
**Что делать:** решение Юрки. Моя рекомендация — (а) при `bad-checksum` **после докачки** (`offset > 0`) удалить `.part` и повторить **тот же** источник один раз с нуля (снимает отравленный префикс, честное зеркало не наказывается); (б) при `bad-checksum` с нуля — переходить к следующему источнику **с `WARNING` в журнале** «источник N (hf) отдал файл с неверной контрольной суммой» (это единственный сигнал о подмене/порче, его нельзя терять); если (б) оставить как есть — зафиксировать в `threat-model.md` §3.4 «принято без контроля» и переписать T-80/N-17. Тест T-122.

### P2-4 · Запрещённый редирект (`not-allowed`) не переводит на следующий источник, текст вводит в заблуждение

**Где:** `downloader.py:32`, `:401`; `fail_reason("not-allowed") == "not-allowed"` → карточка «источник запрещён настройками» (`model_downloads.py:103`).
**Риск:** HF/посредник отвечает `302 Location: https://evil.example/…` → отказ всей загрузки; пользователь и админ ищут проблему в `policy.conf`. `test-plan.md` T-16 обещает «переход к следующему источнику». Безопасность перехода: следующий источник валидируется независимо.
**Что делать:** решение Юрки (в паре с P2-3). Рекомендация: отдельный код для «редирект на запрещённый адрес» (`bad-redirect`) ∈ `_MIRROR_CODES`; `not-allowed` оставить для начального URL (ошибка конфигурации). Текст для последнего источника: «сервер перенаправил на запрещённый адрес».

### P2-5 · `extra_hosts` глобален: редиректы hf → corp и corp → публичные разрешены

**Где:** `http.py:471`, `:483`, `:550` — один список для всех запросов; `model_downloads.py:424`.
**Риск:** (а) публичный источник может отправить клиент на `https://corp.example:8443/<любой путь>` — GET с нашим UA без кредов внутрь корпоративной сети, ответ принимается только при совпадении sha256 (ущерб мал, но это cross-origin переход, инициированный чужим хостом); (б) corp-зеркало (или его прокси) может 302-нуть на HF — утечка, которую администратор хотел исключить.
**Что делать (developer, M7 вместе с `NetworkPolicy.check`):** область допустимых хостов на запрос: для публичных источников — только `ALLOWED_HOSTS`; для corp — только corp host (на всех хопах). Тест T-118.

### P2-6 · Удалена запись «Запрос к <host>» — контроль У66/ИБ-21 остался без реализации

**Где:** `http.py` (строка `log.info("Запрос к %s", host)` удалена); `test_net_http.py` теперь требует отсутствия записей; `threat-model.md` У66 и `test-plan.md` ИБ-21 ссылаются на запись.
**Риск:** для администратора/расследования единственный след сетевых обращений — `tcpdump`/журнал прокси; «Собрать диагностику» ничего о сети не скажет. Приватности удаление не нарушает (`PRIVACY.md` не обещает записи).
**Что делать:** любой из двух вариантов, но зафиксировать: (а) вернуть `INFO` без хоста и пути — «Загрузка модели: источник hf, попытка 1 из 3» в `downloader.py` и `DEBUG` «перенаправление N» в `http.py`; (б) оставить как есть и исправить У66, ИБ-21, добавить абзац в `PRIVACY.md` («журнал не фиксирует сетевые обращения; проверка — `tcpdump`»).

### Проверено — замечаний нет

Редирект проверяется на каждом хопе включая corp-хост; `Location` c `\`, управляющими, `https:host`, `//host`, userinfo, чужим портом — отказ; регистр и fullwidth-латиница нормализуются; `https:///` — отказ. `TLS verify` никогда не `False`. Гейт `offline`/`profile≠personal`/`INVALID`/`HF_HUB_OFFLINE` закрывает corp наравне с публичными. `Content-Length` не влияет на запись; лишний байт — `too-large` до записи, `.part` удалён; 200 после `Range` — с нуля; 206 без корректного `Content-Range` — сброс и повтор, затем `bad-status`; докачка с другого источника — digest с диска, sha256 в конце. `installer` перечитывает все файлы до `commit`/`set_current`. Пути `id`/`revision`/`path` и `discard_staging` — внутри store, ссылки не разыменовываются. На провод — только `Host`/`UA`/`Accept-Encoding`/`Connection`/`Range`. Трейсбеков и хостов в журнале/карточках нет; `fail_reason` — закрытый список. `.part` при отмене/паузе сохраняется (пауза «нет места» проверяет остаток каждые 0,5 с). Простой 30 с → `timeout` → следующий источник, `.part` сохранён (тесты дифа это фиксируют).
