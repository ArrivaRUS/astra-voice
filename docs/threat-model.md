## 4. Ответы на вопросы архитекторов

### 4.1 Root-помощник: Python под `python3 -I` или C-ELF? — **Python приемлем**
- Что реально защищает помощник: не язык, а **протокол** (У1–У2): один argv-вариант, копия через fd, проверка копии,
  фиксированный env и абсолютные пути. Всё это одинаково реализуемо на Python и C; на C добавляется риск ошибок памяти
  при разборе `.deb`/вывода `gpgv`, на Python — риск «подсунуть импорт», который снимается `-I` (нет `PYTHONPATH`,
  user-site, `sys.path[0]`), stdlib-only и тем, что `/usr/lib/python3.11` — root-owned из состава ОС.
- `pkexec` 122 сам чистит окружение (`LD_*`, `PYTHON*`), CVE-2021-4034 закрыт; polkit `exec.path` работает со скриптом
  (ядро исполняет shebang `#!/usr/bin/python3 -I`, polkit проверяет путь программы). `python3 -I` в shebang — одна
  строка, Linux передаёт её как один аргумент — корректно.
- ЗПС v1.1: скрипт = **0 объектов ГОСТ-подписи**; интерпретатор `/usr/bin/python3` подписан изготовителем. C-ELF = +1
  объект и +1 позиция в SBOM/ELF-инвентаре ради нуля выигрыша. Единственный режим, где Python проигрывает, —
  «блокировка интерпретаторов» поверх ЗПС; в нём не работает и сам продукт, так что трек B там всё равно единственный.
- **Условия приёма** (в `plans.md`, веха M8): (1) файл `root:root 0755`, shebang `#!/usr/bin/python3 -IS` (`-S` — без системного `site`, Astra; проверить, что stdlib грузится без него);
  (2) stdlib only, без `import astra_voice`, без правок `sys.path`; (3) `os.environ.clear()` + фиксированный набор;
  (4) argv строго `install <абс. путь>`; (5) копия через fd, staging `O_DIRECTORY|O_NOFOLLOW` + `fstat` uid 0 / 0700;
  (6) `gpgv --status-fd` с пином fingerprint (4.2); (7) `dpkg-deb --field` и `dpkg --compare-versions` по копии;
  (8) `apt-get` с фиксированным argv, без `--allow-unauthenticated`; (9) `syslog`; (10) unit-тесты с фейками
  `gpgv`/`apt-get` через **абсолютные пути в тестовом chroot-каталоге**, а не через `PATH` (PATH помощник игнорирует).

### 4.2 `gpgv` + закреплённый keyring (Ed25519) — достаточно? Ротация и отзыв
- **Достаточно для подлинности и целостности**, при трёх уточнениях: (а) `gpgv --status-fd 1 --keyring <abs>`;
  успех = есть `VALIDSIG <fpr>` **и** `fpr ∈ PINNED_FINGERPRINTS` **и** `fpr ∉ REVOKED_FINGERPRINTS`; одного `GOODSIG`
  и кода возврата мало. **Факт (`man gpgv` 2.2.40): «does not check for expired or revoked keys»** — expiry подключа и
  сертификат отзыва в keyring клиенту ничего не дают (#2 это отметил, Astra подтвердил); отзыв реализуем сами: список в коде
  + удаление ключа из keyring; expiry подключа — гигиена CI, не контроль на клиенте; последний аргумент `VALIDSIG` — fingerprint **первичного** ключа: пинить его тоже, тогда любой подключ, привязанный к мастеру и лежащий в keyring, принимается без правки кода;
  (б) keyring и список fingerprint в **одном** пакете, оба root-owned — подмена одного без другого невозможна;
  (в) `SHA256SUMS.asc` подписывает файл сумм, а имя `.deb` в нём должно совпадать с ожидаемой версией (У4).
  Проверено 26.09 (gpg 2.2.40, T2 master-key §2): `EXPKEYSIG`/`REVKEYSIG` приходят **вместе** с `VALIDSIG` и exit 0 — `verify.py` принимает, срок и отзыв на клиенте не контроль; gpg **не подписывает** истёкшим подключом и **cert-only мастером** (→ `trust.json` только офлайн-подключом T с точным пином, У93); ключ, созданный позже часов клиента → `ERRSIG` exit 2 (У92); binding-подписи gpgv проверяет — привитый подключ не проходит (Astra). S1 и S2 истекают в один день — при переводе резерва в рабочие продлять его мастером (`--quick-set-expire`, отпечатки не меняются).

- **Схема ключей.** Мастер M1 (Ed25519, cert-only, создан на рабочей машине заказчика; закрытая часть перенесена на носитель,
  CI получает только подключ) → **signing-subkey** `S1` (expiry 12 мес) в GitHub Environment `release` (required reviewer,
  только job по тегу `v*`). Keyring в пакете = мастер-pub + `S1` + **заранее сгенерированный `S2`** (закрытая часть
  не в CI: у M1 — на носителе заказчика, создан на рабочей машине; у M2 — офлайн).
  Плановая ротация: релиз N+1 подписан `S2`, keyring N+1 = мастер + `S2` + `S3`. Старые клиенты
  принимают N+1, потому что `S2` у них уже есть — **ротация без внешнего канала**.
- **Поправка Astra (принята):** заранее вшитый `S2` решает **плановую** ротацию, но не компрометацию — вор `S1` тоже подпишет
  пакет «с огромной версией и своим keyring». Поэтому доверие отделяется от `.deb`: файл `trust.json` `{trust_epoch, allowed[],
  revoked[]}` подписан офлайн-подключом T с точным пином (мастер cert-only), проверяется через `gpgv`, хранится в
  `/var/lib/astra-voice/trust/` (root, пишет помощник) и `~/.local/state` (GUI); `trust_epoch` монотонен; поставляется в `.deb`
  **и** принимается «из файла» администратором — отзыв доставляется без установки пакета. Реализация — M8; до неё (v0.1) обновлятора нет.
- **Компрометация `S1`.** Сразу: `trust.json` с новым epoch и `revoked=[S1]` (публикация + канал заказчика), релиз, подписанный `S2`, с keyring **без** `S1` (сертификат отзыва класть бессмысленно — gpgv его игнорирует) и
  константой `REVOKED_FINGERPRINTS += S1` в коде; каталог переподписать `S2`; объявление с fingerprint в README/Release.
  Окно уязвимости = пока пользователь не поставил этот релиз; из него не выйти без онлайн-якоря доверия — принимается,
  смягчение: трек B через администратора с ручной проверкой fingerprint. Каталог тоже подписан подключом → после
  обновления утилиты каталоги, подписанные `S1`, отвергаются.
- **Документ:** `docs/SECURITY.md` — владелец мастера, календарь ротации, действия при компрометации, канал сообщений об
  уязвимостях и срок реакции (закрывает ФСТЭК № 239 п. 29.3.3 «процедуры устранения уязвимостей»). Корпоративный
  `catalog_pubkey` — тот же разбор статуса; keyring администратора root-owned под `/etc/astra-voice/`.

### 4.3 Монотонная версия/дата в подписанном манифесте и релизах — **манифесту нужна, релизам нет**
- **Каталог: да.** Целый `serial` + `trust_epoch` (Astra: дата вспомогательна, `generated_at` остаётся для UI) — обязательны в
  подписанном JSON; новый манифест применяется, только если `(trust_epoch, serial)` > последнего применённого; равный — только с
  тем же sha256; состояние — в `~/.local/state/astra-voice/catalog-state.json`, **не** в очищаемом кэше;
  равный — no-op, меньший — отказ «каталог старее текущего» в строке статуса. Встроенный в пакет ↔ скачанный: берётся
  больший. Это закрывает У5 (replay ревизии, отозванной из каталога). **Expiry не вводить** — офлайн-инсталляции и трек B
  живут месяцами; freeze-атака принята (П2).
- **Релизы: нет.** Монотонность даёт `dpkg --compare-versions` + имя файла в подписанном `SHA256SUMS` + SemVer из тега;
  `latest.json` может оставаться неподписанным указателем (максимум — предложить легитимную подписанную версию или
  промолчать). Дата в `SHA256SUMS` избыточна.
