## Итог

1. Менять движок не нужно: **GigaAM v3 остаётся лучшим офлайн-русским на CPU**, и то, что
   уже стоит на машине (`csukuangfj/…-transducer-punct-…-v3-…` int8) — это официальный
   `e2e_rnnt` вариант Сбера, MIT, 222 МБ. Реальная альтернатива внутри семейства —
   **`e2e_ctc`** (те же 215 МБ, но на ~35–40 % быстрее по RTFx) и **не-e2e `rnnt`/`ctc`**
   (лучше WER, но без пунктуации).
2. Появилось два новых игрока, которых не было в июне: **GigaAM Multilingual** (июль 2026,
   220M/600M, ru CV WER 5.1 % у Large — лучше v3, но CTC без пунктуации) и **GGUF-экспорты
   от самой Handy** (`handy-computer/*-gguf`, Q4_K_M 175 МБ при том же WER) — второй сильно
   меньше по диску, но тянет за собой C++-движок transcribe.cpp.
3. Для интеграции в Python-утилиту самый дешёвый путь — пакет **`onnx-asr`** (MIT, чистый
   Python: numpy + onnxruntime): он уже умеет GigaAM v2/v3/Multilingual, T-one, Vosk,
   Whisper, Parakeet, Canary одним API и сам качает веса с HF. Это снимает 80 % работы
   по «каталогу моделей».
4. Проверка обновлений и докачка **решаются штатным HF API без токена**: `x-repo-commit`
   в HEAD, `lfs.oid` = готовый sha256 в `/api/tree` (сверено с нашим SHA256SUMS — совпало),
   `Range` даёт 206. Главный риск — **не HF-лимиты, а доступность HF из РФ**:
   `hf-mirror.com` больше не зеркало (проверено — 308 на huggingface.co).

### A2. Whisper для русского — где он объективно хуже

- Единственные варианты Whisper с приличным русским — **large-v3 / large-v3-turbo**.
  На CPU они непригодны для «зажал хоткей — получил текст»: RTFx 3,9 даже на 9800X3D
  `high`; наш замер whisper-medium-q4_1 — **14 с на любую фразу**, потому что Whisper
  всегда паддит вход до 30-секундного окна `high`.
- Маленькие Whisper на русском — **не вариант**: base даёт 38,3 % WER на Russian
  LibriSpeech против 4,4 % у GigaAM v3 rnnt `high`.
- По собственной оценке Сбера Whisper проигрывает GigaAM v3 на всех 10 наборах,
  среднее 21,0 % против 8,3 % `high`.
- Уточнение честности: **на FLEURS ru Whisper large-v3 отличный — 3,1 %** (таблица
  Multilingual). То есть Whisper хорош на чистой начитке и проваливается на телефонии,
  колл-центре, дальнем поле. Для диктовки в редакторе это скорее «сойдёт по качеству,
  не сойдёт по скорости».
- Форматы (справочно, размеры проверены):
  ggml — tiny 75 МиБ / base 142 / small 466 / medium 1,5 ГиБ / large-v3 2,9 ГиБ /
  large-v3-turbo 1,5 ГиБ / turbo-q5_0 547 МиБ ([models/README whisper.cpp](https://github.com/ggml-org/whisper.cpp/blob/master/models/README.md));
  sherpa-onnx int8 — tiny 98 МБ / base 153 / small 357 / medium 902 / turbo 987 / large-v3 1693;
  faster-whisper (CT2, репозитории fp16, int8 делается на лету при загрузке) — small 464 МБ /
  medium 1460 / large-v3 2948 / turbo-ct2 1547.

**Вывод по требованию заказчика «выбор различных вариантов Whisper»:** держать в каталоге
имеет смысл 2–3 позиции (base/small — «быстро и плохо, но многоязычно»;
large-v3-turbo — «качественно, но очень медленно на CPU»), обязательно с честными
полосками, где у base полоска качества почти пустая. Иначе пользователь выберет
Whisper и решит, что утилита плохая.

### A4. Как честно измерять ОЗУ и скорость в самой утилите

Константы «на глаз» в каталоге — то, за что Handy можно ругать (там `accuracy_score`
и `speed_score` — просто вписанные руками float’ы, см. `vendor/Handy/src-tauri/src/managers/model.rs`).
Предлагаю в нашей утилите три уровня достоверности и показывать их пользователю разной
подачей:

1. **Замерено на этом компьютере** (жирным) — появляется после первого реального
   распознавания этой моделью.
2. **Заявлено автором модели** (обычным) — из карточки/бенчмарка, со ссылкой.
3. **Оценка** (серым, с «~») — пока ничего не замерено.

**Как мерить ОЗУ.** Инференс должен жить в отдельном процессе-воркере (это и так нужно
ради «Стоп» и защиты GUI от краха ORT). Тогда:
- перед первым распознаванием запомнить `VmRSS` из `/proc/<pid>/status`;
- после — прочитать **`VmHWM`** (пик RSS за жизнь процесса) — это ровно «сколько модель
  заняла памяти в работе», без ручной семплировки;
- писать в кэш `{model_id: {peak_rss_mb, measured_at, cpu_model, audio_sec}}`;
- инвалидировать кэш при смене ревизии модели или числа потоков ORT.
Важно: мерить **после** первого прогона, а не сразу после загрузки — ORT выделяет арену
под активации лениво, и «после загрузки» даст заниженные ~250 МБ вместо реальных 415.

**Как мерить скорость.** На каждом распознавании копить `(t_ms, audio_ms)`; показывать
**медиану RTFx = audio_ms / t_ms** по последним N≥5 прогонам, отдельно от «холодного»
первого запуска (загрузка 222 МБ весов с диска — это секунды, и она не характеризует
модель). Формулировка для человека: «≈20× быстрее реального времени: фраза 6 с → 0,3 с».

**Как заполнять полоски качества/скорости.**
- Полоска **скорости** — из измеренного RTFx, шкала логарифмическая, привязка к якорям
  (RTFx 1 = 0 %, RTFx 60 = 100 %). Для незамеренных — из таблицы бенчмарка onnx-asr,
  пересчитанной на коэффициент нашей машины (у нас 20 против 42,5 у 9800X3D → ×0,47).
- Полоска **качества** — из WER одного и того же набора для всех моделей
  (предлагаю Russian LibriSpeech из onnx-asr: там есть все наши кандидаты), шкала
  `quality = clamp(1 − WER/25 %)`. **Обязательно** с подписью источника и с оговоркой
  про пунктуацию (см. «Противоречия»).

## B. Проверка обновлений модели при запуске

### B1. Новая ревизия того же репозитория

Три способа, все **без токена** (проверено — анонимные запросы отработали):

| Способ | Запрос | Что вернёт | Цена |
|---|---|---|---|
| Самый дешёвый | `HEAD https://huggingface.co/{repo}/resolve/main/{любой мелкий файл}` | заголовок **`x-repo-commit: a6039be7…`** + `etag` | 1 запрос, ответ 307, тело не качается |
| Метаданные репо | `GET /api/models/{repo}` | `sha`, `lastModified`, `siblings` | 1 запрос |
| Все ветки сразу | `GET /api/models/{repo}/refs` | `branches[].targetCommit` — для `ai-sage/GigaAM-v3` это 5 веток вариантов | 1 запрос |

Проверено вживую: для нашего репо `sha = a6039be7cee829a9044a69ac0ebaf1c191217c97`,
что совпадает с закреплённой ревизией в `handy-gigaam/model/SOURCE.txt` `high`.
Логика: хранить в конфиге `pinned_revision`; если пришедший `x-repo-commit` ≠ сохранённого —
показать «доступно обновление модели» и **дать diff-описание, а не молча обновить**
(веса могут поменять имена входов ONNX — ровно наши июньские грабли).

Отдельно: `ai-sage/GigaAM-v3` использует **ветки как варианты модели**, поэтому «новая
версия e2e_rnnt» — это изменение `targetCommit` ветки `e2e_rnnt` (сейчас
`7655ad717f81…`), а не `main` (`ec1dc1f0…`). Ловушка: следить надо за нужной веткой. `high`

### B2. Появилась ли «близкая» модель / новое поколение

| Что отследить | Как | Заметка |
|---|---|---|
| Новые экспорты у нашего автора | `GET /api/models?author=csukuangfj&search=giga-am&sort=lastModified&direction=-1&limit=10` | Проверено: возвращает ровно 8 giga-am репо, свежие сверху (v3 — 2025-12-16) |
| Любые новые giga-am в сообществе | `GET /api/models?search=giga-am&sort=lastModified&direction=-1` | Проверено: сверху шум сообщества (coreml/mlx/uzbek-fine-tune) — **нужен фильтр по автору-белому списку**, иначе пользователь увидит чужие эксперименты |
| Официальные модели Сбера | `GET /api/models?author=ai-sage&sort=lastModified&direction=-1` | Проверено: так и находится `GigaAM-Multilingual` (2026-07-14) — то есть механизм реально ловит «новое поколение» |
| GitHub GigaAM | `GET https://api.github.com/repos/salute-developers/GigaAM/commits?per_page=1` | **Релизов и тегов нет** (проверено) → следить только за `sha` последнего коммита; для «вышла v4» надёжнее сигнал — новый репо у `ai-sage` |

Практический вывод: **v4 обнаружится не через GitHub-релизы, а через список моделей
автора `ai-sage`**. Разумная политика — раз в сутки один запрос `author=ai-sage` +
один `x-repo-commit` по закреплённому репо. Итого 2 запроса в день на пользователя.

### B3. Токен, лимиты, этика

- **Токен для чтения публичных репо не нужен** — подтверждено: все запросы этой сессии
  анонимные, отдавали 200/206/307. HF лишь добавляет заголовок
  `x-hf-warning: unauthenticated…` `high`.
- Лимиты (официальная [страница Hub rate limits](https://huggingface.co/docs/hub/rate-limits),
  окно 5 минут): аноним по IP — **500 API / 3000 resolvers / 100 pages**; free-аккаунт —
  1000/5000/200. Мы это видели в ответе: `ratelimit-policy: "fixed window";"resolvers";q=3000;w=300` `high`.
  При превышении — `429` + заголовки `RateLimit`/`RateLimit-Policy`.
- Этика/частота: 2 запроса в сутки на пользователя — заведомо в пределах; в корпоративной
  сети за одним NAT-адресом даже 1000 машин дадут ~2000 запросов/сутки против 500 за
  5 минут — тоже нормально, если **разнести проверку случайной задержкой 0–30 мин
  после старта**, а не бить в момент включения рабочего дня.
- User-Agent ставить свой (`astra-voice/x.y (+ссылка на репо)`) — вежливо и помогает
  HF не считать нас ботом.

### B4. Нет сети / корпоративный прокси

| Ситуация | Поведение |
|---|---|
| Нет сети (DNS/connect fail) | **Тихий пропуск**, никаких модалок; в статусной строке ничего не меняется |
| Таймаут | Жёсткий таймаут ≤3 с на всю проверку; работа утилиты не блокируется никогда — проверка в фоне после того, как GUI готов |
| Прокси | Уважать `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` из окружения (requests/httpx это делают сами); при 407 — считать «нет сети» |
| Ретраи | Не более 1 повтора, экспоненциально; при 429 — не повторять до конца окна |
| Кэш | `~/.config/astra-voice/update-cache.json`: `{repo, last_checked_at, last_seen_sha, last_result}`; не проверять чаще раза в сутки |
| Выключатель | Настройка «проверять обновления моделей: при запуске / раз в неделю / никогда» + глобальный «офлайн-режим» (важно для закрытых контуров ALSE) |
| Закрытый контур | Предусмотреть `model_index_url` — свой URL каталога моделей внутри периметра заказчика |

## C. Загрузка моделей

### C1. Целостность и докачка — всё есть в HF API

**Открытие сессии (проверено, high):** `GET /api/models/{repo}/tree/main?recursive=1`
возвращает для LFS-файлов `lfs.oid` — это **готовый sha256**. Сверил с нашим
`handy-gigaam/model/SHA256SUMS`: `encoder.int8.onnx 369f35a7…`, `decoder.onnx 38fc7475…`,
`joiner.onnx 602ff701…` — **совпали все три**. То есть sha256 можно получить до скачивания,
одним запросом, и не хардкодить суммы в утилите.

Тот же sha256 приходит в HEAD/GET на resolve-ссылку как **`x-linked-etag`**.

Ловушка: у мелких **не-LFS** файлов (`tokens.txt`, 13 КБ) `lfs` отсутствует, а `oid` —
это git-SHA-1 блоба (40 hex), не sha256. Для них: либо считать sha256 самим после
скачивания и запоминать, либо просто сверять размер + git-SHA-1. `high`

**Возобновление:** проверено — `curl -r 0-99` на LFS-файл даёт `HTTP 206` +
`content-range: bytes 0-99/4600132`, `accept-ranges: bytes` на обоих хопах (HF и CDN
`us.aws.cdn.hf.co`). Значит:
- качать во временный `.part`, при обрыве повторять с `Range: bytes=<уже>-`;
- на 200 вместо 206 (сервер не поддержал) — начинать заново;
- в конце — sha256 всего файла против `lfs.oid`, только потом атомарный `rename`;
- при несовпадении — удалить и **не** пытаться «доклеить».

## Находки/риски

- **R1. Наша модель — не самая точная в семействе.** e2e_rnnt проигрывает обычному rnnt
  ~2–3 п.п. WER, платя этим за пунктуацию и нормализацию чисел
  ([evaluation.md](https://github.com/salute-developers/GigaAM/blob/main/evaluation.md), `high`).
  Для диктовки пунктуация важнее — выбор был верный, но в UI это надо честно показать
  («+пунктуация, −точность»), иначе полоски будут врать.
- **R2. Квантование int8 у v2 ломало скорость, у v3 — нет.** RTFx v2: 39,7 fp32 → 15,9 int8;
  v3: 42,6 → 42,8 (`high`). Это ровно объясняет наш замер v2 RTF 0,11 → v3 0,05. Вывод:
  при добавлении **любой** новой модели скорость надо перемерять, а не наследовать.
- **R3. e2e_ctc почти бесплатно быстрее.** Те же 215 МБ, та же пунктуация, WER хуже на
  ~0,2 п.п., RTFx +25 % (`high`). Кандидат на дефолт для слабых машин.
- **R4. GGUF Q4_K_M — 175 МБ при том же WER** (`med`) — но требует C++-движка
  transcribe.cpp без Python-биндингов. Соблазнительно и дорого; пока — «наблюдать».
- **R5. GigaAM Multilingual Large (564 МБ) по-русски лучше v3 на Common Voice**
  (5,1 % vs у v3 CTC 1,3 % — внимание, это разные протоколы, см. «Противоречия»),
  но **без пунктуации** → для нашей задачи не замена, а «второй режим». `med`
- **R6. Лицензии в каталоге разные.** MIT (GigaAM, Whisper, T-one — нет, Apache),
  Apache-2.0 (T-one, Vosk, sherpa-onnx), **CC-BY-4.0** (NeMo FastConformer, Parakeet,
  Canary — требует атрибуции), **CC-NC-BY** у Silero — **некоммерческая, для заказчика
  блокер**. Нужен экран «о моделях» с лицензиями. `high`
- **R7. Автообновление весов опасно.** Смена ревизии может поменять имена входов/выходов
  ONNX-графа — это уже стреляло в июне (`joiner`: ожидали `encoder_outputs`/`decoder_outputs`,
  в экспорте `enc`/`dec`). Любое обновление модели обязано прогонять смоук-инференс на
  вшитом тестовом wav и откатываться при провале. `high`
- **R8. Единственный замер ОЗУ — один.** 415 МБ на одну модель. Всё остальное в столбце
  «ОЗУ» — оценка. Не показывать пользователю как факт.
- **R9. Доступность HF из РФ** — см. C3, `low` по источникам, но риск реальный: без
  плана зеркал утилита у корпоративного пользователя может просто не скачать модель.

## Противоречия между источниками

1. **e2e vs не-e2e: кто точнее — зависит от того, есть ли в эталоне пунктуация.**
   - onnx-asr (Russian LibriSpeech, без постобработки): rnnt 4,39 % **лучше** e2e_rnnt 7,60 %.
   - GigaAM evaluation.md (тот же RuLS, **с постобработкой**): rnnt 4,4 % против e2e 6,4 % —
     разрыв меньше, но знак тот же.
   - handy-computer (FLEURS ru, эталон **с** пунктуацией): e2e_rnnt 5,35 % **лучше**
     rnnt 8,08 % — знак противоположный.
   → Единой «полоски качества» без указания протокола быть не может. Предлагаю в UI
   брать один набор (RuLS/onnx-asr) и рядом писать «+пунктуация» отдельным значком.
2. **Whisper по-русски — 3,1 % или 21 %.** FLEURS ru (таблица Multilingual) — 3,1 %;
   среднее по 10 наборам Сбера — 21,0 %; Russian LibriSpeech (onnx-asr) turbo — 10,10 %.
   Разброс объясняется составом наборов (чистая начитка vs телефония), но при цитировании
   «Whisper хуже/лучше» нужно всегда называть набор.
3. **Размер «нашей» модели: 222 МБ или 224 МБ.** SOURCE.txt пишет 214 МБ для энкодера,
   API — 224 570 820 байт (= 214,2 МиБ = 224,6 МБ в десятичных). Это МиБ vs МБ, не
   расхождение по существу, но в UI надо выбрать одну единицу.
4. **Доступ к HF из РФ**: блоги утверждают «в реестре РКН с 31.05.2025 и блокировки
   в январе 2026»; первичных подтверждений (сайт РКН, статус-страница HF) не нашёл;
   из этой сессии HF доступен. **Данных достаточного качества нет.**

## Открытые вопросы к человеку

1. **Дефолтная модель** — оставляем e2e_rnnt (как сейчас) или ставим по умолчанию
