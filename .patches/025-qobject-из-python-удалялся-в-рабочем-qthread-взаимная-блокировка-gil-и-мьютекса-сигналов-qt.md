# 025 · QObject из Python удалялся в рабочем `QThread`: взаимная блокировка GIL и мьютекса сигналов Qt

**Дата:** 2026-09-28. **Где:** CI run 36420705856 (прогон по тегу v0.1.0) — завис unit-тест
`test_model_install_failure_message_uses_reason_code`; фикс — PR #11 `09ca017` (`ui/model_downloads.py`, `ui/tray.py`).

## Что случилось
1. Шаблон `thread.started → job.run`, `job.finished.connect(job.deleteLater)` удалял job в рабочем потоке внутри
   `QThreadPrivate::finish`. `~QObject(job)` через sip проверяет Python-переопределение `disconnectNotify` у отправителя
   (QThread с Python-обёрткой) → `PyGILState_Ensure`, **держа мьютекс сигналов-слотов** Qt.
2. Одновременно главный поток под GIL (сборка мусора в 3.11 срабатывает при выделении памяти, отпуск последней ссылки)
   уничтожал другой QObject → `destroyed` → `QMetaObject::activate` → ждёт мьютекс. Мьютексы — пул из 131 по адресу
   объекта, поэтому совпадение редкое: ~1 из 200 прогонов CI; у пользователя — возможное полное зависание (CPU 0%) в конце
   установки/проверки модели. Шаблон жил с M6 (середина сентября).
3. Строка в стеке CI (`_installed_revision`) была случайной — место, где сработал GC. ptrace на машине запрещён:
   родные стеки debugger снимал своей LD_PRELOAD-библиотекой по сигналу. Воспроизведение — только усиленное:
   `sys.setswitchinterval(0.02–0.2)`, цикл ссылок через замыкание на сигналах, 6 процессов (4–6 зависаний за минуты).

## Правило
- Python-наследники QObject, жившие в рабочем `QThread`, **удаляются только в GUI-потоке и только после `thread.wait()`**:
  в конце `run` — `moveToThread(gui)` (толкать из своего потока можно), затем отпуск ссылки/`sip.delete` в GUI.
  `deleteLater` в завершившийся поток не доставляется — без переноса объект утечёт.
- Последнюю ссылку на Python-владеемый `QThread` не отпускать до `wait()` (в т. ч. лямбдой на `finished`).
- Остаток (P2 ревью): `moveToThread` в PyQt5 без `/ReleaseGIL/` — теоретически тот же класс; надёжнее вообще не держать
  Python-QObject в рабочих `QThread` (`threading.Thread` + сигналы GUI-объекта) — при следующей переделке загрузчика.
- Плавающее зависание теста — сначала подозревать продукт: снимать стеки всех потоков (faulthandler + родные), проверять
  контрольными опытами (GC выкл., объект не удаляется в рабочем потоке). Регресс — детерминированный тест потока
  `destroyed` (`DirectConnection` + `threading.get_ident()`) + stress вне CI (`-m stress`).
- Нагрузочные прогоны на машине заказчика — коротко и с предупреждением: 1,5 ч стенда отладчика заметно грели ноутбук.

(BlockingQueued на `destroyed`); там объект бессмертный, логика в `threading.Thread`. См. 026.
