# 020 · CI на main красный с 26.09 05:02, заметил заказчик по письмам GitHub

**Дата:** 2026-09-26. **Где:** job «pytest -m xvfb» (`make test-xvfb` → `xvfb-run`), segfault в
`test_metric_labels_fit_their_field` (`tests/xvfb/test_onboarding.py:2018`). Первый красный — `4bf0308` (сразу после
слияния карточки A), последний зелёный — `ad27ac5`. Дальше ~15 push подряд, каждый — письмо заказчику.

## Что случилось
Правило «после этапа — commit+push» выполнялось, а итог CI после push никто не смотрел. Локально все агенты
отчитывались зелёным: тесты у нас идут под `offscreen`+`software`, а в CI — под `xvfb`/`xcb`, где путь рендера другой
и дефект проявляется. Разница окружений была известна (Xvfb на машине нет, поднимать нельзя), но не
компенсировалась проверкой CI. Заказчик узнал о проблеме раньше оркестратора — из почты.

## Правило на будущее
1. **После каждого push в main Юрка проверяет CI** этого коммита: `gh run list --branch main --limit 3` через 10–15 мин
   (или `gh run watch <id>` в фоне). Красный — сразу debugger, и это первая строка статуса заказчику, до него самого.
2. **xvfb-тесты локально не заменяют CI.** Ветки с QML/рендером до слияния — прогон CI на ветке (push `wip/*` +
   `workflow_dispatch` или триггер на `wip/**`), слияние только при зелёном job «pytest -m xvfb».
3. **Перед каждой сборкой deb для заказчика** — статус CI на main в отчёте сборки; красный = сборка с пометкой
   «CI красный: <причина>», не молча.
4. HEARTBEAT: строка «CI main: зелёный/красный с <коммит>» в каждом снимке.
