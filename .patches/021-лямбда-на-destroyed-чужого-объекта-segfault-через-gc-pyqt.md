# 021 · Лямбда с замыканием на сигнале `destroyed` движка — segfault через сборщик мусора PyQt

**Дата:** 2026-09-26. **Где:** `src/astra_voice/ui/icons.py:121` (провайдер иконок, слит в main `ba1c945`),
CI job xvfb на PR #1: `icons.py, line ??? in <lambda>` в teardown `tests/xvfb/test_dictation_cycle.py:348`.

## Что случилось
`engine.destroyed.connect(lambda _o: _providers.pop(key, None))`. Обёртку движка мы не держим (`view.engine()` —
временный объект), лямбда живёт только в C++-прокси PyQt. `visitSlotProxies` приписывает ссылку прокси на лямбду
**любой** Python-обёртке QObject с тем же адресом. Устаревшая обёртка удалённого QML-элемента (урок 019/020: sip не все
помечает удалёнными; QQuickItem и QQmlEngine по 24 байта — адреса переиспользуются) попадает в мусор → GC «очищает»
живую лямбду, обнуляя `__closure__` → при уничтожении движка PyQt вызывает лямбду → `COPY_FREE_VARS` по NULL →
segfault. В Python 3.11 у этой инструкции нет номера строки — отсюда `line ???`. Плавающий: зависит от порядка GC и
совпадения адресов; на main 3 прогона прошли, на ветке упал. Тот же путь — закрытие программы у пользователя.

## Правило на будущее
1. **Не подключать Python-лямбды/замыкания к сигналам C++-объекта, чью Python-обёртку мы не держим** (движки из
   `view.engine()`, объекты, возвращённые Qt). Нужна реакция на уничтожение — метод живого QObject-владельца, или
   удержание без сигнала (список + `sip.isdeleted` при следующем обращении).
2. Код-ревьюер ищет `\.destroyed\.connect\(lambda` и лямбды на сигналах временных объектов; остальные места с той же
   схемой (`app.py:328–329`, `ui/model_downloads.py:2180`, `ui/tray.py:246`) — ревизия отдельной задачей.
3. Segfault со стеком `line ??? in <lambda>` — сначала проверять замыкание (`closure: None`), а не тело лямбды.
