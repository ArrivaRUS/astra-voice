# 026 · Фикс 025 через `moveToThread` + `sip.delete` в трее повесил остановку: QtDBus держит BlockingQueued на `destroyed`

**Дата:** 2026-09-29. **Где:** CI main `4ae4fc5` — `test_tray_dbus_lifetime[plasma_reply-1]` завис после слияния PR #11
(урок 025); фикс — PR #15 `4a6e4aa` (`ui/tray.py`). Попутно ревью нашло второе зависание — на выходе процесса.

## Что случилось
1. PR #11 применил правило 025 и к трею: рабочий QObject шины в конце переносился в GUI (`moveToThread`) и удалялся там
   (`sip.delete`). Но у QtDBus своя связь с получателем хуков: сигнал `destroyed` он слушает через
   **BlockingQueuedConnection**, пока его поток разрушает `QDBusConnectionPrivate`. GUI под GIL удаляет объект →
   `destroyed` ждёт поток QtDBus → тот ждёт GIL (Python-переопределения/sip) → взаимная блокировка при остановке трея.
   Тест ловил вероятностно; на старом коде новый тест внутри `app.exec_()` — 7 из 8 зависаний.
2. Фикс (вариант Б): один **бессмертный** получатель в GUI (`sip.transferto(..., None)`), соединение трея не закрывается,
   все блокирующие вызовы QtDBus — в демоне `threading.Thread` + `queue.Queue`, ответы — Python-значениями.
3. Ревью фикса нашло второе: если `join(1.0)` истёк (владелец имени не отвечает), демон постит Python-`QEvent` во время
   `~QApplication` → `cleanupThreadData` держит мьютекс очереди и удаляет sip-событие (нужен GIL), демон под GIL ждёт
   тот же мьютекс. Проба ревьюера — 3–6 из 25. Лечение: будить GUI `QMetaObject.invokeMethod(recv, "_drain",
   QueuedConnection)` (C++-событие без Python-объекта) + затвор `threading.Lock`/`closed`, закрываемый до `join`.

## Правило
- Правило 025 («удалять только в GUI») **не универсально**: если объект — получатель чужой инфраструктуры Qt с
  Blocking-связями (QtDBus-хуки, `destroyed` у служб), его **не удалять вовсе** — делать бессмертным и отцеплять логику.
- Рабочие потоки с Python-логикой — `threading.Thread`, не `QThread` с Python-QObject; в Qt передавать только значения.
- Будить GUI из не-Qt потока — `invokeMethod(..., QueuedConnection)` без Python-аргументов, **не** `postEvent` с
  Python-`QEvent`; после `shutdown` потока постов в Qt быть не должно (затвор до `join`), shutdown — до `~QApplication`.
- Регресс-тест на зависание должен **падать на старом коде** — проверять это явно (исполнитель переделал тест, который
  на старом коде не зависал); сценарии выхода — с неотвечающим владельцем (SIGSTOP по точному pid на частной шине).
- Фикс одного взаимоблокирующего места — ревью ищет тот же класс в соседних путях (выход, отвал шины, повторный setup).
