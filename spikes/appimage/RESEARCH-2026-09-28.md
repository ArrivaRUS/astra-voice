# AppImage для Astra Voice — техисследование (2026-09-28)

Кто: researcher (для Юрки). Вход: решение заказчика 28.09 (`decisions/log.md`, «AppImage — второй артефакт v0.2, 15.10»).
Метод: чтение репозитория (только чтение), `dpkg-query`/`apt-cache` и чтение `/proc`, `/sys`, `/parsecfs` на машине
заказчика (ALSE 1.8.5), веб-источники. Ничего не скачано и не установлено. Яндекс Search API недоступен (нет
`tokens_and_keys.*`), поэтому поиск шёл через WebSearch/WebFetch. Форум forum.astralinux.ru из этой сети не открылся.

Уверенность: **В** — высокая, **С** — средняя, **Н** — низкая. «Локально» — проверено на машине заказчика
(ALSE 1.8.5, KDE, ЗПС выключена), это не стоковая установка.

## 0. Выводы и рекомендация

1. **Стоковая ALSE 1.8 с Fly скорее всего готова к FUSE.** Цепочка Depends `fly-all-main → fly-fm → fly-fm-libs →
   sshfs/archivemount/smbnetfs/curlftpfs` тянет `fuse3` (setuid `fusermount3`), `libfuse3-3` и `libfuse2`. Локально
   `/dev/fuse` имеет права `crw-rw-rw-`. Все системные библиотеки, которые AppImage берёт у хоста (libGL, libX11/xcb*,
   fontconfig, libdbus, libpulse0, `pulseaudio-utils`, `gpgv`), тоже входят в замыкание Depends этого метапакета
   (локально, `apt-cache depends --recurse`, **В** для замыкания и **С** для реальных образов: корпоративные образы
   бывают урезаны).
2. **Главный риск — не FUSE, а PARSEC.** У модуля ядра есть параметр `parsec.enable_exec_on_fuse`, по умолчанию `0`
   («запуск запрещён»). Справочный центр описывает его для 1.8 ([параметры Parsec](https://wiki.astralinux.ru/pages/viewpage.action?pageId=27361844), **В**).
   Но другая статья говорит, что запрет действует **только при включённом запрете установки бита исполнения**
   (`astra-nochmodx-lock`) ([FUSE-запуск](https://wiki.astralinux.ru/pages/viewpage.action?pageId=60358775), **В**).
   Статья базы знаний 1.6/1.7 утверждает, что запуск AppImage «заблокирован от непривилегированного пользователя по
   умолчанию» ([KB](https://wiki.astralinux.ru/kb/zapusk-appimage-zablokirovan-po-umolchaniyu-275956282.html)).
   Как ведёт себя стоковая 1.8, по источникам не установить, это **пункт №1 спайка** (см. «Противоречия»).
   На машине заказчика `nochmodx=0`, а значение `enable_exec_on_fuse` читает только root.
3. **ЗПС, блокировка интерпретаторов, `noexec` на `/home` и запрет бита исполнения делают AppImage неработоспособным.**
   Это известно заранее и не лечится упаковкой. Для таких контуров остаётся только `.deb` через администратора
   (подтверждает решение 09.09, §14.3 плана #1).
4. **Рекомендуемый путь сборки — «ручной AppDir»:**
   - база — готовый переносимый Python 3.11 из `python-appimage` (manylinux_2_28);
   - pip-колёса по хэшам: `PyQt5` 5.15.11, `PyQt5-Qt5` 5.15.19, `numpy`, `python-xlib`, стек `requests`, а также
     `onnxruntime`/`onnx-asr` из нынешнего `wheels.lock`;
   - Qt урезается (лишние модули и QML удаляются);
   - свой `AppRun` вызывает наш `bootstrap.py` без изменений модели запуска;
   - упаковка — `appimagetool` 1.9.1 с **закреплённым локальным** `type2-runtime` (`--runtime-file`).

   Сборка идёт в нынешнем контейнере `debian:12`. Реальный нижний порог glibc определяют колёса (manylinux ≤ 2.28), а
   не контейнер. Значит, файл попутно запустится и на ALSE 1.7 (glibc 2.28), но проверять это до 15.10 не нужно.
5. **Запасной путь B.** Если pip-Qt 5.15.19 даст визуальные расхождения с макетом или проблемы с треем: AppDir из
   `.deb` Debian 12 (Qt 5.15.8 и Python 3.11 — как у `.deb`), собранный через `linuxdeploy` + `linuxdeploy-plugin-qt`.
   Порог — glibc 2.36, то есть только 1.8.
6. **Самообновление — своё, а не AppImageUpdate/zsync.** Схема: скачать AppImage, `SHA256SUMS` и `.asc` → `gpgv` с нашим
   пином (готовый `security/verify.py`) → смоук нового файла → атомарный `rename()` → перезапуск по согласию.
   Встроенную подпись AppImage (`--sign`) при запуске никто не проверяет, пользы для нашей модели доверия от неё нет.
7. **Интеграция с рабочим столом.** Программа сама предлагает при первом запуске «Установить для себя»: копирует себя
   в фиксированное место (`~/.local/bin/`), пишет `.desktop`, значок и автозапуск с абсолютным путём и `TryExec`, а по
   команде снимает регистрацию. На AppImageLauncher/appimaged не полагаться: их ставит root.
8. **Размер.** Оценка 110–160 МБ сжатого файла (разбор в §1.4). Это укладывается в допуск заказчика (150–250 МБ).

### 1.3 Как pip-PyQt5 тянет QML и плагины (что проверить руками)
- `PyQt5` 5.15.11 — колесо `cp38-abi3-manylinux_2_17`, 8,2 МБ, 2024-07-19 ([PyPI](https://pypi.org/project/PyQt5/#files), **В**);
  `PyQt5-Qt5` 5.15.19 — `manylinux2014`, 60,9 МБ, glibc ≥ 2.17 ([PyPI](https://pypi.org/project/PyQt5-Qt5/#files), **В**).
- Что внутри `PyQt5/Qt5/` (`qml/QtQuick/Controls.2`, `Layouts`, `Window.2`, `plugins/platforms/libqxcb.so`,
  `xcbglintegrations`, `imageformats/libqsvg`, `iconengines/libqsvgicon`, наличие QtDBus): по памяти — да, но
  **листинг колеса сегодня получить не удалось** (inspector.pypi.io не отрисовался). Уверенность **Н**, первый шаг спайка — `find`.
- Известные грабли pip-Qt/xcb: `libqxcb.so` требует `libxcb-icccm4`, `-image0`, `-keysyms1`, `-render-util0`,
  `-xinerama0`, `-xkb1`, `libxkbcommon-x11-0` (при их отсутствии: «Could not load the Qt platform plugin xcb»)
  ([Qt Forum](https://forum.qt.io/topic/93247/qt-qpa-plugin-could-not-load-the-qt-platform-plugin-xcb-in-even-though-it-was-found?page=5), **В**).
  **На ALSE 1.8 все они есть в замыкании Depends `fly-all-main`**, потому что их тянет системный `libqt5gui5`
  (локально, **В**). Решение: у хоста не брать, в бандл положить копии (их нет в excludelist, вес небольшой).
- Грабли QML/плагинов «двух Qt в одном процессе». Если в окружении окажутся `QT_PLUGIN_PATH`/`QML2_IMPORT_PATH` с
  системными путями, pip-Qt 5.15.19 подхватит плагины системного 5.15.8, и тогда возможны падения. В сессии заказчика
  этих переменных нет, но есть `QT_QUICK_CONTROLS_STYLE=org.kde.desktop` (Fly `06-fly-misc-env`); `bootstrap.py` уже
  принудительно ставит `Default` (локально, **В**). `AppRun` должен сбрасывать `QT_PLUGIN_PATH`, `QML2_IMPORT_PATH`,
  `QML_IMPORT_PATH`, `QT_QPA_PLATFORMTHEME`, `PYTHONHOME`, `PYTHONPATH` (**С**, практика; прямого источника под наш случай нет).
- Без системных platformtheme (kde/fly) диалоги и меню будут в стиле Fusion, а не нативные (§14.2 плана #1, **С**).
  Наш интерфейс — свой QML, и тема берётся из `kdeglobals`/`paletterc`, то есть от Qt не зависит.
- Трей: `QSystemTrayIcon` в pip-Qt ходит в SNI через QtDBus, а тот подгружает хостовую `libdbus-1.so.3` (**С**).
  Проверить в KDE и Fly.

### 1.5 Рекомендация по пути
**Ручной AppDir** (python-appimage → pip-колёса по хэшам → урезание → `AppRun` → `appimagetool --runtime-file`).
- Колёса ставятся тем же способом, что и в `.deb` (`pip install --no-deps --no-index --require-hashes`); появляется второй
  lock-файл `packaging/appimage.lock`.
- Модель запуска `python -I bootstrap.py {app|worker}` не меняется.
- Гейты `elf-audit`/SBOM переиспользуются, но с новым ожидаемым числом ELF (порядка сотен, не 3).
- Ни от одного заброшенного инструмента не зависим.

## 2. Базовая система сборки и glibc

- **Контейнер:** оставить `debian:12`, как у `.deb` (`packaging/Containerfile`, CI `container: debian:12`). Нужен он
  только для инструментов (`pip`, `patch`, `squashfs`, `file`, `binutils`), в полезную нагрузку ничего из Debian не идёт.
- **Реальный порог glibc определяет самое «новое» колесо:** ORT `manylinux_2_27/2_28` (max GLIBC_2.27, гейт `elf-audit`),
  Python `manylinux_2_28` (или `manylinux2014` = 2.17), Qt/PyQt `manylinux2014/2_17` (PyPI, **В**). Итог — **2.28**:
  это ALSE 1.8 (2.36) и формально 1.7 (2.28). Гейт `elf-audit --max-glibc 2.28` на весь AppDir закрепит это (**С**).
  Собирать «ниже», чем debian:12, смысла нет: glibc контейнера в бандл не попадает.
- **Что оставить хостовым** (excludelist AppImage — «библиотеки, которые считаются присутствующими на хосте и НЕ
  должны включаться»: glibc-семейство, `libstdc++.so.6`, `libgcc_s`, `libGL/EGL/GLX/GLdispatch/OpenGL`, `libdrm`,
  `libgbm`, `libxcb.so.1`, `libX11.so.6`, `libX11-xcb`, `libfontconfig.so.1`, `libfreetype.so.6`, `libharfbuzz.so.0`,
  `libasound.so.2`, `libz`, `libexpat`, `libuuid`, `libgpg-error`, `libpipewire-0.3`…
  ([excludelist](https://raw.githubusercontent.com/AppImageCommunity/pkg2appimage/master/excludelist), **В**)).
  Кроме того, у хоста брать то, чего **нет** в excludelist, но что у нас связано с системными службами:
  - `libdbus-1.so.3` — версия протокола шины должна совпадать с системной;
  - `libpulse.so.0`/`libpulse-simple.so.0` — наш `ctypes` и клиент-серверный протокол;
  - бинарники `pactl` и `gpgv`.

  Все они есть в Depends-замыкании `fly-all-main` (локально, **В**).
- **`libstdc++`.** Хостовая на ALSE — 12.2 (`libstdc++6 12.2.0-14.astra6`, локально), новее той, против которой собраны
  manylinux-колёса. Конфликта не ожидается (**С**).
- **OpenSSL/CA.** Python из python-appimage несёт свой OpenSSL. В `AppRun` нужно
  `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` (если файл есть), иначе в корпоративном контуре с собственным
  корневым сертификатом `certifi` его не увидит (**С**, [issue #24](https://github.com/niess/python-appimage/issues/24)).

| Вопрос | Ответ | Источник, уверенность |

## 4. Astra Linux и AppImage

- **Официальная позиция.** Отдельного заявления о поддержке или неподдержке AppImage не нашёл (искал в справочном
  центре wiki.astralinux.ru: статьи про AppImage, Parsec, ЗПС, Red Book, «особенности 1.8»). Есть инструкции по
  запуску ([«Запуск appimage на ALSE»](https://wiki.astralinux.ru/pages/viewpage.action?pageId=57446782) — версии
  1.6/1.7/CE 2.12, способы `parsec.enable_exec_on_fuse=1` или `--appimage-extract`; **В**).
  Собственный продукт Астры (Termidesk Live) использует AppImage и рекомендует собирать их через
  `appimagetool`+`runtime-x86_64`, причём **«на ОС, отличной от Astra Linux SE, например Alpine, Debian»**
  ([Termidesk](https://wiki.astralinux.ru/termidesk-help/6.0/dokumentatsiya/termidesk-live/live-nastrojka/dobavlenie-priloyoenij-v-termidesk-live/sozdanie-priloyoenij-formata-appimage), **В**).
  Итог: формат в экосистеме признан, но гарантий для 1.8 нет.
- **ЗПС (`DIGSIG_ELF_MODE=1`)** проверяет «исполняемые файлы и разделяемые библиотеки». Неподписанный ELF runtime
  AppImage в `$HOME` не запустится, как и сотни `.so` внутри (research/tech-platform-claude.md §A.1 со ссылкой на
  [Режим ЗПС x.8](https://wiki.astralinux.ru/pages/viewpage.action?pageId=321820023), **В**).
  - Встраиваемая подпись требует ключа, подписанного изготовителем (**В**, там же).
  - Отсоединённая подпись в 1.8 действует «для всех идентичных файлов независимо от расположения» (**В**, там же).
    Теоретически это покрыло бы файлы внутри FUSE-монтирования, но ключи и подписи загружаются root и **до**
    включения ЗПС, а каждое обновление требует администратора.
  - Проверяет ли `digsig_verif` файлы на FUSE вообще, и корректна ли `bsign`-подпись ELF с дописанным в конец
    squashfs (как устроен AppImage) — **данных нет** (искал на странице ЗПС x.8 и в справочном центре).

  **Вывод: при ЗПС AppImage — не поддерживаемый сценарий. ГОСТ-подпись файла AppImage целиком делу не поможет**:
  исполняемы не только runtime, но и все `.so` внутри образа (**С**, вывод из правил выше).
- **Блокировка интерпретаторов** (`astra-interpreters-lock`) закрывает `python` и др., но не для группы `astra-admin`.
  При её включении **автоматически включается `astra-nochmodx-lock`**, который запрещает `chmod +x` всем, кроме root
  ([astra-safepolicy](https://wiki.astralinux.ru/pages/viewpage.action?pageId=109020865), **В**).
  Следствия (вывод, **В**):
  - скачанный AppImage невозможно сделать исполняемым;
  - при nochmodx запуск из FUSE запрещён.

  Под блокировкой AppImage не работает. Проверит ли блокировка **свой** Python внутри бандла по имени — не выяснял:
  при nochmodx до этого дело не доходит.
- **`noexec` на `/tmp`, `/home`, `/var/tmp`** — **рекомендация** Red Book, а не настройка по умолчанию
  ([Red Book x.7](https://wiki.astralinux.ru/pages/viewpage.action?pageId=153486034), **В**). На машине заказчика
  `/home` смонтирован `rw,relatime`, отдельного `/tmp` нет (локально). При `noexec` на `/home` AppImage из `$HOME`
  не запустится. При `noexec` на `/tmp` FUSE-режим работать должен: у точки монтирования свои флаги (**С**, семантика
  mount в Linux), а extract-and-run — только с `TMPDIR` в `$HOME`.
- **Честное поведение продукта.** Если AppImage не может стартовать, runtime покажет только текст в терминале. Двойной
  клик в файловом менеджере даст «ничего не произошло». Поэтому нужна документация: `INSTALL-ADMIN.md` + текст на
  странице загрузки «AppImage не работает при ЗПС, блокировке интерпретаторов, запрете бита исполнения — ставьте .deb».

## 5. Самообновление

| | AppImageUpdate / zsync | Своё обновление (рекомендуется) |
|---|---|---|
| Состояние | «beta-level code» ([README](https://github.com/AppImageCommunity/AppImageUpdate), **В**); последние сборки `2.0.0-alpha-1-20251018`, AppImage 48,6 МБ ([релизы](https://api.github.com/repos/AppImageCommunity/AppImageUpdate/releases), **В**) | наш код; `security/verify.py` (gpgv + пин) уже есть |
| Формат | `zsync\|URL`, `gh-releases-zsync\|user\|repo\|tag\|file.zsync` в секции `.upd_info`; appimagetool `-u` + `zsyncmake` → `.zsync` ([доки](https://docs.appimage.org/packaging-guide/optional/updates.html), [appimagetool](https://github.com/AppImage/appimagetool), **В**) | `latest.json` + AppImage + `SHA256SUMS(.asc)` в релизе, как у `.deb` |
| Проверка подписи | документация: новый файл встаёт на место после проверки целостности «и, **как только будет реализовано**, подписи» (**В**, доки). Библиотека — C++, из Python только вызов внешнего бинарника (+48 МБ) | `gpgv` с нашим keyring и пином отпечатка мастера, sha256 из подписанного `SHA256SUMS` — **та же модель доверия, что у `.deb`** |
| Трафик | дельта (скачивает только изменившиеся блоки) | полный файл (~100–160 МБ) на каждое обновление |
| Вердикт | не подходит модели «пин отпечатка мастера» | **берём** |

Встроенная подпись AppImage (`appimagetool --sign`, секция `.sha256_sig`, ключ — в `.sig_key`) жива в appimagetool
1.9.x (**В**, [README](https://github.com/AppImage/appimagetool)). Однако runtime её **не проверяет**:
`--appimage-signature` только печатает секцию ([runtime.c](https://raw.githubusercontent.com/AppImage/type2-runtime/main/src/runtime/runtime.c), **В**).
Документация прямо говорит, что показ подписи «не сообщает, валидна ли она», а проверка делается отдельным
`validate` из AppImageUpdate ([доки](https://docs.appimage.org/packaging-guide/optional/signatures.html), **В**).
Для нас подпись необязательна. Update-information лучше **не встраивать**: иначе сторонние менеджеры AppImage смогут
обновлять файл мимо нашей GPG-проверки (**Н**, вывод).

Механика своей замены (**В** для POSIX, **С** для деталей):
1. Скачать в каталог **того же** файлового тома, где лежит AppImage (иначе `rename()` не атомарен).
2. Проверить sha256 и подпись.
3. `chmod 0755`.
4. Смоук `new.AppImage --version`.
5. `rename(new, current)`: запущенный процесс держит старый inode через FUSE-монтирование и продолжает работать.
6. Перезапуск по согласию.
7. Предыдущий файл оставить как `.old` для отката.

Уважать `policy.conf: updates=admin/offline`. Трек определять по наличию `$APPIMAGE` в окружении (runtime ставит
`APPIMAGE`, `APPDIR`, `ARGV0`, `OWD`; runtime.c, **В**).

## 6. Интеграция с рабочим столом без root

- **Где лежит файл.** Фиксированное место: при первом запуске программа предлагает «Установить для себя» и копирует
  себя в `~/.local/bin/astra-voice.AppImage` (XDG: пользовательские исполняемые — в `$HOME/.local/bin`). Так делает
  установщик Joplin: файл в `~/.joplin`, `.desktop` в `~/.local/share/applications/appimagekit-joplin.desktop`, значок в
  `~/.local/share/icons/hicolor/512x512/apps/` ([скрипт](https://raw.githubusercontent.com/laurent22/joplin/dev/Joplin_install_and_update.sh), **В**;
  при этом Joplin **не проверяет** ни контрольные суммы, ни подписи — это его слабость, не образец).
- **`.desktop` и значок** — в `~/.local/share/applications` и `~/.local/share/icons/hicolor/...`, `Exec=` с абсолютным
  путём, `TryExec=` с тем же путём. Видит ли **меню Fly** пользовательские `.desktop` — не проверено (§14.5 п.4 плана #1) → спайк.
- **AppImageLauncher/appimaged.** AppImageLauncher: `v3.0.0-beta-3` (2025-10-28), continuous 2025-12-15
  ([релизы](https://api.github.com/repos/TheAssassin/AppImageLauncher/releases), **В**) — бета, ставится пакетом, то есть
  root. appimaged — демон, который надо ставить и запускать ([Running AppImages](https://docs.appimage.org/user-guide/run-appimages.html), **С**).
  **Не полагаться.** Joplin пишет `APPIMAGELAUNCHER_DISABLE=TRUE` в `Exec`, чтобы AppImageLauncher не перехватывал
  запуск (**В**) — стоит сделать так же.
- **Автозапуск.** Сейчас `platform/autostart.py` пишет `~/.config/autostart/astra-voice.desktop` с
  `Exec=/usr/bin/astra-voice --hidden` и маркером `X-AstraVoice-Managed=true`. Для AppImage: `Exec="<путь из $APPIMAGE>" --hidden` + `TryExec`.
  По спецификации запись с непустым `TryExec`, который не указывает на существующий исполняемый файл, **не должна
  автозапускаться** ([autostart spec](https://specifications.freedesktop.org/autostart/latest/), **В**). Значит,
  переезд файла даёт тихий пропуск автозапуска, а не ошибку.
- **Переезд файла.** При каждом старте сравнивать `$APPIMAGE` с путём в своих записях (маркер уже есть) и
  перезаписывать. Если файл переехал и не запускался — меню и автозапуск молча «пропадут». Смягчение — копирование в
  фиксированное место при установке (выше) и пункт «Удалить из меню и автозапуска» (снятие регистрации).

## 7. Сосуществование с `.deb`

- **Меню.** Одинаковый desktop file ID `astra-voice.desktop`: запись в `~/.local/share/applications` перекрывает
  `/usr/share/applications`. `$XDG_DATA_HOME` важнее `$XDG_DATA_DIRS`, а при одинаковом ID используется первый по
  приоритету ([desktop-entry spec](https://specifications.freedesktop.org/desktop-entry/latest/file-naming.html), **В**).
  То есть после регистрации AppImage меню запускает AppImage, даже если стоит `.deb`.
- **Автозапуск.** Файл один (`~/.config/autostart/astra-voice.desktop`, пользовательский каталог важнее `/etc/xdg`,
  **В**, spec). Побеждает тот, кто записал последним.
- **Одновременный запуск.** Общий lock `$XDG_RUNTIME_DIR/astra-voice/lock` (`core/paths.py`): второй экземпляр не
  стартует, кто бы он ни был (**В**, код).
- **Данные.** Общие `~/.config/astra-voice`, `~/.local/share/astra-voice/models` (226 МБ модели не дублируются),
  `~/.cache`. Риск — формат `settings.json` в разных версиях: нужна прямая и обратная совместимость или поле версии (**С**).
- **Практика других.** Krita: AppImage и пакет дистрибутива используют **одни и те же** `~/.config/kritarc` и
  `~/.local/share/krita` ([David Revoy](https://www.davidrevoy.com/article322/krita-appimage-for-cats/show), **С**).
  Joplin: AppImage живёт отдельно в `~/.joplin` со своей записью меню (**В**, скрипт выше). Для Obsidian и Kdenlive
  подтверждённых описаний поведения при двух установках **не нашёл**.
- **Варианты правила для архитектора** (выбор не мой):
  - (а) если есть `/usr/bin/astra-voice` из `.deb`, AppImage при старте предупреждает и не регистрирует себя без явного
    согласия — у администратора приоритет;
  - (б) последняя зарегистрированная копия владеет меню и автозапуском.

  `policy.conf` на хосте AppImage читает так же, как `.deb`: администратор может выразить запрет, но изменённая копия
  его обойдёт. Техническим средством это не является.

## 8. CI (GitHub Actions)

- **Готовые actions.** Живого специализированного action под AppImage не нашёл. Известные обёртки завязаны на
  appimage-builder, а он заброшен (**С**). Практика — скрипт в репозитории: Electrum собирает в контейнере, берёт
  `appimagetool` 1.9.0 с type2-runtime, чинит опции `mksquashfs` ради воспроизводимости, выставляет даты файлов и
  `SOURCE_DATE_EPOCH`, удаляет `__pycache__` и изменчивые метаданные dist-info, заявляет воспроизводимость сборок
  ([make_appimage.sh](https://raw.githubusercontent.com/spesmilo/electrum/master/contrib/build-linux/appimage/make_appimage.sh),
  [README](https://raw.githubusercontent.com/spesmilo/electrum/master/contrib/build-linux/appimage/README.md), **В**).
- **FUSE в CI** недоступен в контейнере (**В**) → `appimagetool` запускать с `--appimage-extract-and-run` (или
  `APPIMAGE_EXTRACT_AND_RUN=1`), смоук готового файла — так же.
- **Воспроизводимость и закрепление.**
  - `appimagetool`, `type2-runtime` и Python-база — по sha256 в новом lock-файле; `--runtime-file` обязателен (**В**).
  - Колёса — `--require-hashes`, как сейчас.
  - `SOURCE_DATE_EPOCH` — из changelog, как в `build-deb.sh`.
  - `touch` дат и сортировка — перед `mksquashfs`.
- **Кэш.** `actions/cache` на каталог колёс и инструментов (ключ — хэш lock-файлов), как у кэша модели в job `engine`.
- **Встраивание в `release`.** Новый job `appimage` (сборка + гейты: ELF-аудит `max GLIBC ≤ 2.28`, SBOM, смоук
  `--version` через extract-and-run под `xvfb`) и артефакт в `release`. В шаге «SHA256SUMS и отсоединённая подпись»
  добавить `astra-voice-*-x86_64.AppImage` в список `sha256sum` — дальше подпись `SHA256SUMS.asc` и сверка `gpgv` те же.
  `latest.json` получает второй артефакт.
  **Правки `.github/workflows` пушит заказчик**: токен агента без Workflows (память `reference_github_agent_token`).

## Противоречия и пробелы

1. **Запрет запуска из FUSE на 1.8.** Три источника расходятся:

   заметку §A.1 стоит поправить.
3. **Проверка подписи в AppImageUpdate.** README описывает проверку GPG как задачу проекта, а документация — как
   «когда будет реализовано».
4. **libfuse2.** Страница «FUSE» в документации AppImage всё ещё велит ставить `libfuse2` — это про старый runtime.
   README type2-runtime говорит, что он не нужен.
5. **Пробелы (данных нет):**

### Что проверить руками

1. **Сборка.** AppDir в `debian:12` (podman), урезание Qt, упаковка с `--runtime-file`. Замер: размер файла, число
   ELF, max GLIBC (`tools/elf-audit`), `find PyQt5/Qt5` (QML-модули и плагины на месте).
2. **FUSE на машине заказчика:** двойной клик и запуск из терминала; `mount | grep .mount_`; время холодного и
   тёплого старта, RSS (сравнить с `.deb`: `spikes/m1_live/rss.md`).
3. **FUSE на стоковой ВМ 1.8 (Fly):**
   - то же, плюс `ls -l /dev/fuse`, `which fusermount fusermount3`;
   - включить `astra-nochmodx-lock` и повторить (ожидаем отказ; зафиксировать текст ошибки);
   - повторить под пользователем с высоким уровнем целостности.
4. **Без FUSE:** `APPIMAGE_EXTRACT_AND_RUN=1` и `TMPDIR=~/.cache/...` — время старта.
5. **Функции в KDE и Fly:**
   - трей SNI (иконки, меню), уведомления с действиями;
   - глобальная клавиша, вставка в Kate/LibreOffice/терминал;
   - захват звука (`libpulse-simple` с хоста), `pactl`;
   - тема из `kdeglobals`/`paletterc`;
   - HiDPI 1.25 на HDMI;
   - скриншоты для сверки с `.deb`.
6. **Сеть и доверие:**
   - загрузка каталога и модели по HTTPS (CA);
   - проверка `SHA256SUMS.asc` хостовым `gpgv` с пином;
   - дочерние процессы получают очищенное окружение.
7. **Интеграция:**
   - «Установить для себя» → запись в меню KDE **и Fly**, значок, автозапуск после перелогина;
   - перенос файла → автозапуск тихо пропускается (`TryExec`) → повторный запуск чинит записи;
   - снятие регистрации.
8. **Сосуществование с `.deb`:** стоят оба — что запускает меню, чей автозапуск, lock, общий `settings.json`.
9. **Замена на лету:** `rename()` нового файла поверх работающего → старый процесс жив → перезапуск поднимает новую версию.

- (1)–(2) и (5) проходят в KDE и Fly;
- размер ≤ 250 МБ;
- по (3) есть ясный ответ, который можно честно написать пользователю.
